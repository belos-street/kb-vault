# 03 — 关系建模：从 1对1 到 多对多

> **本系列基于 Prisma ORM 7.x**（2026-08 编写）。合并原「1对1/1对多」与「多对多」两篇。

- **预计时间**：60 min ｜ **前置**：02

**一句话定位**：给表装上外键——1对1、1对多、多对多、自引用全部讲完，外加级联删除与嵌套写。

**面试可答**：`@relation(fields, references)` 声明的关系在数据库里是真的 FOREIGN KEY；`onDelete` 决定删父时子的命运；N-N 选隐式（纯连接）还是显式（关系本身有属性）；自引用 N-N 必须给关系起名。

---

## 1. 关系的心智模型：两端声明

关系**成对出现**：一端是外键字段（真实列），另一端是虚拟关系字段（不落库，纯查询用）：

```prisma
model User {
  id    Int    @id @default(autoincrement())
  email String @unique
  posts Post[]          // 关系字段：不落库，供 include 查询
}

model Post {
  id       Int    @id @default(autoincrement())
  title    String
  author   User   @relation(fields: [authorId], references: [id])  // 外键声明端
  authorId Int    // 真实外键列（命名惯例：目标模型小写 + Id）
}
```

> 💡 `@relation` 声明的关系，`migrate` 时会**真的在数据库建 FOREIGN KEY 约束**——约束是真的，不是 ORM 的装饰。反向 `db pull` 时已有外键也能被识别回关系（Schema 单一数据源在关系上的体现）。

## 2. 1-N 与 1-1

```prisma
// 1-N（最常见）：上面 User/Post 即是
// 可空外键（草稿暂无作者）
model Post {
  author   User? @relation(fields: [authorId], references: [id])
  authorId Int?
}

// 1-1：外键必须 @unique，把「多」掐成「一」
model Profile {
  id     Int  @id @default(autoincrement())
  user   User @relation(fields: [userId], references: [id])
  userId Int  @unique
}
model User {
  profile Profile?   // 反向端单数、可空
}
```

> ⚠️ 1-1 铁律：外键字段不加 `@unique`，数据库层面仍是 1-N，Prisma 会直接报错。

## 3. 级联删除：`onDelete`

```prisma
model Post {
  author   User @relation(fields: [authorId], references: [id], onDelete: Cascade)
  authorId Int
}
```

| 策略 | 行为 | 适用 |
|------|------|------|
| `Cascade` | 删父同时删子 | 明细/从属数据（订单→订单项） |
| `Restrict`（默认） | 有子记录拒绝删父 | 防孤儿数据 |
| `SetNull` | 删父后外键置 NULL | 软引用（可容忍丢失） |
| `NoAction` | 事务提交时再检查 | 极少用（与 Restrict 的差异是检查时机） |

> 💡 **默认值规则**：**必填**外键默认 `Restrict`，**可空**外键默认 `SetNull`——声明 `author User?` 时级联行为已经悄悄变了，别靠默认值，显式写 `onDelete`。

## 4. 嵌套写：一条调用写多张表

```ts
// 创建用户同时写三篇文章——底层自动包在一个事务里
const user = await prisma.user.create({
  data: {
    email: "bob@example.com",
    posts: { create: [{ title: "Prisma 入门" }, { title: "关系建模" }] },
  },
})
```

嵌套 `create/update/upsert/delete` 都可用（如删用户连带 `posts: { deleteMany: {} }`）。**何时用嵌套写**：需要「要么全成要么全败」时——它就是自动事务的语法糖；需要中间判断逻辑的复杂事务用 `$transaction`（05 篇）。

## 5. 多对多：隐式 vs 显式

### 隐式 N-N（纯连接，最省事）

```prisma
model Post {
  id    Int    @id @default(autoincrement())
  title String
  tags  Tag[]
}
model Tag {
  id    Int    @id @default(autoincrement())
  name  String @unique
  posts Post[]
}
```

Prisma 自动建中间表 `_PostToTag`（按字母序命名，两列双外键 + 联合唯一），Client 不会为它生成模型（想读它只能 `$queryRaw`）：

```ts
await prisma.post.create({
  data: { title: "Prisma 进阶", tags: { connect: [{ id: 1 }, { id: 2 }] } },
})
const post = await prisma.post.findFirst({ where: { id: 1 }, include: { tags: true } })
```

### 显式 N-N（中间表带属性时升级）

```prisma
model PostTag {
  post    Post     @relation(fields: [postId], references: [id])
  tag     Tag      @relation(fields: [tagId], references: [id])
  postId  Int
  tagId   Int
  addedAt DateTime @default(now())   // 关系自身的属性
  @@id([postId, tagId])              // 联合主键，天然去重
}
// Post 侧反向端变为 tags PostTag[]（不再是 Tag[]）
```

查询要穿过中间表：`include: { tags: { include: { tag: true } } }`。

### 自引用 N-N：关注/好友

同表互指必须给两端关系**起同一个名字**区分：

```prisma
model User {
  id        Int      @id @default(autoincrement())
  following Follow[] @relation("Follows")   // 我关注的人
  followers Follow[] @relation("Follows")   // 关注我的人
}

model Follow {
  followerId  Int
  followingId Int
  createdAt   DateTime @default(now())
  follower    User @relation("Follows", fields: [followerId], references: [id])
  following   User @relation("Follows", fields: [followingId], references: [id])
  @@id([followerId, followingId])
  @@index([followingId])   // 查「谁关注了 X」走这边的索引
}
```

> 💡 同一对模型间出现**两组及以上**关系时（自引用、文章的作者/审核人），都必须 `@relation("名字")` 命名，同名即配对。

## 6. 决策口诀

- 中间表要加第三列以上（时间/角色/权重）→ **立刻显式**；纯打标纯收藏 → **隐式**（少一个模型）
- 1-1 必须外键 `@unique`；级联策略想清楚再定，默认 Restrict 最安全
- 命名惯例：外键 `authorId`、关系名 `"Follows"`——一致性就是约束

## 7. ✍️ 练习

**要求**：① 建 `User / Post / Profile`（Post 加 `onDelete: Cascade`），嵌套创建 1 用户 + 2 文章 + 1 Profile；② 删除用户，验证文章与 Profile 一并消失；③ 实现「商品收藏」：显式 N-N 的 `Favorite`（带 `createdAt`），查询某用户的收藏列表（含时间）。**提示**：`@@id([userId, productId])`；查询 `include: { favorites: { include: { product: true } } }`。**预期效果**：外键、级联、联合主键都亲眼落在迁移 SQL 里；你能说清隐式/显式的升级时机。

## 📌 小结

- 关系两端声明：外键端 `@relation(fields, references)`，反向端数组字段不落库
- `onDelete` 默认 Restrict；嵌套写 = 自动事务的语法糖
- N-N：纯连接隐式、带属性显式、自引用必须命名
