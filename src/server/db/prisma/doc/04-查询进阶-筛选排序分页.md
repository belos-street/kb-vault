# 04 — 查询进阶：筛选·排序·分页·聚合

> **本系列基于 Prisma ORM 7.x**（2026-08 编写）。

- **预计时间**：60 min ｜ **前置**：03

**一句话定位**：补齐查询工具箱——筛得精确、排得灵活、分页不卡、只拿需要的字段、统计不下载数据。

**面试可答**：查询五构件 = `where` / `orderBy` / `take+skip|cursor` / `select+include` / `aggregate+groupBy`；cursor 分页走索引定位，深分页不随页数变慢；`include` 是 N+1 的教科书解法。

---

## 1. where：筛选

```ts
await prisma.post.findMany({
  where: {
    AND: [
      { status: "PUBLISHED" },
      { OR: [{ title: { contains: "prisma" } }, { title: { contains: "ORM" } }] },
    ],
    NOT: { comments: { none: {} } },                            // 反向集合条件
    author: { is: { email: { endsWith: "@example.com" } } },    // 关联表条件
  },
})
```

| 操作符 | 含义 |
|--------|------|
| `equals` / `not` / `in` / `notIn` | 等值与集合 |
| `contains` / `startsWith` / `endsWith` | 模糊（PG 默认区分大小写，加 `mode: "insensitive"`） |
| `lt / lte / gt / gte` | 比较 |
| `has / hasSome / hasEvery` | 数组字段 |
| `is / isNot`、`some / none / every` | 关联条件（正向/反向） |
| 判空 | `deletedAt: null`（没有 isNull 这种写法） |

排序：`orderBy: [{ status: "desc" }, { createdAt: "asc" }]`（数组 = 优先级递减）；PG 支持关系排序与 `nulls: "last"`。

## 2. 分页：offset vs cursor

```ts
// offset：简单，深分页慢（SQL 是 OFFSET，扫描并丢弃前 N 行）
await prisma.post.findMany({ skip: 20, take: 20, orderBy: { id: "desc" } })

// cursor：走索引定位，翻多深都一样快
const page = await prisma.post.findMany({
  take: 20,
  skip: 1,                          // 跳过游标本身
  cursor: { id: lastPageCursorId }, // 上一页最后一条的 id
  orderBy: { id: "desc" },          // 必须与游标字段一致
})
```

- **代价**：不能直接跳页，适合 feed/列表；接口返回 `nextCursor` 传给前端（06 篇实战落地）
- **惯用法**：`take: limit + 1` 多取一条判断「还有没有下一页」，省一次 count

## 3. select vs include：投影与关系预取

```ts
// select：只取需要的字段，类型精确收缩
await prisma.user.findFirst({
  where: { email: "alice@example.com" },
  select: { id: true, name: true },
})

// include：把关联一起取出来——N+1 的解法
await prisma.post.findMany({ include: { author: true, tags: true } })

// 组合：只取我要的字段，且关系里也只取需要的字段
await prisma.post.findMany({
  select: {
    id: true, title: true,
    author: { select: { name: true } },
    _count: { select: { tags: true } },   // 顺便取关联计数
  },
})
```

- `include` 底层可能拆多条 SQL，但由 Prisma 统筹，**条数不随数据量增长**（对比循环查询的 N+1）
- `findUnique` 走主键/唯一约束更快；**能用 findUnique 就别用 findFirst**

## 4. 聚合：count · aggregate · groupBy

```ts
await prisma.post.count({ where: { status: "PUBLISHED" } })

await prisma.post.aggregate({ _sum: { views: true }, _avg: { views: true } })

await prisma.post.groupBy({
  by: ["authorId"],
  _count: { authorId: true },                 // authorId 非空，计数等价 _all
  orderBy: { _count: { authorId: "desc" } },  // orderBy._count 的键是标量字段名，不支持 _all
})
```

`count` 取总数、`aggregate` 取聚合字段、`groupBy` 做分组报表——统计不需要把行拉回应用层。

## 5. ✍️ 练习

**要求**：① 一次调用查出「每篇文章的作者名 + 标签数」；② 用 cursor 分页实现 feed 翻页（每页 10 条）；③ `groupBy` 统计每个作者的已发布文章数。**提示**：关系投影组合 `select`；`take: N + 1` 判断下一页。**预期效果**：数 SQL 条数验证 include 无 N+1；分页参数与 orderBy 字段一致。

## 6. 💬 面试问答（本系列 4 组之二）

> **问：offset 和 cursor 分页的本质区别？include 什么时候变成 N+1？**

**答**：offset = `OFFSET + LIMIT`，先数再跳，越深越慢；cursor = `WHERE 游标 < 上页游标 + LIMIT`，走索引定位，深度无关，代价是不能跳页且游标字段必须唯一可排序（主键最稳）。N+1 看 SQL 条数：请求对应几十条 SELECT、条数随数据量增长就是踩了（典型是循环里逐条查关联）；`findMany({ include })` 是预取不是 N+1——判断标准是「SQL 数量是否随输入规模失控」。

## 📌 小结

- 五构件：where / orderBy / 分页 / select+include / 聚合
- 深分页一律 cursor（唯一可排序字段 + orderBy 对齐）
- 默认 include 图省事，表宽关系深就切 select 投影——90% 查询值得 select
