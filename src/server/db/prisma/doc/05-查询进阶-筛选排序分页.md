# 05 — 查询进阶：筛选·排序·分页·聚合

> **本系列基于 Prisma ORM 7.x**（2026-08 编写）。

- **所属模块**：Prisma 学习大纲 · 应用层
- **预计时间**：60 min
- **面试可答**：Prisma 的查询五个核心构件是 `where`（筛选）、`orderBy`（排序）、`take/skip` 与 `cursor`（分页）、`select/include`（投影与关系预取）、`aggregate/groupBy`（聚合）。其中**cursor 分页比 offset 分页在深分页时快**（它走索引定位，不做全表扫描跳过）。

---

## 1. 一句话定位

前面所有查询都是"全表取 / 按 id 取"。这篇补齐查询的完整工具箱：怎么筛得精确、怎么排得灵活、怎么分页不卡、怎么只拿需要的字段、怎么做统计。

---

## 2. where：筛选

基础筛选 `findMany({ where: { authorId: 1 } })` 之外，重点是**操作符（Operator）**：

```ts
// 组合条件
await prisma.post.findMany({
  where: {
    AND: [
      { status: "PUBLISHED" },
      { OR: [{ title: { contains: "prisma" } }, { title: { contains: "ORM" } }] },
    ],
    NOT: { comments: { none: {} } },           // 没有任何评论的已发布文章
    author: { is: { email: { endsWith: "@example.com" } } },  // 关联表条件
  },
})
```

| 操作符 | 含义 | 例子 |
|--------|------|------|
| `equals` / `not` | 等于/不等于 | `status: { not: "ARCHIVED" }` |
| `in` / `notIn` | 集合内/外 | `id: { in: [1, 2, 3] }` |
| `contains` / `startsWith` / `endsWith` | 包含/前缀/后缀（大小写敏感随数据库） | `title: { contains: "prisma" }` |
| `lt / lte / gt / gte` | 比较 | `views: { gte: 100 }` |
| `has / hasEvery / hasSome` | 数组字段操作 | `tags: { hasSome: ["graphql"] }` |
| `is / isNot` | 关联表条件 | `author: { is: { email: ... } }` |
| `none` / `some` / `every` | 反向集合条件 | `comments: { some: { content: { contains: "赞" } } }` |
| 判空（`null` / `equals: null`） | 判断 NULL | `deletedAt: null`（等价 `{ equals: null }`） |

> 💡 顶层 `AND/OR/NOT` 让条件任意组合；大小写敏感性由数据库决定（PG 的 `contains` 默认区分大小写，要忽略用 `mode: "insensitive"`）。判空别用不存在的 `isNull`——标量判空写 `deletedAt: null` 即可；`isSet`（5.5+，**仅 SQL Server**）用于数据库级 NULL 检测。

## 3. orderBy：排序

```ts
await prisma.post.findMany({
  orderBy: [
    { status: "desc" },        // 主排序
    { createdAt: "asc" },      // 次排序
  ],
})
```

值得知道的排序进阶：

- **多字段排序** = 数组，从前到后优先级递减。
- **关系字段排序**（PG）：`orderBy: { author: { name: "asc" } }`。
- **`nulls` 控制空值位置**（PG only）：`{ createdAt: { sort: "desc", nulls: "last" } }`。

## 4. 分页：offset vs cursor

### offset 分页（简单，深分页慢）

```ts
// 第 2 页，每页 20 条：跳过前 20 条
await prisma.post.findMany({
  skip: 20,
  take: 20,
  orderBy: { createdAt: "desc" },
})
```

问题：`skip` 大了要**扫描并丢弃**越来越多行，50 万条后翻到 10000+ 页就是灾难（对应 SQL 是 `OFFSET 200000`）。

### cursor 分页（游标，深分页稳）

```ts
// 上一页最后一条的 id 作为游标，继续往"小于它"的方向找
const page = await prisma.post.findMany({
  take: 20,                                  // 一次取 20
  skip: 1,                                   // 跳过游标本身
  cursor: { id: lastPageCursorId },          // 游标：翻页剪贴板
  orderBy: { id: "desc" },                   // 必须与游标字段一致
})
```

- **优势**：SQL 是 `WHERE id < ... ORDER BY id DESC LIMIT 20`，走到哪都是从索引定位，**不会随页数变慢**。
- **代价**：参数变成"上一页的游标"，不能直接跳页（适合 feed、列表页；电商页签跳页该用别的方案）。
- **接口形态**：返回里带上一个 `nextCursor`，`?cursor=` 传给前端即可（09 篇实战会落地）。

## 5. 投影与关系预取：select vs include

### select：只取我要的字段

```ts
await prisma.user.findFirst({
  where: { email: "alice@example.com" },
  select: { id: true, email: true, name: true },   // 类型精确到这三个字段
})
```

- **性能**：少传输、少序列化；**也是防"查了一堆字段只用一个"的纪律**。
- `_count` 还能顺便取计数：`select: { _count: { select: { posts: true } } }`。

### include：把关联关系一起取出来（防 N+1）

```ts
await prisma.post.findMany({
  include: { author: true, tags: true },   // 一次查询 JOIN 完，不产生 N+1
})
```

> ⚠️ **面试重点**：01 篇说过 N+1 是"用错了"不是"ORM 的错"——**用 `include` 就是教科书式的解法之一**。`include` 底层可能拆成多条 SQL，但由 Prisma 统筹完成，应用层只剩一次调用。

### select + include 互斥规则

- `findUnique` 且是"只取某字段"时，`select` 与 `include` **不能同时用**（Prisma 会报错）。
- 关系层面的投影：`include: { author: { select: { name: true } } }`。

### 与 02 篇选型呼应

`include`（想带关系）vs `select`（只想省字段）不是二选一，而是组合：**`select: { id: true, title: true, author: { select: { name: true } } }`**——精确到能得到"只有我要的字段，且关系只取需要的字段"。

## 6. 聚合：count · aggregate · groupBy

统计无需把行取出来：

```ts
// 总数
await prisma.post.count({ where: { status: "PUBLISHED" } })

// 聚合：总浏览、平均浏览、最大、最小
await prisma.post.aggregate({
  _sum: { views: true },
  _avg: { views: true },
  _max: { views: true },
})

// 分组统计：按作者分组，各写了几篇
const byAuthor = await prisma.post.groupBy({
  by: ["authorId"],
  _count: { _all: true },
  _sum: { views: true },
  orderBy: { _count: { _all: "desc" } },
})
```

4 个聚合 API 的语义（面试高频区分）：

| API | 返回 | 典型场景 |
|-----|------|---------|
| `count()` | `number` | 列表总数 |
| `aggregate()` | 各聚合字段 | 金额总和、平均分 |
| `groupBy()` | 按字段分组 + 聚合 | 报表、看板 |
| `findFirst()` | 满足条件的**第一条**（有 orderBy 就有意义） | 最新一条 |

> ⚠️ `findUnique` 与 `findFirst` 的区别：`findUnique` 走主键/唯一约束（`@unique`）、更快；`findFirst` 是"任意 where + orderBy"的通用查询。**能用 findUnique 就别用 findFirst**（语义 + 性能）。

## 7. 练习（要求 + 提示 + 预期效果）

**要求**：① 用 include 查出"每篇文章的作者名 + 标签数"，**一次调用**；② 用 cursor 分页实现"历史文章 feed"翻页（30 条数据、每页 10 条）；③ 用 groupBy 统计"每个作者发布了多少已发布文章"。

**提示**：作者名用组合 `select` + 关系投影；分页记得 `orderBy` 与 `cursor` 字段一致；统计先 `where` 再 `groupBy`。

**预期效果**：你能看到 include 基本不会产生 N+1；cursor 翻页最后一条不带 while 死循环（用 `take: N + 1` 判断"还有没有下一页"）。

## 8. 面试问答

> **问：offset 分页和 cursor 分页本质区别？**

**答：** offset = `OFFSET + LIMIT`，先数再跳，页数越深越慢（要扫描丢弃前面的行）；cursor = `WHERE 游标字段 > 上页游标 + LIMIT`，直接走索引定位，**翻多深都一样快**，还天然免疫"翻页时数据变动导致重漏"（快照语义的问题另说）。代价是不能任意跳页、需要上游传游标。

> **追问：cursor 分页能用什么字段？**

**答：** 必须用**唯一可排序**的字段（主键最稳），且 orderBy 和 cursor 必须用同一个字段。用非唯一字段（如围观数相同）会翻错页——这也是面试官常埋的坑，答案是"取一个全局唯一键、或联合游标（id + 排序值）"。

> **问：include 什么时候会变成 N+1？怎么知道有没有踩中？**

**答：** 看 SQL 数量。在日志里数 SELECT 语句数（10 篇有 Query Insights 实操）；"循环里一行行查"是最典型的 N+1 来源，而 `findMany({ include })` 是 Prisma 帮你做预取，别把两者混为一谈。判断标准：**跟你写的调用次数比，SQL 数量是否失控**。

> **追问：include 和 select 到底怎么选？**

**答：** 默认 `include: true` 会把整行全字段 + 整关系全字段取回；只要性能在可接受范围就用 include（简单）。一旦表宽、关系深、字段多无用，切到 `select` 做投影——实际项目里 90% 的查询都可以用 select 只取需要的字段。

## 9. 三角对比

| 维度 | **Prisma**（声明式） | Drizzle（SQL 式） | raw SQL |
|------|---------------------|-------------------|---------|
| where | 操作符对象（可组合） | `select().where(and(...))` | WHERE 子句 |
| 分页 | cursor/offset | limit/offset | LIMIT/OFFSET |
| 预取 | include（自动） | leftJoin 手写 | JOIN 手写 |
| 聚合 | 4 个内置 API | sql`count()` 等 | GROUP BY 手写 |
| 类型反馈 | 自动化、对象式 | 接近 SQL 但也是 TS | none |
