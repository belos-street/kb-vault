# 07 — 事务与错误处理

> **本系列基于 Prisma ORM 7.x**（2026-08 编写）。

- **所属模块**：Prisma 学习大纲 · 应用层
- **预计时间**：45 min
- **面试可答**：Prisma 支持**交互式事务**（`$transaction(async (tx) => ...)`，任意逻辑包进事务）和**批量事务**（回调数组，逐条执行、失败回滚）；错误用**结构化错误码**（P2xxx）区分唯一冲突、记录不存在、外键失败等，`P2002`/`P2025` 是最常被 catch 的两个。

---

## 1. 一句话定位

"多步写入，要么全成要么全败"是数据库一致性的底线。这篇讲 Prisma 怎么开事务、怎么 catch 错误不裸奔。

---

## 2. 为什么要事务

转账就是教科书场景：

```ts
// ❌ 分开写：第一步成功、第二步失败 = 钱凭空消失/多给一份
await prisma.account.update({ where: { id: from }, data: { balance: { decrement: 100 } } })
await prisma.account.update({ where: { id: to }, data: { balance: { increment: 100 } } })
```

要么两步都成功，要么都回滚——**原子性**。这正是数据库事务 ACID 的 A。Prisma 提供两种写法。

---

## 3. 交互式事务：能放任意逻辑

```ts
await prisma.$transaction(async (tx) => {
  // 注意：事务回调里必须用 tx，不能用外层 prisma
  const a = await tx.account.update({
    where: { id: from },
    data: { balance: { decrement: 100 } },
  })
  if (a.balance < 0) throw new Error("余额不足")   // 抛错 → 整个事务回滚

  await tx.account.update({
    where: { id: to },
    data: { balance: { increment: 100 } },
  })
})
```

要点：

- **用 `tx`（Transaction Client）**，不是外层 `prisma`——所有写操作必须挂到 tx 上才会参与同一个事务。
- `throw` 任意错误 → **整个事务回滚**，且错误会冒泡给调用方。
- 适合**中间带判断/计算/条件分支**的复杂流程（转账判余额、下单判库存、幂等检查）。

### 嵌套事务（Prisma 7.5+）

事务里再开事务，内层会落入**savepoint** 而非真嵌套：

```ts
await prisma.$transaction(async (tx) => {
  await tx.user.create({ data: { email: "a@x.com" } })
  try {
    await tx.$transaction(async (inner) => {
      await inner.post.create({ data: { title: "x", authorId: 999 } })  // 外键失败
    })
  } catch {
    // 内层回滚到 savepoint，外层还能继续；否则整体回滚
  }
})
```

> 💡 面试点：Prisma 7.5 之前的嵌套事务是整体回滚，7.5+ 加入 savepoint 支持（官方 changelog 2026-03）。**知道这个演进，就能答"嵌套事务怎么局部回滚"。**

---

## 4. 批量事务：简单有纪律

```ts
await prisma.$transaction([
  prisma.user.create({ data: { email: "a@x.com" } }),
  prisma.user.create({ data: { email: "b@x.com" } }),
])
```

- 传入**一组 Prisma 操作**，按序执行，任何一个抛错 → 全部回滚。
- 不能带业务判断（纯执行；要判断就用交互式）。

---

## 5. 错误处理：错误码体系

Prisma 抛的异常是 `PrismaClientKnownRequestError`，带 `code`（如 `P2002`）。按 code 分支处理，而不是匹配 message：

```ts
import { Prisma } from "./generated/prisma/client"

try {
  await prisma.user.create({ data: { email: "dup@x.com" } })
} catch (e) {
  if (e instanceof Prisma.PrismaClientKnownRequestError) {
    if (e.code === "P2002") {
      // 唯一约束冲突 —— 商业上就是"邮箱已被注册"
      return { code: 409, msg: "email already taken" }
    }
    if (e.code === "P2025") {
      // 记录不存在（update/delete 找不到 where 匹配）
      return { code: 404, msg: "not found" }
    }
    if (e.code === "P2003") {
      // 外键约束失败
      return { code: 400, msg: "foreign key violation" }
    }
  }
  // 兜底：未知错误，打印日志 + 500
  console.error(e)
  return { code: 500, msg: "internal error" }
}
```

高频错误码速查：

| code | 含义 | 业务映射 |
|------|------|---------|
| `P2002` | **唯一约束冲突**（email/slug 重复） | 409 Conflict |
| `P2025` | **记录不存在**（where 没匹配到） | 404 Not Found |
| `P2003` | **外键约束失败**（引用的行不存在/被占） | 400 Bad Request |
| `P2014` | 关系violation（1-1 已占用） | 409 |
| `P2039` | 未映射的 driver 错误透传为用户可捕获错误（[2026-04 起](https://www.prisma.io/changelog/2026-04-27)，未列入公开 Error Reference） | 视驱动而定 |

> ⚠️ **指针对话的坑**：`update/delete` 找不到行默认抛 `P2025`；但 `updateMany/deleteMany` 找不到行**不抛错**（只是 `count: 0`）。判断"批量执行到底影响了没"要用返回值，不能依赖异常。

## 6. 与事务理论的衔接（数据库课程 06）

Prisma 的 `$transaction` 默认隔离级别遵循数据库默认（PG 是 `READ COMMITTED`），必要时可指定：

```ts
await prisma.$transaction(
  async (tx) => { ... },
  { isolationLevel: Prisma.TransactionIsolationLevel.Serializable }
)
```

> 💡 面试点：事务隔离级别（脏读/不可重复读/幻读）的决定权在数据库层，Prisma 只是透传 `isolationLevel`。要查"并发下的丢失更新"这类问题，先温习数据库课程 06 篇的 MVCC 心智模型，再回来看 Prisma 怎么写。

## 7. 练习（要求 + 提示 + 预期效果）

**要求**：① 用交互式事务实现"领取每周签到奖励"（用户在 `User.weeklyStreak` 上加 1，同时往 `StreakLog` 插一条，`StreakLog` 里 `userId + week` 是唯一键）；② 让第二次调用抛 `P2002`，观察外层 catch 拿到 code；③ 验证失败时 `weeklyStreak` 没有变。

**提示**：`StreakLog` 建 `@@unique([userId, week])`；循环调用两次同一个用户验证唯一冲突；用 `count()` 或直接查用户验证回滚。

**预期效果**：你能答出"交互式 vs 批量事务的区别、`P2002`/`P2025` 各自对应的业务状态码"，并在代码里用结构化 catch 而不是 `if (e.message.includes(...))`。

## 8. 面试问答

> **问：什么时候用 `$transaction` 数组，什么时候用回调？**

**答：** 数组适合"固定的一组操作、不依赖中间结果"（批量插入、批量更新）——简单、不易出错；回调适合"需要中间判断/计算/分支"的流程（转账验余额、下单验库存、唯一键预检）——因为事务内能看到中间状态。面试加分：回调里操作必须用 `tx` 而不是外层 `prisma`，否则不参与事务。

> **追问：那嵌套事务呢？**

**答：** 内层 `$transaction` 会变成 **savepoint**（Prisma 7.5+），可以局部回滚后再继续外层；7.5 之前会整体回滚。用途是"大事务里某一段是可恢复尝试"（比如 per-item 的幂等 upsert）。

> **问：为什么不 catch `e.message` 而用 code？**

**答：** 错误码是**稳定契约**，message 是给人看的文案（会随版本变化/被本地化/有参数）。`P2002` 永远代表唯一冲突，语义 20 年不变；用 `instanceof Prisma.PrismaClientKnownRequestError` 再 switch code，才能写出不随版本坏掉的错误映射。

> **追问：`update` 抛 P2025 但 `updateMany` 不抛，这个坑怎么避免？**

**答：** 先理解语义差别：单对象操作（update/delete/findUnique）语义上"必须命中"所以抛错；批量操作（updateMany/deleteMany）语义是"尽力影响 N 行"，不命中就 `count: 0`。**判断业务上"必须存在"用单对象 + 捕获 P2025；判断"影响了多少"用批量 + 读返回的 count。**

## 9. 三角对比

| 维度 | **Prisma** | Knex/kysely（query builder） | raw SQL |
|------|-----------|------------------------------|---------|
| 事务 API | `$transaction`（数组/回调/savepoint） | `transaction()` builder | `BEGIN/COMMIT/ROLLBACK` 手写 |
| 错误结构 | 错误码 + 参数 | 靠 db driver 原始错误 | psql 原生错误，自己解析 |
| 隔离级别 | `isolationLevel` 透传 | 部分支持 | 完全手写 |
| 心智负担 | 低（框架兜底回滚） | 中 | 高（要自己 commit/rollback） |
