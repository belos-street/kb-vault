# 10 — 调试·性能·生产部署

> **本系列基于 Prisma ORM 7.x**（2026-08 编写）。

- **所属模块**：Prisma 学习大纲 · 工程层
- **预计时间**：60 min
- **面试可答**：从能跑到能上生产，Prisma 侧要做四件事：**① 看 SQL**（日志/Query Insights 找慢查询、数 SQL 条数查 N+1）；**② 修查询**（select 精修、include 预取、索引对齐）；**③ 管连接池**（v7 用 driver adapter，默认行为与 v6 不同）；**④ 生产迁移只走 `migrate deploy`**。

---

## 1. 一句话定位

上一篇的 API 能跑了，但"能跑"和"能上生产"中间隔着一整层：查询是不是真的高效、连接会不会爆、迁移是否可复现。这篇做一次"上线前的体检"。

---

## 2. 第一步：先看到 SQL

不看到 SQL，一切性能讨论都是盲猜。三种方式：

### 2.1 Client 日志（开发期最快）

```ts
const adapter = new PrismaPg({ connectionString: process.env.DATABASE_URL! })
const prisma = new PrismaClient({
  adapter,
  log: ["query", "info", "warn", "error"],   // 打开后能看到每条 SQL
})
```

输出示例：

```
prisma:query SELECT "public"."User"."id", "public"."User"."email" FROM "public"."User" WHERE "public"."User"."id" = $1 LIMIT 1
```

**数 SQL 条数**是查 N+1 的第一招：一次"列表 + 关联"请求，如果打印出几十条 SELECT，多半踩了循环查询。

### 2.2 Query Insights（Prisma 平台能力，7.x 可经 Studio 看）

Prisma Studio 已集成 Query Insights（[2026-06 changelog](https://www.prisma.io/changelog/2026-06-05)：Studio 新增 Queries 视图查看慢查询）。接入 Prisma Postgres 后可在 Studio 里直接看 TOP 慢 SQL，用于生产观测（Query Insights 是 Prisma Postgres 内置能力，替代了 Optimize）。

### 2.3 数据库侧 EXPLAIN（终极手段）

拿 Client 日志里那条 SQL，到 psql 里 EXPLAIN 看执行计划（对齐 [database 课程 05 章](file:///Users/apple/code/personal/kb-vault/src/computer-science/database/doc/05-indexes-and-explain.md)）：

```sql
EXPLAIN ANALYZE SELECT ... WHERE "userId" = $1 ORDER BY "id" DESC LIMIT 10;
-- 看: Seq Scan 还是 Index Scan, 有没有走错索引
```

## 3. 三个高频性能问题与修法

### 3.1 N+1

**症状**：日志里 SQL 条数 = `N + 1`。**根因**：循环里逐条查询关联（或 schema 该用 include 没用）。

**修法**：用 `include`/`select` 里的关系预取（05 篇）；必要时拆成连接表一次取回：

```ts
// ❌ 循环里查：N+1
const users = await prisma.user.findMany()
for (const u of users) { await prisma.post.count({ where: { authorId: u.id } }) }

// ✅ 一次预取
const users = await prisma.user.findMany({ select: { id: true, _count: { select: { posts: true } } } })
```

### 3.2 深分页慢

`skip` 越大越慢。深分页改用 cursor（05 篇，靠索引定位）。翻页接口还能额外用 `take: limit+1` 判断是否有下一页。

### 3.3 查询不命中索引 / 取回过多列

**修法**：五步走——① 看 SQL（时序型先问"慢在哪一步"）；② EXPLAIN 看走没走索引；③ 对查询列建 `@@index`（如 `@@index([authorId, createdAt])` 匹配"某人最近文章"）；④ `select` 只取业务要的列（少序列化、少传输）；⑤ 重复验证。

> ⚠️ 建索引是**对查询的响应**，不是无脑堆。`@@index([a, b, c])` 复合索引的最左前缀原则、以及覆盖索引的概念，都归数据库课程 05 篇；Prisma 侧你只需"在 schema 里声明、migrate 落地"。

## 4. 连接池：Prisma 7 的新重点

v7 的 client 是纯 TS + driver adapter，**连接池归底层驱动管**（pg 驱动），两个现实差异要在生产前处理：

| 项 | v6（内置池） | v7（pg 驱动） |
|----|-------------|--------------|
| 连接超时 | 默认 5s | **默认 0（永不超时）→ 易卡死** |
| 池上限 | Prisma 默认公式 | 看 pg 驱动默认（通常 10） |
| 配置位置 | PrismaClient 内 | adapter/pool 配或 env |

```ts
// 显式配池，别吃默认
import { Pool } from "pg"

const pool = new Pool({ connectionString: DATABASE_URL, max: 20, connectionTimeoutMillis: 5000 })
const adapter = new PrismaPg(pool)
const prisma = new PrismaClient({ adapter })
```

> 💡 面试可背的一句话：**v7 把"连接管理"交给数据库驱动，池参数不再由 Prisma 兜底**——这正是 01 篇那句"v7 生产环境最常见的坑"的落点。

## 5. 生产迁移与部署纪律

### 5.1 迁移只走 deploy

```bash
# 生产环境（CI/CD 里）—— 绝不跑 migrate dev/reset
bunx prisma migrate deploy
bunx prisma db seed --skip-generated-generate  # 视需要
```

- `deploy` 只把未应用的迁移文件按顺序执行，**不做 schema diff、不重置**。
- 多实例部署时，迁移应在**发布流程的数据库步骤**统一执行一次（避免每个 pod 各跑一遍 `migrate deploy` 的竞态）。

### 5.2 连接串与环境

- `DATABASE_URL` 走环境变量注入（`.env` 不入库，`prisma.config.ts` 里 `env()` 读取）。
- 生产连接串常走连接池代理（如 PgBouncer / Prisma Accelerate），注意 session vs transaction 模式与驱动的兼容。

### 5.3 读副本 / 缓存（引子，随用随查）

- **读副本**：Prisma 7 支持 read replicas（[7.1+ 引入](https://www.prisma.io/changelog/2025-12-03)，把读流量打到副本），写走主库。适合"读多写少"，[配置方式见官方 read-replicas 文档](https://www.prisma.io/docs/orm/prisma-client/read-replicas)。
- **客户端缓存**：7.4+ 引入 Prisma Client 查询缓存层（`queryPlanCache` 等），弱缓存不进业务代码。
- **应用层缓存 / 加速**：Prisma Accelerate 是托管缓存、把查询提到边缘缓存，属 11 篇速查范围。

## 6. 练习（要求 + 提示 + 预期效果）

**要求**：给 09 的博客 API 做体检：① 打开 query 日志，造出"文章列表一次性查 100 篇 + tags"并数 SQL 条数，把 include 换成 select 关系投影再数一次；② 用 EXPLAIN 验证"作者某时间段的文章"查询是否命中 `@@index([authorId, createdAt])`；③ 给 Hono 起动日志 + 生产路径写一份 `migrate deploy` 的 CI 步。

**提示**：日志级别在 PrismaClient 构造时配；EXPLAIN 用 psql；CI 步骤就写个 scripts（`deploy:db: migrate deploy`）。

**预期效果**：你能说出"我后端这句话会生成几条 SQL、走了什么索引"，并把迁移收敛为 CI 里 `migrate deploy` 一步。

## 7. 面试问答

> **问：N+1 从 SQL 上怎么一眼看出来？**

**答：** 看请求对应 SQL 条数。理想是一两条（JOIN/预取），N+1 时是 `N + 1` 条：先取集合，再对每条取关联。实际开发里开 query 日志数一下就知道；面试聊到"你会怎么排查接口慢"时，把"打开日志 → 数 SQL → 定位循环查询 → 改 include/select"这条链路讲出来就过关。

> **追问：include 会拆多条 SQL 也算性能问题吗？**

**答：** 分场景。Prisma 的预取可能在底层发多条（尤其关系复杂时），但只要**条数不随数据量增长**，复杂度就是 O(1)，可接受；真正的坑是"条数 ~ N"的循环查询。所以面试答法：关注"是否依赖输入规模胀大"，而不是"绝对条数"。

> **问：Prisma 7 连接池为什么跟 v6 不一样？**

**答：** v7 客户端不再内置 Rust 引擎的连接管理，改用 driver adapter 服务化，池由底层驱动提供：pg 的默认连接超时 0（易挂）、池容量约定不同。生产上必须显式配 `max`、`connectionTimeoutMillis`，否则遇到高并发/慢查询时表现为"请求挂住不超时"。

> **追问：生产迁移为什么只允许 migrate deploy？**

**答：** `dev` 会做 schema diff、可能 `reset` 数据（v6 还会自动 `generate`/seed，v7 已移除这些隐式行为）——这些是开发工作流，放生产=灾难（清库、丢数据、版本错位）。`deploy` 只执行迁移文件，幂等可回放，且把"库没跟上"暴露为部署失败而不是运行时崩溃。

## 8. 三角对比

| 维度 | **Prisma 7 生产实践** | v6（内置池） | raw SQL（完全手动） |
|------|----------------------|-------------|---------------------|
| 看 SQL | 日志/Query Insights | 同 | 直接可见 |
| 连接池 | 交给 pg 驱动配置 | Prisma 兜底 | pg 池自己管 |
| 查 N+1 | 数 SQL + include 预取 | 同 | 手写 JOIN |
