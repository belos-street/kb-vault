# 03 — 关系建模：1对1 与 1对多

> **本系列基于 Prisma ORM 7.x**（2026-08 编写）。

- **所属模块**：Prisma 学习大纲 · 应用层
- **预计时间**：60 min
- **面试可答**：Prisma 的关系用「关系字段（relation field）」表达——外键那一端用 `@relation(fields, references)` 显式声明，另一端只需 `User posts Post[]` 反查；`onDelete` 决定删除父记录时子记录怎么办。建表时外键由 Prisma 自动生成，嵌套 `create` 可一条调用写入多张表。

---

## 1. 一句话定位

上一篇的 Post 和 Comment 还是"两张孤立表"。这一篇给它们**装上外键**，并掌握"写一次数据拆成多张表"和"删一个用户连带处理他的文章"两种最核心的联动。

---

## 2. 关系的心智模型：两端声明

关系总是**成对出现**：一端是外键字段（真实列），另一端是虚拟的「关系字段」（不落库，纯查询用）。

以「用户 → 文章」1-N 为例：

```prisma
model User {
  id    Int    @id @default(autoincrement())
  email String @unique
  posts Post[]          // 关系字段：查询用 prisma.user.findMany({ include: { posts: true } })
}

model Post {
  id       Int    @id @default(autoincrement())
  title    String
  author   User   @relation(fields: [authorId], references: [id])  // 外键声明端
  authorId Int    // 真实的外键列
}
```

拆解：

| 元素 | 位置 | 作用 |
|------|------|------|
| `author User @relation(fields: [authorId], references: [id])` | Post 端（有外键的一方） | 声明：`authorId` 引用 `User.id` |
| `authorId Int` | Post 端 | 真实列，`_id` 后缀命名 |
| `posts Post[]` | User 端 | 纯查询用的反向关系，不落库 |

> 💡 **命名惯例**：`authorId` 这种「目标模型小写 + Id」不是强制，但强烈建议——`_id` 后缀让所有关系一目了然。字段叫 `ownerId` 也行，`@relation` 里的 `fields` 写好即可。

## 3. 三种基础关系的 Schema 写法

### 1-N（上面已演示）—— 最常见

```prisma
model User {
  posts Post[]
}
model Post {
  author   User @relation(fields: [authorId], references: [id])
  authorId Int
}
```

### 1-N 的可空外键（草稿不填作者）

```prisma
model Post {
  author   User? @relation(fields: [authorId], references: [id])
  authorId Int?   // 可空外键，配合 User? 
}
```

### 1-1

一篇文章对应一份"支付/详情"类的独享扩展 1:1：

```prisma
model Profile {
  id     Int  @id @default(autoincrement())
  user   User @relation(fields: [userId], references: [id])
  userId Int  @unique   // 关键：@unique 把"多"掐成"一"
}

model User {
  profile Profile?   // 反向端用单数、可空
}
```

> ⚠️ **1-1 的铁律**：外键字段必须加 `@unique`。没有它，数据库层面仍然是 1-N，Prisma 也会报错要求你加。

## 4. 级联删除：`onDelete`

删除用户时，他的文章怎么办？需要显式定策略，默认是 **`Restrict`（有子记录就禁止删）**：

```prisma
model Post {
  author   User @relation(fields: [authorId], references: [id], onDelete: Cascade)
  authorId Int
}
```

| 策略 | 行为 | 适用 |
|------|------|------|
| `Cascade` | 删父同时删子 | 明细/从属数据（订单→订单项）、本地草稿 |
| `Restrict`（默认） | 有子记录时拒绝删除父 | 用户→已发布文章，防止误删留孤儿 |
| `SetNull` | 删父后外键置 NULL | 软引用（"最后由谁编辑"可容忍丢失） |
| `NoAction` | 交给数据库约束（PG 默认行为，与 Restrict 略异） | 极少用 |

> ⚠️ **SQLite 注意**：SQLite 的表结构变更能力受限（多数约束无法 ALTER），`migrate dev` 若提示重置数据库属于正常现象（本系列后续默认 PostgreSQL，避坑）。

## 5. 嵌套写：一条调用写多张表

Prisma 的杀手锏之一——嵌套 `create` 把多表写入放进同一原子调用（底层是事务）：

```ts
// 创建一个用户，同时给他三篇文章
const user = await prisma.user.create({
  data: {
    email: "bob@example.com",
    posts: {
      create: [
        { title: "Prisma 入门" },
        { title: "关系建模" },
        { title: "迁移实战" },
      ],
    },
  },
})
```

同理还能嵌套 `update`、`upsert`、`delete`（删除用户连带 `posts: { deleteMany: {} }`）。**什么时候用嵌套写、什么时候分开写**，标准是：是否要"要么全成功要么全失败"？嵌套写底层就是一个事务，需要时用，散装时分开写（性能更可控）。

## 6. 练习（要求 + 提示 + 预期效果）

**要求**：① 建 `User / Post / Profile`（用本文三张写法，Post 加 `onDelete: Cascade`）；② 用 `prisma.user.create` 嵌套创建 1 个用户 + 2 篇文章 + 1 个 Profile；③ 删除该用户，验证文章与 Profile 一并被删（查 `Post.count()`）。

**提示**：先确认 `migrate dev` 生成的 SQL 里有 `ON DELETE CASCADE`；删除用 `prisma.user.delete({ where: { id } })`；验证删除后 count 为 0。

**预期效果**：三条 SQL 级别的行为（外键、级联、联合事务）你都亲眼看到——嵌套创建的多个 `INSERT` 被包在一个事务里（可看日志见 10 篇）。

## 7. 面试问答

> **问：Prisma 里"关系"和数据库外键是什么关系？**

**答：** 一一对应。`@relation(fields: [authorId], references: [id])` 声明的关系，`migrate` 时会真的在数据库建 FOREIGN KEY 约束——也就是说**约束是真的，不是为了 ORM 舒服的装饰**。反过来 `db pull` 反向同步时，已有外键也能被识别为关系。这是"Schema 单一数据源"在关系上的体现。

> **追问：那 `User.posts` 这种虚拟字段呢？**

**答：** 不落库，纯粹是 Prisma Client 的查询语法糖（`include`/嵌套写会用）。字段声明不写它也能建表（但没法用 `include` 查询），所以规范做法是显式写上两端，让 schema 表达完整的关系图。

> **问：`onDelete` 的 Restrict 和 NoAction 在 PG 里的区别？**

**答：** 都是"不让删"，但时机不同：`Restrict` 是**立刻**拒绝（PG 在约束检查立即失败）；`NoAction` 是"事务提交时再检查"，给同一事务内先删子后删父留了余地。绝大多数场景用 `Restrict` 或 `Cascade`，纠结 NoAction 属于过度设计。

> **追问：嵌套 create 底层是事务，那和手写 `$transaction` 比呢？**

**答：** 嵌套写是"自动帮你包事务"的语法糖，适用"写入路径固定"（建用户必然带文章）；`$transaction` 则适合多表间需要中间逻辑（判断、计算、条件分支）的复杂写入。两者在 07 篇都会展开。

## 8. 三角对比

| 维度 | **Prisma 关系** | TypeORM 关系 | raw SQL FK |
|------|----------------|-------------|-----------|
| 声明 | DSL 两端声明 | 装饰器关系的种类 | 建表语句手写 |
| 级联 | `onDelete` 声明式 | JoinColumn 等项 | ON DELETE 子句 |
| 嵌套写 | create 内嵌自动事务 | SaveOptions | 无，手写多语句事务 |
| 查询 | include（05 篇） | relations | JOIN 手写 |
