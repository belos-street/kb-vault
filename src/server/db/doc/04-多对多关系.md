# 04 — 多对多关系

> **本系列基于 Prisma ORM 7.x**（2026-08 编写）。

- **所属模块**：Prisma 学习大纲 · 应用层
- **预计时间**：45 min
- **面试可答**：Prisma 的 N-N 有两种建模：① **隐式关联表**（只有两端 `Post[]`/`Post[]`，Prisma 自动建 `_CategoryToPost` 中间表，省事但只能存两列）；② **显式关联表**（自己建第三个 model，字段自由，能挂 createdAt/role 等额外信息）。选哪个看"中间表要不要带属性"。

---

## 1. 一句话定位

上一篇的关系是"一个对多个"，这篇处理"多个对多个"——比如**一篇文章打多个标签，一个标签下有多篇文章**，以及"用户关注用户"这种自引用 N-N。

---

## 2. 隐式 N-N：最省事的写法

```prisma
model Post {
  id       Int    @id @default(autoincrement())
  title    String
  tags     Tag[]
}

model Tag {
  id    Int    @id @default(autoincrement())
  name  String @unique
  posts Post[]
}
```

Prisma 会自动建一张不可见的中间表（PG 里叫 `_PostToTag`，表名规则 `_<模型A>To<模型B>`、**按字母序**排序——Post 在 Tag 前；表内两列 `A`、`B`，各带外键 + 联合唯一），[命名规则见官方文档](https://www.prisma.io/docs/concepts/components/prisma-schema/relations/many-to-many-relations)。你看不到、也不能自定义它，但 `create`/`include` 的嵌套语法照常可用：

```ts
// 建文章时直接挂标签
await prisma.post.create({
  data: {
    title: "Prisma 进阶",
    tags: { connect: [{ id: 1 }, { id: 2 }] },   // 关联已有标签
  },
})

// 查文章时带出标签
const post = await prisma.post.findFirst({
  where: { id: 1 },
  include: { tags: true },
})
```

**适用**：纯粹的 "A ↔ B" 连接，中间没有附加信息。**代价**：中间表带不了 `createdAt`、`role` 这类属性。

> ⚠️ 中间表名是自动的（`_PostToTag`，按字母序 Post 在 Tag 前）。想自定义表名就必须走显式 N-N。

## 3. 显式 N-N：带属性的连接表

当中间要存谁知道什么时候打的标签、或标签在文章里的权重时，把中间表"升格"为显式模型：

```prisma
model Post {
  id          Int            @id @default(autoincrement())
  title       String
  tags        PostTag[]      // 注意：反向端是 PostTag[]，不是 Tag[]
}

model Tag {
  id    Int       @id @default(autoincrement())
  name  String    @unique
  posts PostTag[]
}

model PostTag {
  post   Post @relation(fields: [postId], references: [id])
  tag    Tag  @relation(fields: [tagId], references: [id])
  postId Int
  tagId  Int
  addedAt DateTime @default(now())   // 附加信息：谁在何时打的标
  @@id([postId, tagId])              // 联合主键，天然去重
}
```

读写：

```ts
// 写入（带附加信息）
await prisma.postTag.create({
  data: { postId: 1, tagId: 2, addedAt: new Date() },
})

// 查询：文章 -> 标签及附加信息
const post = await prisma.post.findUnique({
  where: { id: 1 },
  include: { tags: { include: { tag: true } } },  // 穿过中间表
})
```

**何时升级成显式**：只要中间表需要第三列以上（`addedAt`、`role`、`weight`、`sortOrder`…）就升级。至少在动手写代码前先问："这个关系本身是不是一个业务实体？"是，就显式。

## 4. 自引用 N-N：关注/好友

"用户关注用户"是 N-N 指向同一张表，必须用 `@relation` 给两端**起不同名字**区分：

```prisma
model User {
  id        Int    @id @default(autoincrement())
  following Follow[] @relation("Follows")   // 我关注的人
  followers Follow[] @relation("Follows")   // 关注我的人
}

model Follow {
  followerId Int
  followingId Int
  createdAt  DateTime @default(now())

  follower  User @relation("Follows", fields: [followerId], references: [id])
  following User @relation("Follows", fields: [followingId], references: [id])

  @@id([followerId, followingId])
  @@index([followingId])   // 查"谁关注了 X"要走这边的索引
}
```

读取：

```ts
// 我关注了谁（id=1 的用户关注的列表）
await prisma.user.findUnique({
  where: { id: 1 },
  include: { following: { include: { following: true } } },
})
// -> [{ followingId: 3, following: { id: 3, name: 'Alice' } }]
```

> 💡 `@relation("Follows")` 的字符串是**关系的名字**（可以任意起），作用是让 Prisma 区分同一对模型之间的多组关系——同名必选，不同名会报错 "Please provide a name for this relation"。

## 5. 隐式 vs 显式：怎么选

| 维度 | 隐式 N-N | 显式 N-N（连接表模型） |
|------|---------|----------------------|
| 声明成本 | 低（两端各一个数组字段） | 高（多一个模型） |
| 中间表 | 自动生成，不能碰 | 自己建，随便加字段 |
| 附加信息（时间/排序） | ❌ 存不了 | ✅ |
| 查询写法 | 两层 include | 三层（过中间表） |
| 适用 | 纯打标、纯收藏 | 带业务属性的连接 |

**决策口诀**：能不用第三列就隐式（少一个模型少一份心智负担）；一但需要"关系本身有属性"，立刻转显式。

## 6. 练习（要求 + 提示 + 预期效果）

**要求**：实现"商品收藏"：`Product` 与 `User` 之间设 `Favorite` 连接表（带 `createdAt`；默认按收藏时间倒序）。① 用显式 N-N 写 schema；② 写入 1 用户 2 商品并收藏；③ 查"某用户收藏的商品（含收藏时间）"。

**提示**：`@@id([userId, productId])` 联合主键；查询用 `include: { favorites: { include: { product: true } } }`。

**预期效果**：联合主键 + 附加属性都落在迁移 SQL 里；你能说清"什么时候该把关系升级成显式表"。

## 7. 面试问答

> **问：隐式 N-N 的中间表在数据库里长什么样？我能改它吗？**

**答：** 一张只有 `A`/`B` 两列、双外键 + 联合唯一约束的表，表名是 `_<模型A>To<模型B>`（按字母序，如 Post↔Tag 就是 `_PostToTag`）。可以读（`prisma._PostToTag.findMany()` 这类元表 API），但**字段是固定的，加不了第三列**——要加就得显式重写。

> **追问：既然加不了列，为什么还推荐它？**

**答：** 因为"纯连接、无属性的 N-N"是真实且高频的场景（打标、收藏、分组）。隐式用最小的模型噪音覆盖它；显式会为每个纯连接多造一个模型，代码量不成比例。**面试标准答案：按需升级**。

> **问：自引用 N-N 为什么必须写关系名？**

**答：** 因为 `User` 与 `User` 之间有两条反向关系（following/followers），Prisma 无法靠类型区分，必须用 `@relation("名字")` 显式给两端命名。同理，**同一对模型间出现两组关系时**（如"文章→作者"与"文章→审核人"），也必须给关系起名。

> **追问：那 @relation 名字是怎么强制配对的？**

**答：** 同名即配对——follower/following 各自声明里的 `"Follows"` 相同，Prisma 就知道它们属于同一组关系；`fields`/`references` 指明哪端是外键。名字本身只是标签，一致性才是约束。

## 8. 三角对比

| 维度 | **Prisma** | TypeORM | raw SQL |
|------|-----------|---------|---------|
| 隐式 N-N | 自动中间表 | @ManyToMany + JoinTable | 手写连接表 |
| 显式 N-N | 普通模型 + 双 @relation | @OneToMany × 2 | 连接表 + 主外键 |
| 附加属性 | 显式模型直接加 | JoinTable 带额外列 | DDL 里加 |
| 自引用 | @relation("name") | 同一实体双向 | 自连接 SQL |
