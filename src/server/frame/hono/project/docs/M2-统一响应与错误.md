# M2 统一响应与错误

## 这一步做什么

全站唯一的响应形状：成功 `{ code:'OK', data }`、失败 `{ code, message, details? }`；错误按语义分层；校验失败自动转信封。

## 错误分层（lib/errors.ts）

```ts
export type ApiErrorCode =
  | 'VALIDATION_ERROR' | 'UNAUTHORIZED' | 'FORBIDDEN' | 'NOT_FOUND'
  | 'CONFLICT' | 'UNPROCESSABLE' | 'RATE_LIMITED' | 'INTERNAL'

export class ApiError extends HTTPException {
  readonly code: ApiErrorCode
  constructor(code: ApiErrorCode, message: string, details?: unknown) {
    super(statusByCode[code], { message })   // status 由 code 单向推导
  }
}
```

设计点：**code 是因，status 是果**。业务代码只说语义（`apiError.conflict()`），HTTP 状态码由映射表推导——避免「该给 409 还是 422」在每个 handler 里现场纠结一遍。

## ok() 的重载保类型

```ts
export function ok<T>(c: Context, data: T): TypedResponse<{ code: 'OK'; data: T }, 200, 'json'>
export function ok<T, S extends ContentfulStatusCode>(c: Context, data: T, status: S): TypedResponse<...>
```

不加重载的话，`return ok(c, dto, 201)` 的响应类型会退化，OpenAPI 的 `responses` 声明与实际返回对不上——三同源从这里开始松。细节：**失败侧 details 不进 OpenAPI 契约**（[schemas/common.ts](../src/schemas/common.ts) 的 failEnvelope 只有 code/message），调试信息不等于接口承诺。

## 接线

- `app.onError`：ApiError → 信封；HTTPException → codeByStatus 兜底；其余 → 500（日志见 M3）
- `app.notFound` → NOT_FOUND 信封
- `createOpenAPI()` 工厂统一注入 `defaultHook`——zValidator 校验失败自动转 `VALIDATION_ERROR`，业务 handler 里永远不写校验分支

## 验证

未知名路由 → `{ code:'NOT_FOUND' }`；缺字段 POST → 400 `VALIDATION_ERROR`（后续 M4/M5 测试覆盖完整错误路径）。

## 面试可答

> **问：错误处理为什么要「code 单向推导 status」而不是反过来？**
> status 只有十几个、语义粗糙（409 和 422 的边界全靠人背），code 是业务自定义的、可以精确到场景。以 code 为源，新增业务错误码不用动状态映射，反过来则每加一个 status 都要重排业务分支。
