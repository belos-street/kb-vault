# M2 统一响应与错误

> 所属：[project](../) 实现教学 ｜ 前置：[10-实战B](../../doc/10-实战B-企业级REST-API.md) §4、[06-错误处理](../../doc/06-错误处理.md) ｜ 对应代码：`src/lib/{response,errors,validator}.ts`、`src/index.ts`

**一句话定位**：全站响应信封唯一——成功 `{ code: 'OK', data }`、失败 `{ code, message, details? }`，错误只从 `onError` 一个出口出去。

**面试可答**：业务错误码（`CONFLICT`）与 HTTP 状态码（409）是两层语义——前者给前端程序判断，后者给 HTTP 语义；实现上用「业务异常类继承 `HTTPException`」让 status 自动推导、code 搭车传递，`onError` 单点兜底。

---

## 1. 信封：`lib/response.ts`

```ts
export function ok<T>(c: Context, data: T): TypedResponse<{ code: 'OK'; data: T }, 200, 'json'>
export function ok<T, S extends ContentfulStatusCode>(
  c: Context,
  data: T,
  status: S,
): TypedResponse<{ code: 'OK'; data: T }, S, 'json'>
export function ok<T, S extends ContentfulStatusCode>(c: Context, data: T, status?: S) {
  return c.json({ code: 'OK' as const, data }, (status ?? 200) as S)
}

export const fail = (
  c: Context,
  code: string,
  message: string,
  status: ContentfulStatusCode,
  details?: unknown,
) => c.json(details === undefined ? { code, message } : { code, message, details }, status)
```

三个设计点：

1. **`details` 按需省略**——`details === undefined` 时不输出字段，响应体干净（而不是 `"details": null`）
2. **`fail` 不限定 code 类型**——它只被 `onError` 和 hook 调用，错误码的真实约束在 `ApiErrorCode` 上
3. **`ok` 的重载是整个文件最值钱的部分**，见下一节

### 1.1 为什么 `ok` 必须写成重载（踩坑实录 ⭐）

第一版签名是朴素的：

```ts
export const ok = <T>(c: Context, data: T, status: ContentfulStatusCode = 200) =>
  c.json({ code: 'OK', data }, status)
```

在普通路由里能用，一接 `@hono/zod-openapi` 的 `createRoute` 就类型报错。两个连环坑：

- **坑 A：`c.json` 第二参数要求字面量联合**。hono 的 status 参数类型是 `ContentfulStatusCode`（`200 | 201 | 404 | ...` 的联合），不是 `number`——传 `number` 直接编译失败。所以各处状态码要写字面量。
- **坑 B：status 字面量被拓宽**。`ok(c, data, 201)` 时，`status` 参数类型写成 `ContentfulStatusCode` 会让返回类型里的 `_status` 变成**整个联合**（`-1 | 100 | ... | 511`），而 OpenAPI 的 handler 类型要求返回 `TypedResponse<..., 201, 'json'>`——对不上。
- **坑 C（最隐蔽）：上下文返回类型污染**。改成 `<S extends ContentfulStatusCode = 200>(c, data, status?: S)` 后，没传 status 的调用（如 login 里 `ok(c, user)`）会从 **handler 的期望返回类型**反推 `S`——把该路由声明的所有响应状态（`200 | 400 | 401`）全并进 `S`，照样对不上。

最终解法是**重载**：不传 status → 返回类型钉死 `200`；传了 → 从**实参**推断字面量。这是「函数返回类型参与泛型推断」的经典陷阱，值得记住。

## 2. 业务异常：`lib/errors.ts`

```ts
export type ApiErrorCode =
  | 'VALIDATION_ERROR' | 'UNAUTHORIZED' | 'FORBIDDEN' | 'NOT_FOUND'
  | 'CONFLICT' | 'UNPROCESSABLE' | 'RATE_LIMITED' | 'INTERNAL'

export const statusByCode: Record<ApiErrorCode, ContentfulStatusCode> = {
  VALIDATION_ERROR: 400, UNAUTHORIZED: 401, FORBIDDEN: 403, NOT_FOUND: 404,
  CONFLICT: 409, UNPROCESSABLE: 422, RATE_LIMITED: 429, INTERNAL: 500,
}
```

- **code → status 单向映射**：抛业务异常时只说「这是 CONFLICT」，HTTP 状态由映射表推导。新增错误码只改这张表，所有路由自动跟随。
- `codeByStatus()` 反向函数给 `onError` 兜底用：框架抛出的裸 `HTTPException`（只有 status）也能映射回业务 code。

```ts
export class ApiError extends HTTPException {
  readonly code: ApiErrorCode
  readonly details?: unknown

  constructor(code: ApiErrorCode, message: string, details?: unknown) {
    super(statusByCode[code], { message })
    this.name = 'ApiError'
    this.code = code
    this.details = details
  }
}
```

**为什么继承 `HTTPException` 而不是自造 Error 类**：hono 的错误体系里 `HTTPException` 是「带 HTTP 语义的 Error」——它能把 status 带进异常本身，`onError` 里不需要再 if-else 猜状态码；子类只是往车上加 `code`/`details` 两个业务字段。

`apiError` 工厂收敛默认文案：

```ts
export const apiError = {
  conflict: (message = '资源状态冲突，请刷新后重试') => new ApiError('CONFLICT', message),
  unauthorized: (message = '未认证') => new ApiError('UNAUTHORIZED', message),
  // ...
}
```

调用侧变成一行：`throw apiError.conflict('邮箱已被注册')`——比 `new ApiError('CONFLICT', ...)` 少一次 code 拼写错误的机会。

## 3. 校验失败 → 信封：`lib/validator.ts`

```ts
export const validationHook = (result: HookResult, c: Context) => {
  if (!result.success) {
    return fail(c, 'VALIDATION_ERROR', '参数校验失败', 400, z.prettifyError(result.error))
  }
}
```

校验失败的响应也要走信封，否则「全站格式唯一」就有缺口。接入点是 `OpenAPIHono` 的 **defaultHook**（`lib/openapi.ts`）：

```ts
export const createOpenAPI = () => new OpenAPIHono<Env>({ defaultHook: validationHook })
```

> 💡 `zValidator` 的 hook 与 `OpenAPIHono` 的 `defaultHook` 是同一语义的两个入口——我们所有业务路由都走 `createRoute` 三同源，所以只接 defaultHook 一处，`createOpenAPI()` 工厂保证每个子路由 app 自动带上。

## 4. 唯一出口：`index.ts` 的 onError 三段式

```ts
app.onError((err, c) => {
  if (err instanceof ApiError) {
    return fail(c, err.code, err.message, err.status, err.details)   // 业务异常：完整信封
  }
  if (err instanceof HTTPException) {
    return fail(c, codeByStatus(err.status), err.message, err.status) // 框架异常：status 反推 code
  }
  logger.error({ requestId: c.get('requestId'), err }, 'unhandled')   // 未知异常：记日志
  return fail(c, 'INTERNAL', '服务器内部错误', 500)                    // 不把堆栈泄露给客户端
})
```

顺序即语义：`ApiError` 是 `HTTPException` 的子类，必须**先判子类**。第三段是安全底线——未知异常对客户端只说「服务器内部错误」，细节进日志（带 requestId，M3 接上后自动串联）。

配合 `app.notFound`：

```ts
app.notFound((c) => fail(c, 'NOT_FOUND', '路由不存在', 404))
```

404 也走信封，前端拿到的永远是同一种结构。

## 5. 洋葱模型里的错误传播（06 篇兑现）

```
request → requestContext → handler(throw ApiError) → onError → 信封响应
```

任何一层 `throw`，洋葱立即开始回卷，跳过中间所有 `next()` 之后的逻辑，直达 `onError`。这就是「路由里只管 throw、不写 try/catch 拼错误响应」的底气——M5 的 `transitionPost` 里 403/422/409 全是 throw，路由 handler 一个 catch 都没有。

## 6. 对比板块：错误处理三种做法

| 做法 | 优点 | 缺点 | 适用 |
|------|------|------|------|
| **本项目：ApiError + onError 兜底** | 路由零 try/catch；格式强制统一；status 推导 | 需要理解洋葱错误传播 | 所有业务路由 |
| 裸 `HTTPException` | 零封装 | 没有业务 code，前端只能靠 status 猜 | 纯框架层错误 |
| 每个路由手写 `c.json(错误)` | 直观 | 格式漂移是时间问题；重复代码爆炸 | 禁止 |

## 📌 小结

- 信封唯一 = `ok`/`fail` 两个构造器 + onError 唯一出口
- 业务 code 与 HTTP status 分两层，`statusByCode` 单向映射
- `ok` 重载是 OpenAPI 类型对齐的前提；「返回类型污染泛型推断」是 TS 经典坑
