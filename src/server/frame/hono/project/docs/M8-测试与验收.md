# M8 测试与验收

> 所属：[project](../) 实现教学 ｜ 前置：[M7](./M7-生产加固.md) ｜ 对应代码：`src/tests/{setup-env,reset-db}.ts`、`bunfig.toml`、`scripts/test-setup.ts`、`src/tests/*.test.ts`

**一句话定位**：测试隔离三层落地（独立库 / 套件间 TRUNCATE / 独立 Redis 下标）+ fail-fast 自动化验收，57 个测试全绿且绝不误伤开发库。

**面试可答**：套件隔离用事务回滚的前提是「单一连接池」——bun test 每个测试文件独立模块注册表（各自实例化 PrismaClient），外层 BEGIN 包不住别的事务；落地方案是独立测试库 + 每套件 TRUNCATE + 唯一请求特征（邮箱/XFF）。

---

## 1. 隔离方案：为什么不是「每套件事务回滚」

教程初稿（本教程 §6 亦然）设想外层事务回滚——**实测不可用**：

```
bun test 每个测试文件 = 独立模块注册表 = 独立 PrismaClient = 独立连接池
→ 文件 A 里的 BEGIN 包不住文件 B 的连接
→ 回滚方案从根上不成立，不是「实现得好一点」能救的
```

落地方案三层：

| 层 | 手段 | 说明 |
|----|------|------|
| 库级 | 独立 `DATABASE_URL_TEST`（blog_test） | `bun run test:setup` 里 `prisma db push` 自动建库 + 幂等 seed |
| 套件级 | `beforeAll` TRUNCATE（RESTART IDENTITY）+ 重建种子 + `flushdb` | 实测 bun 1.4.2 测试文件**严格串行**（两个 1s 睡眠文件总耗时 2.0s），无并发干扰 |
| 请求级 | 唯一邮箱、唯一 `X-Forwarded-For` | 限流按 IP+路由计数，测试间互不污染 |

## 2. `bunfig.toml`：preload 切换环境（生产代码零改动）

```ts
// src/tests/setup-env.ts —— [test].preload，先于所有测试文件执行
if (!process.env.DATABASE_URL_TEST || !process.env.REDIS_URL_TEST) {
  console.error('[test] 缺少 DATABASE_URL_TEST / REDIS_URL_TEST——拒绝执行测试')
  process.exit(1)
}
process.env.DATABASE_URL = process.env.DATABASE_URL_TEST
process.env.REDIS_URL = process.env.REDIS_URL_TEST
```

`lib/env.ts` 仍只认 `DATABASE_URL`——只是测试进程里的值被换成了测试库。**fail-fast 拒跑是故意的**：测试变量缺失时静默回落 dev 库，第一条 TRUNCATE 就是删库事故。

## 3. `resetTestState`：双保险

```ts
export async function resetTestState() {
  if (process.env.DATABASE_URL !== process.env.DATABASE_URL_TEST) {
    throw new Error('[test] DATABASE_URL 未指向 DATABASE_URL_TEST，拒绝 TRUNCATE')
  }
  await prisma.$executeRawUnsafe(TRUNCATE_ALL)   // 常量字符串，无注入面
  const passwordHash = await Bun.password.hash(SEED_PASSWORD)
  await prisma.user.createMany({ data: SEED_USERS.map((u) => ({ ...u, passwordHash })) })
  await redis.flushdb()
}
```

preload 一层 + 执行前再校验一层——「TRUNCATE 误伤开发库」值得两道锁。`RESTART IDENTITY` 让自增 id 每套件从 1 开始，配合 flushdb 防止旧缓存串台。

## 4. fail-fast 自动化验收（教程 §9 第 7 项）

```ts
const cwd = mkdtempSync(join(tmpdir(), 'blog-env-'))   // 临时 cwd：脱离项目 .env
const env = { ...process.env } as Record<string, string>
delete env.JWT_SECRET
const proc = Bun.spawnSync({
  cmd: [process.execPath, join(import.meta.dir, '..', 'index.ts')],
  cwd, env, stdout: 'pipe', stderr: 'pipe',
})
expect(proc.exitCode).toBe(1)
expect(new TextDecoder().decode(proc.stderr)).toContain('JWT_SECRET')   // 点名缺失项
```

把「验收清单」变成可回归的测试——清空 JWT_SECRET 启动必须死、且死得明白。

## 5. 工具链约定

- `bun run test` = `test:setup`（幂等）+ `bun test`——每次全量都在干净状态上跑
- 种子数据单一来源：`prisma/seed-data.ts`，seed 脚本与 reset 共用
- oxlint 对 `src/tests/**` 豁免 `no-await-in-loop`：限流测试的串行 await 是计数语义本身

## 6. 对比板块：测试隔离策略

| 策略 | 前提 | 速度 | 本项目落点 |
|------|------|------|-----------|
| 事务回滚 | 单一连接池 | 快 | ❌ bun test 模型下不成立 |
| **TRUNCATE 重置（本项目）** | 套件串行 | 中 | 套件 beforeAll |
| 独立 schema/库 per 套件 | 建库成本 | 并行友好 | 规模大了再上 |

## 📌 小结

- 隔离三层：库级、套件级、请求级；工具的执行模型决定测试架构（串行 → TRUNCATE 安全）
- TRUNCATE 的双保险 fail-fast：宁可拒跑，不可误删
- 验收清单里「清空配置启动即崩」这类行为断言，spawn 测试固化后永不回退
