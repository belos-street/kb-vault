## 这一步做什么

把「项目能启动、配置缺失能立刻炸」立起来：bun 初始化、strict tsconfig、依赖清单、目录骨架、`lib/env.ts` fail-fast、`/healthz` 占位。

## 动手步骤

1. `bun init`，确认 `package.json` 里有 `"type": "module"`——**Prisma 7 是 ESM-only，这一步漏了后面 migrate 直接报错**
2. `tsconfig.json`：`strict: true` + `module: ESNext` + `moduleResolution: bundler` + `types: ["bun"]`
3. 装依赖：`hono`、`@prisma/client@7`、`@prisma/adapter-pg`、`zod`、`@hono/zod-openapi`、`@scalar/hono-api-reference`、`pino`、`ioredis`；dev：`prisma@7`、`oxlint`、`oxfmt`（配置复制 agents.md §5.6）
4. 目录骨架：`src/{routes,middleware,lib,schemas,domain,tests}` + `prisma/`
5. `lib/env.ts`：Zod 校验 env，失败 `process.exit(1)`
6. `index.ts` 挂 `/healthz`，`bun run dev` 跑通

## fail-fast 的实现（lib/env.ts）

```ts
const parsed = envSchema.safeParse(process.env)
if (!parsed.success) {
  const detail = parsed.error.issues
    .map((i) => `${i.path.join('.')}: ${i.message}`)
    .join('; ')
  console.error(`[env] 环境变量校验失败 → ${detail}`)   // 点名缺哪项
  process.exit(1)
}
export const env = parsed.data
```

设计点：**只校验一次、启动期校验**。运行期任何代码读到的 `env` 都是已收敛的类型化对象，不需要防御式判空。`JWT_SECRET` 用 `min(32)` 表达长度约束——弱密钥在启动期就拦下，而不是等出事。

## 验证

- 清空 `JWT_SECRET` 再 `bun src/index.ts` → 退出码 1、stderr 点名 `JWT_SECRET`（这个行为在 M8 被写成 spawn 自动化用例）

## 面试可答

> **问：为什么配置校验放在启动期而不是运行时？**
> 配置缺失是「不可恢复错误」，晚暴露只会让故障点离原因更远。启动期 fail-fast + 点名缺失项，把排障时间从「运行时诡异行为」压缩成「看一眼启动日志」。
