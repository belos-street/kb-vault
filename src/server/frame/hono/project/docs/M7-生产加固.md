# M7 生产加固

> 所属：[project](../) 实现教学 ｜ 前置：[M6](./M6-评论并发与Refresh吊销.md) ｜ 对应代码：`src/index.ts`、`src/middleware/{rate-limit,csrf}.ts`、`src/lib/cache.ts`、`src/services/{posts,comments}.ts`

**一句话定位**：功能能用与企业级之间差的那几件——两层缓存、Redis 限流、CSRF、优雅停机、中间件组装顺序，全部带部署前提与实测坑位。

**面试可答**：缓存的第一约束是可见性不是性能——匿名响应才可共享缓存；限流的原子性（SET NX + INCR）和 IP 信任前提（可信网关）决定它在生产里是防线还是摆设。

---

## 1. 缓存：两层各管一层，可见性是第一约束

- **HTTP 层**：公开列表 `Cache-Control: public, max-age=60` + `hono/etag`——**只给匿名响应打 public**。登录响应按可见性矩阵个性化（能看到自己的 DRAFT），打了 public，CDN/浏览器会把 A 的列表缓存给 B
- **应用层**：详情 cache-aside 只缓存匿名可见的 PUBLISHED 文章——否则缓存层就是绕过权限矩阵的旁路；缓存的是 DTO 不是 ORM 行（JSON round-trip 后 Date 变 string，`toPostDTO` 直接炸）
- **失效**：更新/流转/软删/评论增删统一 `DEL post:{id}`——`commentCount` 进了详情 DTO，评论增删也必须失效，否则读到旧计数。失效点覆盖「所有进入缓存值的字段」是纪律不是技巧

## 2. 限流：原子性 + 键空间 + 部署前提

```ts
await redis.set(key, '0', 'EX', windowSec, 'NX')   // 首请求原子占位并带上 TTL
const hits = await redis.incr(key)
if (hits > max) throw apiError.rateLimited()
```

三个层次：

1. **原子性** ⭐：教程初稿的 `INCR` 后补 `EXPIRE` 是两步——进程崩在两步之间，key 永无 TTL，该 IP+路由累积到**永久 429**。`SET NX` 占位 + INCR 计数，TTL 与 key 同生
2. **键空间**：`/login` 独立前缀（`prefix: 'login'`）更严阈值 10 次/分——与全局限流分开计数，同请求不会双扣同一个键
3. **部署前提**（写在 docblock）：XFF 首段只在可信网关（反代/LB）后可信；直连暴露时客户端可伪造 XFF 轮换 IP 绕过限流——撞库防线是否有效取决于部署拓扑

## 3. CSRF：为什么自实现 csrfGuard ⭐

hono 内置 `csrf()` 对**缺失 Content-Type 的非安全方法默认按 text/plain 处理**——无请求体的 `DELETE`、无 body 的 `/refresh` 全被 403，curl 直接不可用（容器实测发现，先于文档存在）。按教程声明的语义自实现 `csrfGuard`：只拦「带表单类 Content-Type 的非安全方法」。分层上 **SameSite=Lax Cookie 才是主防线**——跨站 fetch/表单 POST 本就不携带 Cookie；csrfGuard 兜底老浏览器忽略 SameSite 的表单向量（表单伪造不了 `application/json`）。

## 4. 优雅停机（index.ts）

```ts
process.on('SIGTERM', () => {
  void shutdown()   // server.stop() → prisma.$disconnect() → redis.quit()
})
// + 8s 超时兜底强制退出
```

- 链路任何一步挂住都会把 SIGTERM 拖成编排器宽限期后的 SIGKILL——每步打点让容器日志可核对
- 兜底 `process.exit` 保证「有界退出」比「完美退出」重要
- 部署级坑（`sh -c` 包装不转发 SIGTERM → SIGKILL）单独在 [M9](./M9-部署.md) 展开

## 5. 组装顺序（§7.5，顺序即语义）

```ts
app.use('*', requestContext)      // M3
app.use('*', secureHeaders())
app.use('/api/*', cors(...))      // 可选 CORS_ORIGIN：缺省同源不放开（fail-safe 默认）
app.use('*', csrfGuard)
app.use('*', bodyLimit({ maxSize: 1024 * 1024 }))
app.use('/api/*', rateLimit({ max: 60, windowSec: 60 }))
app.route('/api', api)
```

错误处理与请求上下文最先；限流与 bodyLimit 在业务解析前拦。审计收尾：`DELETE_POST` 补 DENIED 留痕，流转 OK/DENIED 已有（M5）。

## 6. 踩坑实录：全量测试被自家限流打死

套件内几十次 register/login 全来自 `unknown` IP，login 阈值 10 次 → 测试中途 429。解法：测试 helper 每次请求带唯一 `X-Forwarded-For`——限流按 IP+路由计数，天然隔离（M8 收进测试规范）。

## 7. 对比板块：限流窗口

| 方案 | 突刺 | 实现复杂度 | 适用 |

| **固定窗口（本项目）** | 窗口边界 2x 突刺 | INCR 一行 | 防滥用阈值场景 |

## 📌 小结

- 缓存可见性 > 缓存性能：匿名才 public、cache-aside 只存匿名可见、失效覆盖全部字段来源
- 限流三件：原子性、键空间隔离、部署前提声明——缺一件就是生产事故预案
- 优雅停机 = 摘流量 → 关依赖 → 有界退出；每步打点是容器环境下的可观测底线
