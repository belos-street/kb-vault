## 这一步做什么

缓存（HTTP + Redis 两层）、Redis 限流、CSRF、优雅停机、中间件组装、审计收尾。

## 缓存：可见性是缓存的第一约束

- 公开列表：`Cache-Control: public, max-age=60` + `hono/etag`——**只给匿名响应打 public**，登录响应按可见性矩阵个性化，打了 public 会把 A 的列表缓存给 B
- 详情 cache-aside：只缓存匿名可见的 PUBLISHED 文章（否则缓存层就是绕过权限矩阵的旁路）；缓存的是 DTO 不是 ORM 行（JSON round-trip 后 Date 变 string，缓存行会让 toPostDTO 炸）
- 失效：更新/流转/软删/评论增删统一 `DEL post:{id}`——`commentCount` 进了详情 DTO，评论增删也必须失效，否则读到旧计数

## 限流：原子性与键空间

```ts
await redis.set(key, '0', 'EX', windowSec, 'NX')   // 首请求原子占位带 TTL
const hits = await redis.incr(key)
```

- 为什么不是教程原稿的 `INCR` 后补 `EXPIRE`：两步之间崩溃 → key 永无 TTL → 该 IP+路由永久 429
- `/login` 独立键空间（`prefix: 'login'`）更严阈值 10 次/分——与全局限流分开计数，同请求不会双扣同一个键
- **部署前提**（写在代码 docblock）：XFF 首段只在可信网关后可信，直连暴露可伪造轮换 IP 绕过限流

## CSRF：为什么自实现 csrfGuard

hono 内置 `csrf()` 对**缺失 Content-Type 的非安全方法默认按 text/plain 处理**——无请求体的 `DELETE`、无 body 的 `/refresh` 全被 403，curl 直接不可用（实测发现）。按教程声明的语义自实现：只拦「带表单类 Content-Type 的非安全方法」；主防线本就是 SameSite=Lax Cookie（跨站 fetch/表单 POST 不携带 Cookie）。

## 优雅停机（index.ts）

```ts
process.on('SIGTERM', () => {
  void shutdown()   // server.stop() → prisma.$disconnect() → redis.quit()，逐步打点
})
// + 8s 超时兜底强制退出
```

链路任何一步挂住都会把 SIGTERM 拖成编排器宽限期后的 SIGKILL——打点让容器日志能核对每步，兜底保证有界退出。（sh 包装不转发 SIGTERM 的部署级坑见 [M9](./M9-部署.md)。）

## 组装顺序（§7.5，顺序即语义）

`onError → requestContext → secureHeaders → cors(可选) → csrfGuard → bodyLimit(1MB) → rateLimit → 业务路由`——错误处理与请求上下文最先，限流与 bodyLimit 在业务解析前拦。审计收尾：`DELETE_POST` 补 DENIED 留痕，流转 OK/DENIED 已有。

## 踩坑实录

测试全量跑限流误伤：套件内几十次 register/login 都来自 `unknown` IP，login 阈值 10 次直接 429。解法：测试 helper 每次请求带唯一 `X-Forwarded-For`（限流按 IP+路由计数，天然隔离）。

## 面试可答

> **问：cache-aside 为什么是「先更库再删缓存」，不是「先删缓存再更库」或「更新缓存」？**
> 先删后更：删与更之间读请求会把旧值回填，缓存脏到下一次写；更新缓存：并发写时后到的旧值可能覆盖新值，且多数缓存值是查询结果的加工物、写路径算不起。先更库再删缓存，最坏情况是删后读到一次旧值（TTL 兜底），一致性窗口最小。
