# 01 概述与快速入门

> 所属大纲：[readme.md](../readme.md) ｜ 预计：0.5 天 ｜ 前置：无

**一句话定位**：建立全景认知——Hono 是什么、快在哪、与 Express/Koa 的本质差异在哪。

**面试可答**：Hono 是基于 Web Standards（Request/Response/Fetch API）的轻量级 Web 框架，零依赖，一套代码可跑在 Cloudflare Workers、Deno、Bun、Node.js 等多个运行时上。

---

## 1. Hono 是什么

- 名字来自日语「炎（ほのお）」，作者 yusukebe，2021 年首发
- 当前稳定线 **v4.13.x**（写作时点，以 [Releases](https://github.com/honojs/hono/releases) 为准）
- 定位是「库」而非「架构框架」：它解决 HTTP 层，不管 DI、模块边界、微服务——那是 Nest 的地盘

## 2. 四个核心特性（一句话原理）

| 特性 | 一句话原理 |
|------|-----------|
| Ultrafast | RegExpRouter 把所有路由编译成「一个大正则 + 静态表」，匹配时单次执行 |
| Lightweight | 核心零依赖，`hono/tiny` 预设体积在 14kB 量级（以官方 README 当前数据为准） |
| Multi-runtime | handler 本质是 `fetch`：`(Request) => Promise<Response>`，任何平台都能托管 |
| Web Standards | 直接使用标准 Request/Response/Cookie API，不发明 req/res 抽象 |

> 💡 最后一行是其余三行的「因」：因为只依赖 Web 标准，才能零成本跨运行时；因为不做重复抽象，才能保持极小。

## 3. Bun 快速上手

```bash
bun create hono@latest hono-playground
cd hono-playground
bun install
bun run dev
```

默认模板入口 `src/index.ts`：

```ts
import { Hono } from 'hono'

const app = new Hono()

app.get('/', (c) => c.text('Hello, Hono!'))

export default app
```

- Bun 识别「默认导出的 fetch handler」，`bun run dev`（带热重载）即可托管
- 需要显式控制端口时：

```ts
Bun.serve({ fetch: app.fetch, port: 3000 })
```

## 4. 心智模型：一切皆 fetch

每个 handler 接收 Context `c`，返回标准 `Response`——`c.json()` / `c.text()` 只是 Response 工厂函数。这带来两个直接红利：

1. **代码可移植**：`app.fetch` 就是一个标准 fetch 函数，谁都能托管（07 篇展开）
2. **测试不需要启动服务器**：`await app.request('/api/users')` 直接构造标准 Request 拿到 Response（10 篇实战）

对比 Express 的 `req/res` 双对象抽象：Hono 没有第二层抽象税，你学的就是平台本身。

## 5. ⚖️ 对比板块：Hono vs 同类

| 维度 | Hono | Express | Koa | Elysia |
|------|------|---------|-----|--------|
| 请求/响应 | Web Standards | 自有 req/res | 自有 ctx | 类 fetch 自有实现 |
| 中间件模型 | 洋葱（async） | 线性（callback） | 洋葱（async） | 类洋葱 |
| 运行时 | 全平台 | Node | Node | Bun 优先 |
| 类型安全 | 路由级推导 + RPC 端到端 | 弱 | 弱 | 强（TypeBox 体操） |
| 生态 | 快速增长，兼容 fetch 生态 | 最大 | 中 | 年轻 |

**选型结论**：

- Bun 生态 / 边缘部署 / Agent 后端 / 轻量 API → **Hono**
- 大团队、长周期、微服务架构的企业系统 → **NestJS**（架构层框架，与本课互补）
- 纯 Bun + 极致类型体操，无跨运行时诉求 → Elysia 可作备选
- 存量 Express 项目 → 除非有明确痛点，迁移收益通常不值

## 6. 不适用场景

- 复杂企业架构（DI 容器、模块边界、微服务治理）→ NestJS
- 重前端 SSR 一体化全栈 → Next.js / Remix
- 深度依赖 Express 专属中间件的存量系统

## 8. 💬 面试问答

**Q1：Hono 为什么快？**

RegExpRouter 在路由注册完成后，将所有动态路由编译为一个正则、静态路由存入查找表——匹配时单次执行同时命中 handler 与路径参数。对比 Express 逐条遍历全部 layer。

（追问：所有路由都能编译进一个正则吗？——不能覆盖的少数模式由 TrieRouter 兜底，SmartRouter 负责调度，详见 02 篇。）

**Q2：「基于 Web Standards」在实际开发里意味着什么？**

三件事：① 可移植——fetch handler 放到任何运行时都能跑；② 零抽象税——直接用标准 Request/Response/Cookie，框架学习成本极低；③ 工具链直连——`app.request()` 构造标准 Request 即可测试，无需起服务器。

**Q3：Hono 和 Elysia 怎么选？**

同一 Runtime 下的两条路线：Hono 押注「标准 + 可移植」，Elysia 押注「Bun 深度绑定 + 极致类型」。未来可能迁 Node 或需部署边缘 → Hono；纯 Bun 项目且吃类型体操 → Elysia 可选。

## 📌 小结

- `fetch` handler 是 Hono 一切可移植性的根
- RegExpRouter 编译期正则是性能的根
- 选型一句话：轻、快、跨运行时 → Hono；重架构 → Nest；纯 Bun 极致类型 → Elysia
