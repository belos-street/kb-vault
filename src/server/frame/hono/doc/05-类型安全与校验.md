# 05 类型安全与校验

> 所属大纲：[readme.md](../readme.md) ｜ 预计：1 天 ｜ 前置：04

**一句话定位**：Hono 一等公民 TypeScript——路由字符串推导出参数类型，Zod 校验产出「已验证」的类型。

**面试可答**：路径参数由模板字面量类型自动推导；`@hono/zod-validator` 让 `c.req.valid('json')` 拿到 Zod schema 产出与收窄后的完整类型。

---

## 1. 路径参数的类型推导

```ts
const app = new Hono()

app.get('/posts/:id/comments/:commentId', (c) => {
  // c.req.param 的类型自动为 { id: string; commentId: string }
  const { id, commentId } = c.req.param()
  return c.json({ id, commentId })
})
```

**原理一句话**（源码级）：Hono 的路由方法返回的是**携带累积类型信息的 app 新类型**——`:id` 这类段名经模板字面量类型（`` `:${string}` `` 提取）累积进泛型参数，`param/query/header` 的签名随之收窄。这也解释了一个常见约束：**类型随链式调用累积，`app.route()` 的返回值要接住**（08 篇 RPC 依赖同一条机制）。

## 2. 类型化 Context：Env 泛型

```ts
import { Hono } from 'hono'

type Env = {
  Variables: { userId: string }   // 逻辑态：中间件注入的数据（c.set/get）
  Bindings: { DB: D1Database }    // 平台态：运行时绑定（Workers 的 KV/D1、env）
}

const app = new Hono<Env>()
```

- `Variables`：你自己的请求链数据（04 篇 `c.set('userId')`）
- `Bindings`：平台给你的东西——Workers 里是 KV/D1/R2 与 vars；Node/Bun 里通常放环境变量（07 篇）

两个槽分开，是为了让业务代码与平台解耦：换运行时只改 Bindings，业务逻辑不动。

## 3. Zod 校验：`@hono/zod-validator`

```bash
bun add zod @hono/zod-validator
```

```ts
import { z } from 'zod'
import { zValidator } from '@hono/zod-validator'

const createUserSchema = z.object({
  name: z.string().min(1),
  email: z.email(), // v4 顶层 API（zod v3 写 z.string().email()）
})

app.post('/users',
  zValidator('json', createUserSchema),
  (c) => {
    const user = c.req.valid('json')   // 类型 = z.infer<typeof createUserSchema>
    return c.json(user, 201)
  },
)
```

三个关键点：

1. **校验失败默认返回 400**（body 为校验结果），成功才进 handler——handler 里拿到的数据**已通过校验**，不需要二次防御
2. **各槽独立校验**：`zValidator('json', s1)`、`zValidator('query', s2)`、`zValidator('param', s3)` 可叠加，`c.req.valid('query')` 等分别取值
3. **要自定义失败响应**（如统一错误格式）用 hook：

```ts
zValidator('json', createUserSchema, (result, c) => {
  if (!result.success) {
    return c.json({ code: 'VALIDATION_ERROR', details: result.error.flatten() }, 400)
  }
})
```

### 3.1 常用技巧：query 的数字与多值

```ts
const pageQuery = z.object({
  page: z.coerce.number().int().min(1).default(1),  // '?page=2'（string）→ 2（number）
  tags: z.array(z.string()).optional(),             // 配合 c.req.queries
})
```

`z.coerce` 处理「query 永远是 string」的转换，比 handler 里手写 `Number()` 安全。

### 3.2 ⚖️ 校验路线对比

| 路线 | 形态 | 何时选 |
|------|------|--------|
| `@hono/zod-validator` + Zod | 函数式，schema 单一来源，类型即校验 | 主推——本课与实战 B 统一 Zod |
| class-validator + class-transformer | 装饰器挂 DTO 类 | Nest 生态存量路线（Nest 12 亦支持 Zod 同源） |
| handler 内手写 if 防御 | 零依赖 | 一次性小接口；业务长大立即劣化 |

## 4. ✍️ 练习：类型安全 CRUD

**要求**：为 `/posts` 实现创建（`{ title, tags?, published? }`）与列表（query: `page`、`limit`）两个接口，全部经 Zod 校验；列表返回 `{ items, page, limit }`。

**提示**：两个 schema 分别挂 `json` 与 `query` 槽；`z.coerce.number()` 处理分页参数。

**预期效果**：合法请求返回 201/200 且数据结构正确；`POST` 缺字段或 `?page=abc` 得 400，且响应里能定位到具体字段。

## 5. 💬 面试问答

**Q1：路径参数类型是怎么推导出来的？**

路由方法带泛型累积：`:xxx` 段名通过模板字面量类型解析进 app 的类型参数，`c.req.param` 等方法签名随之收窄为 `{ xxx: string }`。代价是类型只在链式书写时累积——这就是官方强调「把路由链赋给变量再导出」的原因。

**Q2：zValidator 校验失败的默认行为？自定义怎么做？**

默认 400 + 校验结果 body。需要统一错误格式时给第三个参数 hook，失败时返回自定义 Response——与 06 篇的全局错误处理打通（业务校验错误也走 `{ code, message, details }`）。

**Q3：Env 泛型里 Variables 和 Bindings 为什么要分开？**

生命周期与来源不同：Variables 是请求链内中间件注入的逻辑数据；Bindings 是运行时平台注入的环境能力。分开后业务代码只依赖 Variables，换部署平台只动 Bindings——多运行时可移植的类型层保障。

## 📌 小结

- 路由类型 = 模板字面量类型累积，链式书写是前提
- Env 双槽：Variables 管逻辑、Bindings 管平台
- zValidator 三槽独立 + hook 自定义失败响应；`z.coerce` 是 query 数值化的标准解
