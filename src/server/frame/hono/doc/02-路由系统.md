# 02 路由系统

> 所属大纲：[readme.md](../readme.md) ｜ 预计：1 天 ｜ 前置：01

**一句话定位**：掌握 URL → 处理函数的映射体系，并理解 Hono「快」的根源。

**面试可答**：Hono 有 5 种路由器，RegExpRouter 最快（静态查表 + 动态路由编译为单次正则匹配），SmartRouter 默认自动调度。

## 1. 路由 API 速过（不占篇幅）

```ts
const app = new Hono()

// RESTful 动词
app.get('/posts', listAll)
app.post('/posts', create)
app.put('/posts/:id', update)
app.delete('/posts/:id', remove)

// 路径参数 / 查询参数
app.get('/users/:id', (c) => {
  const id = c.req.param('id')        // /users/42 → '42'
  const page = c.req.query('page')    // ?page=2   → '2'（注意：永远是 string）
  return c.json({ id, page })
})

// 可选参数与通配
app.get('/users/:id?', (c) => c.req.param('id') ?? 'all')  // /users 与 /users/42 都命中
app.get('/static/*', (c) => c.text('SPA fallback'))         // 前缀匹配

// 一次注册多方法
app.on(['GET', 'POST'], '/ping', (c) => c.text('pong'))
```

## 2. 模块化分组：`app.route()`

大型应用按资源拆文件，是实战的标准组织手段（09/10 篇直接复用）：

```ts
// src/routes/users.ts
import { Hono } from 'hono'

const users = new Hono()

users.get('/', (c) => c.json([{ id: 1, name: 'Ada' }]))
users.get('/:id', (c) => c.json({ id: c.req.param('id') }))

export default users
```

```ts
// src/index.ts
import { Hono } from 'hono'
import users from './routes/users'
import posts from './routes/posts'

const app = new Hono()

app.route('/users', users)   // /users/:id
app.route('/posts', posts)   // /posts/:id

export default app
```

> 💡 `app.route()` 有返回值且会累积类型——这是 08 篇 RPC 端到端类型安全的基础。

## 3. 5 种路由器：精讲两个，其余了解

| 路由器 | 一句话 | 深度 |
|--------|--------|------|
| RegExpRouter | 静态查表 + 动态路由编译为单次正则 | 精讲 |
| SmartRouter | 自动调度多个路由器（默认） | 精讲 |
| TrieRouter | 纯 TS Trie 树，支持所有模式 | 备选兜底 |
| LinearRouter | 注册 O(1)，线性查找 | 了解即可 |
| PatternRouter | 最小实现，体积最小 | 了解即可 |

### 3.1 RegExpRouter 原理（面试高发）

路由注册结束后、第一次请求前，RegExpRouter 做一次**编译**：

1. **静态路由**（如 `/users/me`）→ 存入查找表，匹配时哈希命中
2. **动态路由**（如 `/users/:id`）→ 全部合并编译成**一个大正则**，路径段参数转为命名捕获组
3. 匹配时执行**一次** `match`，同时拿到 handler 与全部 params

对比 Express：每来一个请求，逐条遍历所有注册的 layer（路由 + 中间件），路由越多越慢；Hono 把成本转移到注册后的一次性编译，匹配复杂度与路由数量近乎无关。

（追问：为什么不全编译成一个正则？——路由模式过复杂时正则会爆炸， RegExpRouter 对无法覆盖的模式会标记「不支持」。）

### 3.2 SmartRouter：默认的调度器

`new Hono()` 内部默认就是：

```ts
import { Hono } from 'hono'
import { RegExpRouter } from 'hono/router/reg-exp-router'
import { SmartRouter } from 'hono/router/smart-router'
import { TrieRouter } from 'hono/router/trie-router'

const app = new Hono({
  router: new SmartRouter({
    routers: [new RegExpRouter(), new TrieRouter()],
  }),
})
```

工作方式：注册请求转发给内部所有路由器；匹配时按顺序询问，RegExpRouter 支持 → 命中并缓存选择；不支持的模式 → 落到 TrieRouter。**快路径走 RegExpRouter，全兼容性由 TrieRouter 兜底**——这就是「默认即最优」的实现。

> ⚠️ 自定义 router 后，`app.route()` 分组等 API 行为不变，仅匹配策略变化。

## 5. 💬 面试问答

**Q1：Hono 的路由为什么快？**

静态路由查表 + 动态路由编译为一个大正则，单次匹配同时得到 handler 与参数；成本从「每请求逐条遍历」转移为「注册后一次性编译」。

（追问：什么情况下会退化？——模式超出正则表达力时由 SmartRouter 落到 TrieRouter 逐段匹配。）

**Q2：5 种路由器怎么选？**

日常不需要选——默认 SmartRouter（RegExpRouter + TrieRouter）已是最优组合。只有两个特殊场景：Serverless 每次冷启动都要重建路由 → LinearRouter（注册 O(1)）；极端体积敏感 → PatternRouter。

**Q3：路由匹配发生在哪个阶段？中间件呢？**

注册阶段只做收集（中间件直接入表，动态路由进入待编译状态）；第一次请求触发 RegExpRouter 编译，之后匹配 O(1)。中间件不参与正则编译，按注册顺序组成洋葱层（04 篇）。

## 📌 小结

- `app.route()` 分组是实战组织手段，且是 RPC 类型的累积基础
- 快的根源：编译期把 N 条路由压成 1 次正则匹配
- 默认 SmartRouter = 快路径（RegExp）+ 全兼容兜底（Trie），日常无需干预
