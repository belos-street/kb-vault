# 07 多运行时与部署

> 所属大纲：[readme.md](../readme.md) ｜ 预计：1 天 ｜ 前置：06

**一句话定位**：同一份业务代码跑在不同运行时——理解 Adapter 模式与 `c.env` 的平台差异，按场景选部署目标。

**面试可答**：Hono 应用本质是 `fetch` 函数，应用代码统一、入口文件不同；各平台通过 Adapter 接入，环境差异收敛在 `c.env`。

---

## 1. 原理：app.fetch 是唯一的契约

```ts
// 这就是 Hono 应用的一切
const handler: (req: Request) => Promise<Response> = app.fetch
```

所有平台适配都是把平台原生 I/O 转成这个签名：Workers 天然如此（fetch 事件）；Bun.serve 原生接受；Node 需要 adapter 转换 IncomingMessage/ServerResponse → Request/Response。

## 2. 三大运行时入口（精讲）

### 2.1 Bun：零适配

```ts
// src/index.ts
import { Hono } from 'hono'

const app = new Hono()
app.get('/', (c) => c.text('hello from bun'))

export default app   // bun run dev / bun ./src/index.ts 直接托管（含 --hot 热重载）
```

或显式控制：

```ts
Bun.serve({ fetch: app.fetch, port: 3000 })
```

### 2.2 Node.js：`@hono/node-server`（v2.x）

```bash
bun add @hono/node-server   # Node 项目内用 npm/pnpm 安装亦可
```

```ts
import { serve } from '@hono/node-server'
import { Hono } from 'hono'

const app = new Hono()
app.get('/', (c) => c.text('hello from node'))

serve({ fetch: app.fetch, port: 3000 }, (info) => {
  console.log(`listening on http://localhost:${info.port}`)
})
```

adapter 的职责：`http.IncomingMessage/ServerResponse ↔ 标准 Request/Response` 双向转换（含流式 body 与 headers 迭代语义差异）。

### 2.3 Cloudflare Workers：`export default app`

```toml
# wrangler.toml（最小配置）
name = "hono-app"
main = "src/index.ts"
compatibility_date = "2026-08-01"
```

```ts
// src/index.ts —— Workers 的入口约定就是默认导出 fetch handler
import { Hono } from 'hono'

const app = new Hono()
app.get('/', (c) => c.text('hello from workers'))

export default app
```

```bash
bunx wrangler dev      # 本地模拟
bunx wrangler deploy   # 发布边缘
```

> Deno 及 Lambda、Vercel、Fastly 等其余平台一行带过：Deno 直接 `Deno.serve(app.fetch)`；其余按 [官方平台文档](https://hono.dev/docs/) 的 adapter 接入，套路与 Node 相同。

## 3. `c.env`：平台差异的收敛点

```ts
type Env = {
  Bindings: {
    KV: KVNamespace      // Workers 绑定资源
    JWT_SECRET: string   // Workers vars / Node process.env
  }
}
const app = new Hono<Env>()

app.get('/x', (c) => {
  const secret = c.env.JWT_SECRET   // 统一入口
  c.env.KV.put('k', 'v')            // 平台能力也在这里
})
```

- Workers：env 是部署时注入的绑定对象（vars + KV/D1/R2）
- Node/Bun：env 通常放 `process.env` 的解析结果——常见做法是在入口把它们塞进 `Bindings` 类型对应的对象（或直接用 `c.env` 传一个 `{ ...process.env }`）
- 业务代码只认 `c.env.xxx`，不直接 import `process.env`——跨运行时移植时零改动

## 4. 部署选型：长连接是分水岭

| 场景 | 推荐 | 原因 |
|------|------|------|
| API / 网站后端、流量波动大 | Workers | 边缘就近 + 按请求计费，冷启动≈0 |
| **SSE / WebSocket / Agent 长任务** | **Node / Bun** | Workers 对单连接时长与 CPU 时间有限制，长流式场景受限 |
| 已有 Node 运维体系 | Node adapter | 渐进迁移，Docker/K8s 流程照旧 |

LLM 流式、Agent 会话这类「一条连接活很久」的服务，选 Node/Bun 是硬约束，不是性能偏好（09 篇实战 A 按此选型）。

## 5. ✍️ 练习：一次编写，两处部署

**要求**：把前几篇的路由应用分别跑在 Bun（`bun run dev`）与 Workers（`wrangler dev`）；secret 类配置走 `c.env`，两处代码零差异。

**提示**：Workers 侧入口改为 `export default app`；`wrangler.toml` 里用 `[vars]` 放测试 secret。

**预期效果**：两个运行时下 `curl localhost:8787`（Workers 默认端口）与 `:3000`（Bun）返回一致；代码里无 `process.env` 直接引用。

## 6. 💬 面试问答

**Q1：Hono 的多运行时是怎么实现的？**

应用层只有一个契约：`fetch(Request) => Promise<Response>`。各平台 adapter 负责原生 I/O 与标准对象的双向转换，平台特有能力（KV 等）收敛在 `c.env` 的 Bindings。业务代码与运行时彻底解耦。

（追问：代价是什么？——adapter 层的性能损耗与语义差异（如 Node 的流式 headers），以及平台特有 API 需要 Bindings 类型化封装。）

**Q2：`c.env` 和 `process.env` 的区别？**

前者是 Hono 抽象的「当前平台环境」（Workers 部署时注入、可含 KV 等非 env 资源），后者是 Node 专属。业务代码依赖 `c.env` 才能跨运行时；`process.env` 只应在入口组装 env 对象时出现。

**Q3：什么服务不适合部署到 Cloudflare Workers？**

长连接（SSE/WS 长流式）、重 CPU 计算、依赖本地文件系统/长驻内存状态的服务。Workers 按请求计费且限制单请求 CPU 时间与连接生命周期。

## 📌 小结

- 契约唯一：`app.fetch`；平台差异收敛在入口文件 + `c.env`
- 业务代码只认 `c.env.xxx`，`process.env` 只出现在入口
- 长连接（SSE/Agent）选 Node/Bun，短请求选 Workers——09 篇按此部署
