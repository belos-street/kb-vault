**一句话定位**：Prisma 与 Nest 的集成范式——连接管理、事务、分页、软删除，以及数据权限/多租户的进阶落地。

## 1. PrismaService：与 Nest 的集成范式

```bash
npm i prisma -D && npx prisma init        # schema.prisma + .env
npx prisma migrate dev --name init        # schema → 迁移 → 客户端生成
```

```prisma
model Post {
  id        String    @id @default(uuid())
  title     String
  content   String
  status    PostStatus @default(DRAFT)
  deletedAt DateTime?
  createdAt DateTime  @default(now())
  updatedAt DateTime  @updatedAt
  @@index([status, createdAt])
}

model AuditLog {
  id        String   @id @default(uuid())
  action    String
  refId     String?
  createdAt DateTime @default(now())
}
```

```ts
// 与 03 篇生命周期钩子的标准配合
@Injectable()
export class PrismaService
  extends PrismaClient
  implements OnModuleInit, OnModuleDestroy
{
  async onModuleInit() { await this.$connect() }
  async onModuleDestroy() { await this.$disconnect() }
}
```

- PrismaModule 注册为 `@Global()`（03 篇的例外条款：数据库客户端是公认的上下文无关基础设施）
- **schema 是单一事实源**：改表 = 改 schema → `migrate dev` → 生成客户端 → TS 类型即时更新；禁止手工改库再反向同步

## 2. 事务：数组式与交互式

```ts
// 交互式事务：业务逻辑参与事务（推荐，能读中间结果）
async transfer(postId: string, toUserId: string) {
  return this.prisma.$transaction(async (tx) => {
    const post = await tx.post.findUnique({ where: { id: postId } })
    if (post?.status !== 'PUBLISHED')
      throw new BizException('POST_NOT_PUBLISHED', '文章不可转移', 422)
    await tx.post.update({ where: { id: postId }, data: { ownerId: toUserId } })
    await tx.auditLog.create({ data: { action: 'transfer', postId } })
    return { ok: true }
  }, { isolationLevel: 'ReadCommitted' })     // 显式声明隔离级别
})
```

- 数组式 `$transaction([...prisma])` 只适合无逻辑的原子批量写；有条件判断/抛错一律交互式
- 隔离级别：默认读已提交够用；「先读后写防并发重复」要么加隔离级别，要么用数据库唯一约束兜底（幂等优先级 > 隔离级别，10 篇呼应）
- **事务传播简介**：Service 层互相调用时让内层复用外层事务——`@nestjs-cls` 提供 transactional hooks（`cls.tx()` 挂载事务实例）；简单场景手动传 `tx` 参数即可，别为传播框架化

## 3. 分页：offset vs cursor

| 方式 | 写法 | 问题 / 优势 |
|------|------|------------|
| offset | `skip: 20, take: 10` | 简单可跳页；深翻页慢（skip 全扫）+ 并发增删导致漂页 |
| cursor | `cursor: { id: nextCursor }, take: 10`（cursor 即上一页返回的 nextCursor） | O(1) 稳定翻页；只能顺序翻，需稳定有序字段（id/createdAt + 二级排序） |

```ts
async list(q: { cursor?: string, take: number }) {
  const items = await this.prisma.post.findMany({
    where: { deletedAt: null },
    orderBy: { id: 'asc' },
    take: q.take + 1,                    // 探头：多取一条判断 hasNext
    // 不写 skip:1 —— cursor 从自身起取，探头行会成为下一页第一条
    ...(q.cursor ? { cursor: { id: q.cursor } } : {}),
  })
  const hasNext = items.length > q.take
  return { items: items.slice(0, q.take), nextCursor: hasNext ? items[q.take].id : null }
}
```

> ⚠️ **实测踩坑（P0 级，playground 复现）**：`take + 1` 探头与 `cursor + skip: 1` 混用会**静默丢行**——探头行（下一页首条）被当 cursor 传下去后又被 `skip: 1` 跳过，每翻一页丢一条。二选一：要么 `skip: 1` 且 nextCursor 用「本页末条 id」，要么如上「不 skip 且 nextCursor 用探头行」。改完务必用真实数据翻三页验证行数守恒。

决策线：管理后台可跳页 → offset；信息流/无限滚动 → cursor。**软删除**：查询侧统一 `deletedAt: null`——手写遗漏就漏数据，进阶用 Prisma client extension 把过滤内建（见第 5 节）。

## 4. ⚖️ 对比板块：Prisma vs TypeORM vs Drizzle

| 维度 | Prisma | TypeORM | Drizzle |
|------|--------|---------|---------|
| 建模 | schema DSL 单一事实源 | 装饰器实体 | TS 定义 schema |
| 类型安全 | 生成客户端，查询即类型 | 弱（装饰器推导有限） | 强（零代码生成，直连 TS） |
| 迁移 | `migrate` 内建 | 内建但历史包袱 | drizzle-kit |
| 心智成本 | 低（API 面小） | 中（ActiveRecord/DataMapper 双模式） | 中（贴近 SQL） |
| Nest 12 peer | 官方无强绑定，社区成熟 | **peer 滞后**（核对 @nestjs/typeorm 声明） | 无官方包装，手写 Provider 即可 |

选型：默认 **Prisma**（类型安全 + 迁移顺滑，团队上手最快）；需要 SQL 级控制与轻运行时 → Drizzle；存量 TypeORM 项目维持但注意 Nest 12 peer 兼容（大纲版本基线条款）。

## 5. 进阶：数据权限 / 多租户（行级隔离）

RBAC（07 篇）管功能级，行级隔离用 **Prisma client extension** 把租户过滤内建进查询：

```ts
const tenantPrisma = prisma.$extends({
  query: {
    post: {
      async findMany({ args, query }) {
        args.where = { ...args.where, tenantId: currentTenantId }
        return query(args)
      },
      async findUnique({ args, query }) {
        args.where = { ...args.where, tenantId: currentTenantId }
        return query(args)
      },
    },
  },
})
```

- 租户上下文来源：请求作用域——CLS（`@nestjs-cls`）按 AsyncLocalStorage 挂载，02 篇「REQUEST 作用域的替代方案」在此闭环
- 每请求 `tenantPrisma` 的组装在 CLS 的 setup 里完成，Service 无感知——「数据权限不靠自觉」与 01 篇的架构约束思想一致

## 6. ✍️ 练习：文章模块的 Repository 封装

**要求**：

1. `PostRepository` 封装 Prisma 调用（Controller/Service 不直接 import PrismaClient），含 `create / findById / list(cursor) / softDelete`
2. 一个交互式事务：发布文章时同步写 `auditLog`，任一步失败整体回滚（故意抛错验证）
3. cursor 分页返回 `{ items, nextCursor }`，用 curl 连翻两页验证游标衔接
4. 软删除后 `findById` 不可见

**预期效果**：`findMany` 参数里看不到裸 `deletedAt`（藏在 Repository/extension 里）；事务回滚后 auditLog 无残留。

## 7. 💬 面试问答

**Q1：offset 与 cursor 分页怎么选？**

可跳页的管理后台选 offset（实现直、能算总数）；信息流选 cursor（O(1) 翻页、无漂页，代价是只能顺序翻 + 需要稳定有序游标）。深翻页 + 并发写场景 offset 的 skip 是 O(n) 且会漂页。

**Q2：Prisma 事务怎么写？隔离级别什么时候调？**

数组式适合原子批量写，交互式适合带逻辑的事务（能拿中间结果、能抛错回滚）。默认 ReadCommitted 够用；「先读后写」防并发重复优先用唯一约束兜底（幂等），确实不够再调隔离级别——调级别是最后手段。

**Q3：多租户的数据隔离怎么做？**

应用层行级隔离：tenantId 进每张表 + client extension 把过滤内建进所有查询（不靠开发者自觉），租户上下文用 CLS 按请求挂载。强隔离需求（金融）上独立 schema/独立库——成本与隔离度成正比。

## 📌 小结

- PrismaService + `onModuleInit` 连库是官方范式；schema 单一事实源，禁手工改库
- 事务：带逻辑一律交互式；防并发重复「唯一约束 > 隔离级别」
- 分页决策线：可跳页 → offset；无限滚动 → cursor（多取一条判 hasNext）
- Prisma vs TypeORM vs Drizzle：默认 Prisma，注意 Nest 12 peer 滞后的是 TypeORM
- 行级数据权限 = extension 内建过滤 + CLS 租户上下文——不靠自觉靠机制
