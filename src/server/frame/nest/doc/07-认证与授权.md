# 07 认证与授权

> 所属大纲：[readme.md](../readme.md) ｜ 预计：1 天 ｜ 前置：04、06

**一句话定位**：Passport/JWT/RBAC 完整链路——认证（你是谁）归 Strategy，授权（你能不能）归 Guard，外加无状态 token 的登出难题。

**面试可答**：Passport 策略封装认证方式（校验凭证 → `validate()` 返回 user 挂到 request），Guard 做授权决策（RolesGuard 读 `@SetMetadata` 比对角色）；企业默认组合是 access/refresh 双 token + RBAC。

---

## 1. Passport：认证方式的封装层

`@nestjs/passport` 把「凭证校验」抽象成策略类。JWT 策略的完整链路：

```ts
import { ExtractJwt, Strategy } from 'passport-jwt'

@Injectable()
export class JwtStrategy extends PassportStrategy(Strategy, 'jwt') {
  constructor(config: ConfigService) {
    super({
      jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken(),
      ignoreExpiration: false,
      secretOrKey: config.getOrThrow('JWT_SECRET'),
    })
  }

  // token 签名校验通过后进入这里；返回值挂到 request.user
  async validate(payload: JwtPayload) {
    return { id: payload.sub, roles: payload.roles }
  }
}
```

生命周期：`@UseGuards(AuthGuard('jwt'))` → Guard 委托 Passport → 签名校验 → `validate()` → 结果挂 `request.user` → 04 篇的 `@CurrentUser()` 装饰器取用。**Strategy 管「凭证怎么验」，Guard 管「验不验、结果算不算过」。**

## 2. JWT：双 token 设计

| token | 有效期 | 存储 | 职责 |
|-------|--------|------|------|
| access token | 短（15 分钟） | 内存 / Bearer 头 | 每次请求的通行证 |
| refresh token | 长（7~30 天） | httpOnly Cookie 或库表 | 只用于换新 access |

```ts
@Injectable()
export class AuthService {
  constructor(
    private jwt: JwtService,
    private users: UserService,
  ) {}

  async login(email: string, password: string) {
    const user = await this.users.verify(email, password)   // bcrypt 比对
    return this.issueTokens(user)
  }

  private issueTokens(user: AuthUser) {
    const payload = { sub: user.id, roles: user.roles }
    return {
      accessToken: this.jwt.sign(payload),                  // 过期取 JWT_EXPIRES_IN
      refreshToken: this.jwt.sign(payload, { expiresIn: '30d' }),
    }
  }
}
```

**httpOnly Cookie vs Bearer 的取舍**：Cookie（`httpOnly + Secure + SameSite`）防 XSS 窃取、前端零管理，但跨域/小程序/App 不便；Bearer 灵活跨端但 token 落在 JS 可及处。Web 优先 Cookie，多端 API 优先 Bearer——混合方案（refresh 走 Cookie、access 走 Bearer）也常见。

## 3. 登出的真实实现（无状态 token 的天坑）

JWT 签出后服务端无法「作废」——登出必须补状态。三种方案按推荐排序：

| 方案 | 做法 | 取舍 |
|------|------|------|
| **refresh 轮换（推荐）** | 每次换新 refresh 时旧 token 立即失效（库表存版本/指纹，重复使用旧 token 视为泄露 → 全家族吊销） | 有状态但只在刷新时查库；安全性最高 |
| Redis 黑名单 | 登出把 `jti` 写入 Redis（TTL = 剩余有效期），Guard 校验是否命中 | 实现直观；每个请求多一次 Redis 查（可与短 access 期对冲） |
| token 版本号 | 用户表存 `tokenVersion`，签发时写入 payload，登出时 +1 使所有旧 token 失效 | 粒度粗（全端登出）；实现最简 |

```ts
// refresh 轮换核心：重放检测在前，正常轮换只吊销当前 jti
async refresh(refreshToken: string) {
  const payload = await this.jwt.verifyAsync(refreshToken)
  const stored = await this.sessionRepo.find(payload.jti)

  // 重放：旧 jti 已吊销或不存在 → 疑似泄露，吊销全家族
  if (!stored || stored.revoked) {
    await this.sessionRepo.revokeFamily(payload.family)
    throw new BizException('TOKEN_REUSED', '会话已失效，请重新登录', 401)
  }

  // 正常轮换：吊销当前 jti，签发新 token（新 jti 写入会话表）
  await this.sessionRepo.revoke(payload.jti)
  return this.issueTokens({ id: payload.sub, roles: payload.roles })
}
```

> 💡 面试高频：「JWT 怎么登出」的满分答案 = 先说「无状态 token 本质上登不出」，再给三方案与取舍——能说透取舍比背方案加分。

## 4. Guards + RBAC

```ts
// 1) 路由声明角色：@SetMetadata 太裸，封装成 @Roles()
export const ROLES_KEY = 'roles'
export const Roles = (...roles: Role[]) => SetMetadata(ROLES_KEY, roles)

// 2) RolesGuard：读声明 + 比对 request.user.roles
@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private reflector: Reflector) {}

  canActivate(ctx: ExecutionContext): boolean {
    const required = this.reflector.getAllAndOverride<Role[]>(ROLES_KEY, [
      ctx.getHandler(),          // 方法级声明优先
      ctx.getClass(),            // 其次控制器级
    ])
    if (!required?.length) return true
    const { roles } = ctx.switchToHttp().getRequest().user
    return required.some(r => roles?.includes(r))
  }
}

// 3) 使用
@UseGuards(AuthGuard('jwt'), RolesGuard)
@Roles('admin')
@Delete(':id')
remove() {}
```

顺序有两个层次，第二个是实测陷阱：

1. **同一处的声明顺序**：`@UseGuards(AuthGuard('jwt'), RolesGuard)`——Auth 在前写入 `request.user`
2. **全局 vs 路由级**：全局 Guard **恒先于**路由级 Guard 执行——「全局 RolesGuard + 路由级 AuthGuard」的组合下，RolesGuard 执行时 `request.user` 还是 `undefined`（实测 TypeError）。正解：**认证/授权都全局注册**（`APP_GUARD` 数组顺序 Jwt → Roles → Throttler），公开路由（注册/登录/刷新）用 `@Public()` 豁免：

```ts
export const IS_PUBLIC_KEY = 'isPublic'
export const Public = () => SetMetadata(IS_PUBLIC_KEY, true)

@Injectable()
export class JwtAuthGuard extends AuthGuard('jwt') {
  constructor(private readonly reflector: Reflector) {
    super()
  }

  canActivate(ctx: ExecutionContext) {
    const isPublic = this.reflector.getAllAndOverride<boolean>(IS_PUBLIC_KEY, [
      ctx.getHandler(),
      ctx.getClass(),
    ])
    return isPublic ? true : super.canActivate(ctx)
  }
}
```

属性级权限（「只改自己的文章」）进阶用 CASL（`@nestjs/casl`），了解即可。

## 5. ✍️ 练习：完整认证链路

**要求**：实现注册 / 登录 / 刷新 / 登出 + RolesGuard：

1. `POST /auth/register`（密码 bcrypt 哈希入库）→ `POST /auth/login` 发双 token
2. `POST /auth/refresh`：refresh 轮换 + 重放检测（会话表落内存即可）
3. `POST /auth/logout`：吊销 refresh 家族；access token 剩余期靠短有效期自然失效
4. `DELETE /admin/posts/:id` 挂 `@Roles('admin')`，用普通用户验证 403

**预期效果**：全链路 curl 跑通；旧 refresh 二次使用触发全家族吊销；能口头复述第 3 节三方案的取舍。

## 6. 💬 面试问答

**Q1：JWT 双 token 为什么这么设计？**

矛盾是「安全（短有效期）」与「体验（少登录）」。access 短有效期把被盗窗口压到分钟级；refresh 长有效期只在高危端点（刷新）出现，配合轮换 + 重放检测把「长期凭证泄露」变成「可检测、可吊销」事件。

**Q2：Passport 和 Guard 各自的角色？**

Strategy 封装「认证方式」（凭证 → 用户），与框架解耦可换（Local/JWT/OAuth）；Guard 是 Nest 生命周期的准入环节，决定「这次请求带不带上这个用户、放不放进路由」。同一段认证逻辑换 Guard/Strategy 组合即可支持多种登录方式。

**Q3：RBAC 到行级权限还差什么？**

RBAC 管「角色能不能调接口」（功能级），行级（「这条数据能不能碰」）要数据权限：owner 比对、租户隔离——08 篇用 Prisma client extension 按 tenantId 过滤是数据权限的标准落地。

## 📌 小结

- Strategy 管凭证怎么验、Guard 管放不放行、`validate()` 结果挂 `request.user`
- 双 token：access 15 分钟管通行，refresh 30 天管续期；Cookie 防窃 vs Bearer 跨端按端型选
- 登出三方案：refresh 轮换（推荐）> Redis 黑名单 > token 版本号——核心是给无状态 token 补状态
- RBAC = `@SetMetadata` 声明 + RolesGuard 比对；顺序上 RolesGuard 在 AuthGuard 之后
