# 03 模块系统与动态模块

> 所属大纲：[readme.md](../readme.md) ｜ 预计：1 天 ｜ 前置：02

**一句话定位**：读懂所有第三方集成的钥匙——`forRoot`/`forFeature`/`register` 是 Nest 生态的通用契约，学会它就能自己封装基础设施模块。

**面试可答**：Module 是 Nest 的装配单元，`imports/exports/providers` 构成静态依赖图；动态模块（`forRoot` 全局单例配置 / `forFeature` 局部注册 / `register` 每处独立）通过方法返回 `DynamicModule` 把「运行时参数」带进装配图——ConfigModule、BullModule 全是这一模式。

---

## 1. Module 边界：依赖图的三张清单

```ts
@Module({
  imports: [PrismaModule],        // 我需要谁（拿它 exports 的东西）
  controllers: [PostController],  // 谁负责路由（自动注册，无需 export）
  providers: [PostService],       // 谁干活（模块内私有）
  exports: [PostService],         // 我对外提供什么
})
export class PostModule {}
```

三条硬规则：

1. **Provider 默认模块私有**——别的模块要用，必须 `exports`；这正是「模块边界」的物理形态
2. **imports 是显式依赖声明**——禁止「跨模块直接 new」，02 篇的循环依赖问题在模块层同样存在且同解
3. **controller 无需 export**——路由不参与模块间依赖，只有 Service 层才需要跨模块共享

> 💡 判断模块划分好坏的标准：`imports` 清单是否稳定。一个被半个应用 imports 的「上帝模块」和互相乱 import 的「面条模块」是两个方向的坏味道。

## 2. 动态模块三大模式：forRoot / forFeature / register

静态 `@Module()` 没法接收运行时参数（连接串、队列名）。动态模块 = **一个静态方法，返回带参数的装配清单**：

```ts
import { DynamicModule, Module } from '@nestjs/common'

@Module({})
export class RedisModule {
  static forRoot(url: string): DynamicModule {
    return {
      module: RedisModule,                      // 自身也要声明
      global: false,
      providers: [
        { provide: 'REDIS_URL', useValue: url },
        {
          provide: 'REDIS_CLIENT',
          inject: ['REDIS_URL'],
          useFactory: (url: string) => createClient({ url }),
        },
      ],
      exports: ['REDIS_CLIENT'],                // 把连接暴露给业务模块
    }
  }
}
```

生态里三种调用姿势，各有明确语义：

| 模式 | 调用位置 | 语义 | 实例 |
|------|---------|------|------|
| `forRoot(options)` | 仅根模块一次 | 全局单例配置，建立共享连接 | `ConfigModule.forRoot()`、`BullModule.forRoot()`、`GraphQLModule.forRoot()` |
| `forFeature(局部参数)` | 每个业务模块 | 复用 forRoot 的连接，注册局部条目 | `TypeOrmModule.forFeature([Post])` |
| `register(参数)` | 每处独立 | 每次调用独立配置、独立实例 | `BullModule.registerQueue({ name: 'mail' })` |

读第三方文档时的速判法：**名字带 Root = 全局一次；带 Feature = 配合 Root 用；带 register = 各自独立**。`forRoot` 通常还配 `forRootAsync`——从 ConfigService 异步取配置（避免 env 未就绪的时序问题）：

```ts
RedisModule.forRootAsync({
  inject: [ConfigService],
  useFactory: (config: ConfigService) => ({
    url: config.getOrThrow('REDIS_URL'),
  }),
})
```

## 3. 生命周期钩子：启动与关闭的挂点

| 钩子 | 时机 | 典型用途 |
|------|------|---------|
| `onModuleInit` | 依赖解析完成后 | 主动建立连接（如 PrismaService 连库） |
| `onApplicationBootstrap` | 全部模块 init 完 | 需要全应用就绪后的动作（预热缓存、启动消费者） |
| `onModuleDestroy` | 收到关闭信号（需 `enableShutdownHooks`） | 关连接、flush 缓冲 |
| `beforeApplicationShutdown` / `onApplicationShutdown` | 关闭传播完成前后 | 等待在途任务收尾、清理句柄 |

```ts
@Injectable()
export class PrismaService extends PrismaClient implements OnModuleInit, OnModuleDestroy {
  async onModuleInit() { await this.$connect() }
  async onModuleDestroy() { await this.$disconnect() }
}
```

> ⚠️ **v12 行为变化**：钩子改为**按组件层级**调用——多 Provider/模块存在依赖链时，`onModuleInit`、`onApplicationBootstrap` 及 shutdown 钩子的执行顺序可能与 v11 不同。升级存量项目时，凡是对「谁先初始化」有假设的逻辑（A init 时假设 B 已就绪）必须回归测试。来源：[Migration Guide](https://docs.nestjs.com/migration-guide)。
>
> 优雅关闭前提：`app.enableShutdownHooks()`（默认不监听 SIGTERM）——11 篇展开。

**Lazy modules**：重模块（如完整 GraphQL 装配）可用延迟加载推迟到首次使用，加速冷启动——知道有这个开关即可，需要时查官方文档。

## 4. 全局模块与 ModuleRef 联动

- `@Global()` 装饰的模块被根模块 import 一次后，其 exports 全应用可见——适合 ConfigModule 这类真正全局的基础设施；**业务模块禁用**（否则依赖图退化成隐式魔法）
- 02 篇的 `ModuleRef` 在模块语境下还有 `moduleRef.resolve()`（解析 REQUEST / TRANSIENT 作用域实例）与模块级懒加载能力，需要时回查

## 5. ✍️ 练习：自实现 forRoot / forFeature

**要求**：基于第 2 节的 `RedisModule.forRoot(url)`，补一个 `forFeature(db: number)`——为不同业务模块提供「绑定指定 db 的局部客户端」，并让它复用 `forRoot` 建立的连接（不是重新建连）。

**提示**：

- `forFeature` 返回的 DynamicModule 里只注册局部 Provider，工厂参数注入 `'REDIS_CLIENT'`（前提：业务模块 imports 了 RedisModule，且 forFeature 与 forRoot 在同一个 module class 上）
- 验证「复用连接」：两个业务模块各注入局部客户端，`client.options.db` 不同但底层连接数不翻倍

**预期效果**：根模块 `forRoot(6)` + 业务模块 `forFeature(1)` / `forFeature(2)` 各自拿到正确 db 的客户端；能对第三方库的 `forFeature` 用法说出「哦，就是这套」。

## 6. 💬 面试问答

**Q1：forRoot / forFeature 的原理与区别？**

都是静态方法返回 `DynamicModule`（带参数的装配清单）。forRoot 在根模块调用一次，注册全局单例（连接、配置）；forFeature 在各业务模块调用，基于 forRoot 共享的连接注册局部条目（如 Repository/Queue）；register 每次调用产生独立实例。本质都是「把运行时参数带进静态装饰器装不下的装配图」。

**Q2：Nest 的生命周期钩子有哪些？v12 有什么变化？**

init 侧 `onModuleInit` → `onApplicationBootstrap`，destroy 侧 `onModuleDestroy` → `beforeApplicationShutdown` → `onApplicationShutdown`。v12 起钩子按组件层级调用，依赖链上的初始化顺序可能与 v11 不同——对初始化顺序有假设的代码升级时需回归。（追问：优雅关闭怎么开？——`enableShutdownHooks`，11 篇。）

**Q3：为什么业务模块不该用 @Global？**

全局 Provider 让依赖从「显式 imports」退化成「隐式可见」——依赖图无法静态分析，模块边界名存实亡。只有真正全局无争议的基础设施（Config）才配 @Global。

## 📌 小结

- Module 三张清单（imports/providers/exports）就是依赖图的物理形态，Provider 默认私有
- 动态模块三模式：forRoot 全局一次、forFeature 局部注册、register 各自独立——读第三方文档的速判法
- 钩子挂启动与关闭，v12 改按层级调用（升级注意）；`enableShutdownHooks` 是优雅关闭的总开关
- @Global 只留给 Config 级基础设施；业务依赖必须显式 imports
