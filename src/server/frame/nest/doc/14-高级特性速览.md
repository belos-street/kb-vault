# 14 高级特性速览

> 所属大纲：[readme.md](../readme.md) ｜ 预计：0.5 天 ｜ 前置：无硬依赖（可跳读）

**一句话定位**：知道有这些东西、知道何时启用——需要时再回来查，不在主线展开。

**面试可答**：微服务 transport 选型取决于一致性与吞吐需求；CQRS 适合读写分离的复杂域——普通 CRUD 场景是过度设计。

---

## 1. 微服务 transports（选型对照表）

| Transport | 协议 | 适合 | 注意 |
|-----------|------|------|------|
| Redis（pub/sub） | RESP | 轻量解耦、已有 Redis 底座 | 尽力而为投递，可靠性一般 |
| Kafka | 自有协议 | 高吞吐、事件溯源、日志型流 | 运维重；消费组语义要学 |
| gRPC | HTTP/2 + Protobuf | 服务间强类型 RPC、低延迟 | 需 proto 管理；跨语言团队首选 |
| NATS | 自有协议 | 轻量高性能消息、云原生 | **v12 换 NATS v3 包**（`nats` → `@nats-io/transport-node`），自定义序列化行为有变 |

选型钩子：**内部同步调用 → gRPC；事件广播/削峰 → Redis（轻）或 Kafka（重）；超轻量 → NATS。** 单体够用时不要微服务——14 篇全部特性都服从这条总纲。

## 2. CQRS 与事件总线

- **@nestjs/cqrs**：命令写模型、查询读模型分离——适合读写模型差异大、有独立优化诉求的复杂域（订单流转、审批流）。普通 CRUD 上 CQRS 是负资产：概念翻倍换不来任何东西
- **EventEmitter2（@nestjs/event-emitter）**：进程内事件解耦——02 篇循环依赖的「事件解法」就是它；`@OnEvent('user.registered')` 订阅、`eventEmitter.emit` 发布。跨进程才需要消息队列（10 篇 BullMQ）

## 3. GraphQL 与 WebSocket

- **@nestjs/graphql**：resolver + 装饰器生成 SDL；适合「多端字段需求碎片化」的场景。v12 变更：GraphiQL 成默认 IDE、subscriptions 移除 `subscriptions-transport-ws` 改用 `graphql-ws`。REST（+OpenAPI）够用就不上 GraphQL——多一层网关心智
- **WebSocket 网关**：`@WebSocketGateway` 装饰器 + 网关类，v12 支持 disconnect reason 参数；适合实时推送（通知、协作编辑），注意与 11 篇优雅关闭的配合（连接排空）

## 4. 外部调用弹性（一句带过）

调第三方 HTTP API：超时必设、重试带退避、失败降级——封装成 Provider（02 篇 `useFactory`）统一注入。需要专门方案时查 resilience 类库（熔断/舱壁），本课程不展开。

**启用时机总表**：

| 特性 | 等到什么时候再启用 |
|------|-------------------|
| 微服务 | 单体真的拆不动了（团队/部署节奏冲突） |
| CQRS | 读写模型差异大到互相拖累 |
| GraphQL | REST 字段碎片化问题真实发生 |
| WS | 出现真实推送需求 |
| 熔断 | 下游故障真实发生过一次 |

## 5. 💬 面试问答

**Q1：微服务 transport 怎么选？**

同步强类型调用选 gRPC；事件流/削峰按量级选 Redis（轻）或 Kafka（重）；轻量云原生消息选 NATS（v12 换 v3 包）。先问「单体为什么不够」，再谈 transport——微服务是组织问题的技术解。

**Q2：什么时候上 CQRS？**

读写模型差异大、有独立扩缩容/优化诉求的复杂域（订单、审批）。普通 CRUD 上 CQRS 是用架构税买不存在的问题——面试反问「你的读写分离痛点是什么」比背概念加分。
