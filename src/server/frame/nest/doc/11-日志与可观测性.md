# 11 日志与可观测性

> 所属大纲：[readme.md](../readme.md) ｜ 预计：1 天 ｜ 前置：09、10

**一句话定位**：从「console.log 排查」到「trace 一查到底」——结构化日志、两条可观测路线、健康检查与优雅关闭。

**面试可答**：v12 的 @nestjs/observe 是官方托管 SaaS 可观测平台（appKey 直传仪表盘，不走 OTLP）；自托管/本地 Grafana 走 OpenTelemetry SDK——两条独立路线。日志用 pino 结构化输出，request id 全链路贯穿。

---

## 1. nestjs-pino：结构化日志与 request id

```ts
import { LoggerModule } from 'nestjs-pino'

LoggerModule.forRootAsync({
  inject: [ConfigService],
  useFactory: (c: ConfigService) => ({
    pinoHttp: {
      level: c.get('NODE_ENV') === 'production' ? 'info' : 'debug',
      genReqId: (req) => req.headers['x-request-id'] ?? randomUUID(),  // 入口生成/透传
      customProps: () => ({ service: 'kb-api' }),
      transport: c.get('NODE_ENV') === 'production' ? undefined : { target: 'pino-pretty' },
    },
  }),
})
```

- **结构化输出**：生产环境日志必须是 JSON（Loki/ELK 才能查询），本地才用 pino-pretty 美化
- **request id 全链路**：入口生成 → `req.id` 自动进日志 → 透传给下游服务（HTTP 头）/ 队列消息（payload）→ 任何一行日志都能按 id 串起整条链。11 篇之前的排障是「grep 时间戳」，之后是「按 id 一查到底」
- Service 里拿 logger：`PinoLogger` 注入（自动带 request id 上下文），不要用裸 `console.log`
- 版本注记：v12 的「structured params 默认开启」是**内置 ConsoleLogger** 的变化（`logger.log('msg', { a: 1 })` 中对象成为同条目的结构化字段），与 nestjs-pino 无关——别张冠李戴

## 2. 可观测两条路线：@nestjs/observe（SaaS）vs OpenTelemetry（自托管）

### 路线 A：@nestjs/observe（v12 新，官方托管 SaaS）

```ts
// observe.ts
export const { ObserveModule, ObserveInstrument } = createObserveModule()

// app.module.ts
ObserveModule.forRoot({
  appKey: process.env.OBSERVE_APP_KEY!,
  appSecret: process.env.OBSERVE_APP_SECRET!,   // 仪表盘签发，Free 30 万事件/月
  serviceId: 'kb-api',
})
// main.ts
const app = await NestFactory.create(AppModule, { instrument: ObserveInstrument })
```

- 官方托管平台（observe.nestjs.com）：**appKey/appSecret 直传仪表盘**，自动埋点覆盖 controller/provider/队列/cron，trace 以「类.方法」命名（看得见 `OrdersService.recalculate`，不只是 `POST /orders`）
- **不走 OTLP 导出、不能自托管**——遥测只进官方仪表盘，接受托管才有意义

### 路线 B：OpenTelemetry SDK（自托管，本大纲练习主线）

```ts
// instrumentation.ts —— main.ts 的第一个 import（必须在其他模块前启动）
// 服务名经 OTEL_SERVICE_NAME 环境变量注入（新版本 SDK 已移除顶层 serviceName 选项）
import { NodeSDK } from '@opentelemetry/sdk-node'
import { getNodeAutoInstrumentations } from '@opentelemetry/auto-instrumentations-node'
import { OTLPTraceExporter } from '@opentelemetry/exporter-trace-otlp-http'

const sdk = new NodeSDK({
  traceExporter: new OTLPTraceExporter({ url: 'http://localhost:4318/v1/traces' }),
  instrumentations: [getNodeAutoInstrumentations()],
})
sdk.start()
```

```ts
// main.ts 第一行
import './instrumentation'
```

- `@opentelemetry/sdk-node` 直配是主路线：auto-instrumentations 覆盖 HTTP/Prisma/Redis 等，OTLP 导出到自托管 Grafana/Jaeger——**vendor 中立**，数据在自己的存储里
- `nestjs-otel` 是可选的社区包装（注意：**无官方 @nestjs scope**，pragmaticivan 维护，v8.1.1+ peer 已声明支持 Nest 12）——想要 Nest 生命周期级 span 时再上，SDK 直配已覆盖大多数场景

> ⚠️ 两条路线**相互独立、不可互导**：observe 的数据进不了你的 Grafana，OTel 的数据进不了官方仪表盘。选型钩子：**数据主权敏感/已有 Grafana 栈 → OTel；想要零配置开箱即用 → observe**。

## 3. @nestjs/terminus：健康检查（K8s 就绪）

```ts
@Controller('health')
export class HealthController {
  constructor(
    private health: HealthCheckService,
    private prismaIndicator: PrismaHealthIndicator,   // v12：指标返回结果而非抛错
  ) {}

  @Get('ready')
  @HealthCheck()
  ready() {
    return this.health.check([
      async () =>
        this.prismaIndicator.pingCheck('postgres', this.prisma, { timeout: 1000 }),
    ])
  }
}
```

- v12 变化：legacy `HealthIndicator` 基类（抛 `HealthCheckError` 报告不健康）**已移除**，自定义指标改注入 `HealthIndicatorService`，显式返回 `indicator.up()` / `indicator.down()` 或 `attempt()` 包裹
- liveness（`/health`：进程活着）与 readiness（`/health/ready`：依赖就绪可接流量）分开挂——K8s 探针的前提

## 4. 优雅关闭：零停机发布的最后一环

```ts
// main.ts
const app = await NestFactory.create<NestFastifyApplication>(AppModule, new FastifyAdapter())
app.enableShutdownHooks()     // 默认不监听 SIGTERM，必须显式开
await app.listen(3000)
```

关闭时序：K8s 发 SIGTERM → （readiness 探针转不就绪，负载摘除）→ `onModuleDestroy`（停接新请求、关消费者）→ `beforeApplicationShutdown`（等在途请求收尾，设宽限期）→ `onApplicationShutdown` → 退出。03 篇的钩子表在此实战；配合 10 篇「消费者先停再退」避免消息 Nack 重投。

## 5. ✍️ 练习：全链路可观测落地

**要求**：

1. pino 接入：request id 全链路（自己带 `x-request-id` 调用验证透传）
2. OTel SDK 直配 + 本地 Grafana Tempo/Jaeger（docker 起一个），打一次请求看 trace 瀑布（HTTP → Prisma span）
3. 用 @nestjs/observe 接一次官方仪表盘，对比两条路线的取舍（埋点粒度、数据流向、配置成本）
4. terminus 的 liveness/readiness 双探针；`SIGTERM` 后观察优雅关闭日志顺序

**预期效果**：按 id 能查出一次请求的全部日志与 trace；`docker compose down` 触发 SIGTERM 后日志呈现「摘流 → 关消费者 → 连接关闭」的顺序。

## 6. 💬 面试问答

**Q1：@nestjs/observe 和 OpenTelemetry 怎么选？**

两个独立路线：observe 是官方托管 SaaS（appKey 直传、零配置、trace 以类.方法命名，但不走 OTLP 不能自托管）；OTel SDK 是自托管标准（OTLP → Grafana/Jaeger，数据主权在自己手里）。已有可观测栈或数据敏感选 OTel；想要零运维选 observe。

**Q2：request id 链路怎么设计？**

入口（或网关）生成 → pino `genReqId` 统一进日志上下文 → 调下游时透传 HTTP 头 → 投队列时写入消息 payload。没有这条线，微服务排障是「按时间猜」，有了才是「按 id 查」。

**Q3：优雅关闭要做什么、不做会怎样？**

`enableShutdownHooks` 后依次：摘流（readiness 置否）→ 停消费者 → 等在途请求（宽限期）→ 关连接。不做的话 SIGTERM 直接杀进程：在途请求被腰斩（客户端 5xx）、队列消息 Nack 重投、DB 连接泄漏。

## 📌 小结

- 日志两条底线：结构化 JSON + request id 全链路——排障从「猜」变「查」
- 可观测双路线互不导通：observe（SaaS 托管）vs OTel SDK（自托管/vendor 中立）；SDK 直配为主，nestjs-otel 是社区可选
- terminus v12 改 `HealthIndicatorService` 显式返回 up/down；liveness 与 readiness 分开
- `enableShutdownHooks` + 关闭钩子分步收尾 = 零停机发布的最后一块拼图
