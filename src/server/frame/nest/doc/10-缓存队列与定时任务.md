# 10 缓存队列与定时任务

> 所属大纲：[readme.md](../readme.md) ｜ 预计：1 天 ｜ 前置：08、09

**一句话定位**：异步任务三件套——cache-manager 缓存、BullMQ 可靠队列、@nestjs/schedule 定时任务；外加两道生产保险：消费幂等与 Outbox。

**面试可答**：BullMQ 基于 Redis 提供可靠异步任务（重试/退避/延迟/速率/优先级）；重试必然带来重复投递，消费幂等靠幂等键 + 唯一约束兜底；多实例部署时 cron 会重复执行，需分布式锁或 leader 选举。

---

## 1. cache-manager + Redis

```ts
// 动态模块接 Redis —— Nest 12 的 @nestjs/cache-manager 已切 Keyv 体系
// ⚠️ 旧版 cache-manager-redis-yet 的 store 在此会报 Invalid storage adapter（playground 实测），勿用
import { KeyvRedis } from '@keyv/redis'

CacheModule.registerAsync({
  isGlobal: true,
  inject: [ConfigService],
  useFactory: (config: ConfigService) => ({
    stores: [new KeyvRedis(config.getOrThrow('REDIS_URL'))],
  }),
})
```

- 失效策略：TTL 兜底为主；写操作主动失效相关 key（`del` 与 DB 写同事务语义考虑）；复杂联动用「版本号 key」避免广播式删除
- **生产纪律：批量键操作用 `SCAN` 不用 `KEYS`**——KEYS 是 O(N) 全量阻塞，Redis 单线程模型下会卡死所有请求；SCAN 增量遍历不阻塞。这不是优化建议，是红线

## 2. @nestjs/bullmq：可靠队列

```ts
// 根模块：连接（forRoot）—— connection 传 ioredis 实例或 options；
// 注意 options 没有 url 字段，传 { url } 会静默连 localhost，字符串 URL 必须 new Redis()
import Redis from 'ioredis'

BullModule.forRootAsync({
  inject: [ConfigService],
  useFactory: (c: ConfigService) => ({
    connection: new Redis(c.getOrThrow('REDIS_URL')),
  }),
})
// 业务模块：注册队列
BullModule.registerQueue({ name: 'mail' })
```

```ts
// 生产者：入队
@Injectable()
export class MailQueue {
  constructor(@InjectQueue('mail') private queue: Queue) {}
  enqueueWelcome(userId: string) {
    return this.queue.add('welcome', { userId }, {
      attempts: 5,                       // 重试 5 次
      backoff: { type: 'exponential', delay: 1000 },   // 指数退避
      delay: 60_000,                     // 延迟 1 分钟
    })
  }
}

// 消费者：Worker
@Processor('mail')
export class MailConsumer extends WorkerHost {
  async process(job: Job<{ userId: string }>) {
    await this.mailer.send(job.data.userId)
    // 抛错 = 失败 → BullMQ 按 attempts/backoff 自动重试
  }
}
```

要点速记：

- **Job 生命周期**：wait → active → completed / failed；`attempts` 用尽进 failed 集，可配 `removeOnComplete` / `removeOnFail` 控留存留
- **失败告警**：监听队列 `failed` 事件（或 Bull Board 面板），失败静默是队列事故的第一成因
- **速率控制**：`limiter: { max: 10, duration: 1000 }`——保护下游（如邮件商限额）
- **消费幂等（重试的孪生课题）**：重试必然带来重复投递，消费者必须幂等——幂等键（业务唯一键，如 `userId+scene`）+ 数据库唯一约束/Redis `SETNX` 兜底，重复投递时第二次直接跳过：

```ts
async process(job: Job<{ userId: string }>) {
  const idemKey = `mail:welcome:${job.data.userId}`
  const ok = await this.redis.set(idemKey, '1', { nx: true, ex: 86_400 })
  if (!ok) return                    // 已处理过，幂等跳过
  await this.mailer.send(job.data.userId)
}
```

## 3. @nestjs/schedule：进程内定时任务

```ts
@Injectable()
export class ReportTasks {
  @Cron('0 0 6 * * *', { name: 'daily-report', timeZone: 'Asia/Shanghai' })
  async dailyReport() { /* 每日 06:00 报表 */ }

  @Interval('cleanup', 300_000)
  cleanup() { /* 每 5 分钟清理 */ }
}
```

> ⚠️ **多实例部署的分布式锁问题（企业实战高频坑）**：`@Cron` 挂在每个进程上，N 个实例 = 任务跑 N 遍（报表发 N 封、扣款扣 N 次）。解法按推荐排序：① Redis 分布式锁（`SET key NX EX` 抢锁，拿到锁的实例执行）；② 数据库任务表 + 行锁认领；③ 把调度职责从应用剥离到 K8s CronJob / 云调度（架构最干净）。**答案是「锁」之前先想「要不要每实例都跑」。**

## 4. Outbox 引子：DB 写成功但入队失败

09 篇复盘埋的问题：注册事务提交成功，紧接着 `queue.add` 因为 Redis 抖动失败——邮件永远丢失，且无法回滚已提交的 DB 事务。

**Outbox 模式**：把「要发的事件」当成数据写——

1. 业务数据 + outbox 事件在**同一个本地事务**里落库（原子性由 DB 保证）
2. 独立的 relay 进程/定时任务轮询 outbox 表，把事件投递到队列后标记完成
3. 投递是 at-least-once → 消费方幂等兜底（第 2 节闭环）

```ts
await this.prisma.$transaction(async (tx) => {
  await tx.user.create({ data: userData })
  await tx.outboxEvent.create({
    data: { type: 'user.registered', payload: { userId }, deliveredAt: null },
  })   // 原子：要么都成功要么都失败
})
```

15 篇的注册欢迎邮件按此落地。深挖方向（CDC/Debezium）不在本课程范围，知道轮询之外还有这条路线即可。

## 5. ✍️ 练习：邮件队列 + 每日报表

**要求**：

1. `mail` 队列：发送失败模拟（随机抛错）验证指数退避与 5 次重试；加消费幂等（Redis SETNX）
2. `@Cron` 每分钟报表任务 + Redis 分布式锁，起两个实例验证只执行一次
3. 故意停掉 Redis，观察入队报错——体会 Outbox 要解决什么

**预期效果**：重试日志呈现 1s/2s/4s/8s 退避；双实例只有一把锁生效；能口头复述「重试 → 重复投递 → 幂等」与「事务 → 入队 → Outbox」两组因果链。

## 6. 💬 面试问答

**Q1：BullMQ 怎么保证可靠性？**

三段拼图：Redis 持久化保队列本身不丢；attempts/backoff 保证瞬时失败可恢复；失败集 + 告警保证最终失败可见。注意「可靠」不等于「精确一次」——重试带来 at-least-once，幂等是消费者的法定义务。

**Q2：多实例下定时任务怎么去重？**

每个进程都挂 cron，天然重复执行。三种方案：Redis 分布式锁抢锁执行、DB 任务表认领、调度职责外移（K8s CronJob）。优先考虑架构解——应用内调度适合轻量场景，重任务外移。

**Q3：消息队列一定能保证不丢消息吗？**

不能一概而论。DB → 队列之间存在「双写窗口」（本地事务提交后入队失败），Outbox 把事件写入同一事务用轮询/CDC 投递补上这一环；消费侧 at-least-once 配幂等。全链路「不丢」是设计出来的，不是队列自带的。

## 📌 小结

- 缓存 TTL 兜底 + 写时失效；Redis 批量操作 SCAN 是红线不是建议
- BullMQ = 重试退避 + 速率控制 + 失败告警；重试的孪生课题是消费幂等（幂等键 + 唯一约束）
- 多实例 cron 必然重复，锁只是手段，先问「要不要每实例都跑」
- Outbox 解决「DB 成功但入队失败」的双写窗口——事件当数据写，同事务原子落库
