## 1. 单元测试：DI 范式

```ts
import { Test } from '@nestjs/testing'

describe('PostService', () => {
  let service: PostService
  const prismaMock = { post: { findMany: vi.fn(), create: vi.fn() } }

  beforeEach(async () => {
    const moduleRef = await Test.createTestingModule({
      providers: [PostService, { provide: PrismaService, useValue: prismaMock }],
    }).compile()

    service = moduleRef.get(PostService)
  })

  it('创建文章走事务并返回 id', async () => {
    prismaMock.post.create.mockResolvedValue({ id: 'p1' })
    await expect(service.create({ title: 't', content: 'c' })).resolves.toMatchObject({ id: 'p1' })
    expect(prismaMock.post.create).toHaveBeenCalledOnce()
  })
})
```

要点：

- `moduleRef.get(PostService)` 拿到的是**被真实容器组装**的服务——注入路径与生产一致，mock 只发生在边界（Prisma/Redis/HTTP）
- Service 层测试范式：依赖全 mock、验证「输入 → 副作用调用 + 返回值」；Repository/Prisma 的查询正确性留给 E2E
- 02 篇的「可测试性红利」在此兑现：换依赖 = 配置，不是 monkey-patch

## 2. E2E 测试：打真实 HTTP

```ts
describe('POST /posts (e2e)', () => {
  let app: NestFastifyApplication

  beforeAll(async () => {
    const moduleRef = await Test.createTestingModule({ imports: [AppModule] }).compile()
    app = moduleRef.createNestApplication<NestFastifyApplication>(new FastifyAdapter())
    app.useGlobalPipes(new StandardSchemaValidationPipe())   // 与 main.ts 保持同一装配！
    await app.init()
  })

  it('非法 body 返回统一错误格式', async () => {
    const res = await app.inject({ method: 'POST', url: '/posts', payload: { title: '' } })
    expect(res.statusCode).toBe(400)
    expect(res.json().code).toBe('VALIDATION_ERROR')
  })
})
```

- `app.inject()`（Fastify）/ supertest 起**全量应用**打真实 HTTP——验证校验、Guard、Interceptor、Filter 的**装配正确性**（单测验证不了它们）
- ⚠️ 经典坑：E2E 里忘了复刻 main.ts 的装配（全局管道/Guard/hook），测出来的行为和生产不一致——把装配抽成 `createApp()` 工厂函数，main.ts 与 E2E 共用
- ⚠️ 实测坑集（playground 验证）：E2E 跨运行要**清库**（唯一约束残留会让注册接口 500）；多 spec 共享测试库时 Vitest 关 `fileParallelism`（并行写库互相踩）；`*.e2e-spec.ts` 默认不匹配 `*.spec.ts` 的 include，改配置或统一命名

## 3. Vitest：v12 的默认测试栈

| 维度 | Vitest（新 ESM 默认） | Jest（存量 CJS 默认） |
|------|----------------------|----------------------|
| 速度 | 原生 ESM + worker 并行，快 | 转译链路重 |
| 装饰器元数据 | **SWC 插件保留** | ts-jest/babel 插件链 |
| API | `vi.fn() / vi.mock()` | `jest.fn() / jest.mock()` |
| 配置 | vite 生态复用 | 独立配置 |

- **选型关键：esbuild 不支持 `emitDecoratorMetadata`**，esbuild 转译的测试会拿不到构造参数元数据 → DI 解析失败；SWC 插件是保留元数据的正确姿势。这就是「不用 esbuild 系测试」的根本原因
- 迁移清单：换 `vi.fn`、检查 supertest 导入形态（ESM 默认导出）、test script 改写
- 运行时基线：统一 **Node**——Bun 装包/跑脚本没问题，但 bun test 与 `@nestjs/testing`、SWC 装饰器元数据的兼容未充分验证，不作推荐（生产基线同为 Node）

## 4. 构建与工程化工具链

| 工具 | 角色 | 说明 |
|------|------|------|
| tsc | 标准项目默认编译器 | 稳妥，类型检查一步到位 |
| SWC | dev 热重载（start:dev） | 快；元数据靠插件 |
| Rspack | monorepo 打包（v12 CLI 默认） | 替代 webpack；标准项目不必上 |
| oxlint + oxfmt | lint + format | Rust 系，秒级反馈；配置与项目规范一致（单引号无分号） |

```bash
nest build                    # 标准项目 = tsc
nest build --builder rspack   # monorepo 打包
```

## 6. 💬 面试问答

**Q1：为什么说 Nest 的单测容易写？**

DI 的副产品：`Test.createTestingModule` 起真实容器，`.overrideProvider()` 模块级换 mock——被测对象是真实组装的服务，mock 只在边界发生，注入路径与生产一致。对比手工 new + 反射改私有字段的测试方式，稳定性和表达力都高一档。

**Q2：Vitest 跑 Nest 为什么要用 SWC，不能用 esbuild？**

Nest DI 依赖构造参数元数据（`design:paramtypes`），esbuild 不支持 `emitDecoratorMetadata`，转译后元数据丢失 → 容器解析失败；SWC 插件保留元数据。这是选型关键，不是性能偏好。

**Q3：单测覆盖很高还需要 E2E 吗？**

需要。单测验证「单元逻辑正确」，验证不了**装配正确性**——全局管道漏注册、Guard 顺序错、Filter 未挂，单测全绿但线上事故。E2E 起全量应用打真实 HTTP，专门抓这一层。

## 📌 小结

- 单测 = 真实容器 + 边界 mock；E2E = 全量装配 + 真实 HTTP——两者抓的缺陷不同，缺一不可
- 装配抽 `createApp()` 工厂，main.ts 与 E2E 共用——消灭「测试环境行为不一致」的头号来源
- Vitest + SWC 是 v12 ESM 默认栈；esbuild 丢装饰器元数据是硬伤，不是口味问题
- 运行时统一 Node（Bun 装包可以，bun test 不推荐）；构建 tsc 为主，Rspack 属于 monorepo
