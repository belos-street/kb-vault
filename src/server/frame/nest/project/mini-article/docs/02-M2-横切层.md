# 02 M2 横切层 — 实现教程

> 对应：[TODO.md](../TODO.md) M2 ｜ 参考：[doc/05](../../../doc/05-RxJS速通与过滤器拦截器.md)
> 产物：BizException → GlobalExceptionFilter → Transform/Timing/Audit 三个 Interceptor → 全局装配 → 验证点（curl 5/5 PASS）

M2 的目标一句话：**把「每个接口都要写的重复逻辑」收进全局挂点**——成功包装、错误格式、审计、耗时，业务代码一行都不用管。

---

## Step 1：BizException（src/common/exceptions/biz-exception.ts)

```ts
export class BizException extends HttpException {
  constructor(
    readonly code: string,   // 参数属性：自动挂到 this.code
    message: string,
    status: HttpStatus = HttpStatus.BAD_REQUEST,
  ) {
    super(message, status, { errorCode: code })   // v12 machine-readable
  }
}
```

- `readonly code` 参数属性是关键：Filter 侧读 `e.code`——不写这行就是 `undefined`（README 陷阱 #3）
- `errorCode` 进 HttpException 的 response body：v12 的 machine-readable error codes

## Step 2：GlobalExceptionFilter（src/common/filters/global-exception.filter.ts)

三段 normalize，优先级从业务到兜底：

| 异常类型 | code | 来源 |
|---------|------|------|
| `BizException` | `e.code` 透传 | 实例属性（Step 1） |
| 其他 `HttpException` | 无 errorCode 的 400 → `VALIDATION_ERROR`；否则 `HTTP_ERROR` | response body |
| 未知异常（如 `new Error`） | `INTERNAL_ERROR`(500)，message 固定文案 | **堆栈不外泄** |

响应发送用最小结构接口 `JsonResponder`（`status() + send()`）——Express/Fastify 的 Response 都满足，跨 adapter 通用。

## Step 3：三个 Interceptor（src/common/interceptors/）

| Interceptor | RxJS 操作符 | 作用 |
|-------------|------------|------|
| `TransformInterceptor` | `map` | 成功响应包装 `{ code: 'OK', data, message: 'success' }` |
| `AuditInterceptor` | `tap` | 写操作（POST/PATCH/DELETE）落 `auditLog`，**排除 `/api/auth`** |
| `TimingInterceptor` | `tap` | 记录耗时（Nest Logger） |

三个实现细节：

1. **审计排除认证前缀**：`req.url?.startsWith('/api/auth')` 直接 `return next.handle()`（不包装）——register/login 虽是 POST 但无用户上下文（README FR-3）
2. **审计不阻塞响应**：`tap` 里 `void this.prisma.auditLog.create(...).catch(log)`——fire-and-forget，失败仅记日志（审计慢一拍可接受，拖慢响应不可接受）
3. **`req.user?.id ?? null`**：M2 阶段还没有 Guard，`user` 恒为 undefined——写 `?.` 是为 M3 无缝接上（Guard 写入后这里自然有值）

## Step 4：全局装配

```ts
// main.ts
app.setGlobalPrefix('api')
app.useGlobalPipes(new StandardSchemaValidationPipe())   // ← 从 @nestjs/common 导入
// app.module.ts —— 全局注册顺序 = 洋葱层级：先注册的在外层
providers: [
  { provide: APP_FILTER, useClass: GlobalExceptionFilter },
  { provide: APP_INTERCEPTOR, useClass: TransformInterceptor },
  { provide: APP_INTERCEPTOR, useClass: AuditInterceptor },
  { provide: APP_INTERCEPTOR, useClass: TimingInterceptor },   // 最贴 handler，计时最准
]
```

## 实测踩坑（Tier 1 + Tier 2 各一个）

1. **Tier 1**：`StandardSchemaValidationPipe` 的导入来源猜错了（`@nestjs/core`）——编译直接报 TS2305，查官方 Pipes 文档确认从 **`@nestjs/common`** 导出
2. **Tier 2（更有价值）**：M1 曾把 PostRepository 构造参数写成父类 `PrismaClient`，M2 启动时炸出 `Nest can't resolve dependencies of the PostRepository (?)`——**Nest 的 DI 按类引用精确匹配 token**，容器里注册的是 `PrismaService` 这个 token，写父类类型 ≠ 可注入。已收回改为 `PrismaService` 类型（README 陷阱 #8）

> 陷阱 #8 的深层教训：`import type`（类型擦除）与「父类类型当 token」是两个独立问题，前者编译后元数据变 `Function`，后者 token 不匹配——症状相同（启动报 UnknownDependenciesException），病因不同。

## 验证点实测（curl 5/5）

| 请求 | 响应 |
|------|------|
| `GET /api` | `{"code":"OK","data":"Hello World!","message":"success"}` |
| `GET /api/boom`（抛 `new Error`） | 500 `{"code":"INTERNAL_ERROR","message":"Internal Server Error","data":null}` |
| `GET /api/biz-error`（抛 BizException） | 404 `{"code":"POST_NOT_FOUND","message":"文章不存在","data":null}` |
| `POST /api/echo`（`{}`） | 400 `{"code":"VALIDATION_ERROR","message":[...],"data":null}` |
| `POST /api/echo`（`{"name":"mini"}`） | `{"code":"OK","data":{"echo":"mini"},"message":"success"}` |

`/echo`、`/boom`、`/biz-error` 是验证端点，保留到 M5 验收用。
