> 产物：四表 schema → 首次迁移 → PrismaService(v7 adapter) → PrismaModule(@Global) → PostRepository → cursor 验证点（PASS）

M1 的目标一句话：**让应用拥有一层「干净的」数据访问**——schema 是唯一事实源，Repository 封装查询，业务层（M4 的 Service）永远不直接摸 PrismaClient。

---

## Step 1：schema 四表（prisma/schema.prisma）

四张表不是随手建的，每张都对着一个功能需求（FR）：

| 表 | 服务于 | 设计要点 |
|----|--------|---------|
| `User` | FR-1 注册/登录 | `email @unique` 冲突即 409；`passwordHash` 存 bcrypt 结果，永不存明文 |
| `Session` | FR-1 refresh 轮换 | **登出难题的落点**——无状态 JWT 靠它补状态，见下 |
| `Post` | FR-2 CRUD | `deletedAt DateTime?` 软删除；查询靠索引 `[deletedAt, createdAt]` |
| `AuditLog` | FR-3 审计 | 只追加不更新（没有 updatedAt），`userId?` 可空容忍匿名写操作 |

**Session 表的两个关键设计**（07 篇登出三方案的实现基础）：

- `id @default(uuid())` 就是 refresh token 的 **jti**——每次轮换发新 jti、吊销旧 jti，重放检测靠查这张表
- `family` 字段把「同一次登录派生出的整条 token 链」串起来：检测到重放（已吊销的 jti 再次出现）= 可能泄露 → `revokeFamily` 一次吊销全家族。索引 `@@index([family, revoked])` 正好覆盖这个查询模式

**Prisma 关系的强制约束**：`Session.user` / `Post.author` 声明了外键方向，`User` 侧就必须有反向标量列表（`sessions[]` / `posts[]`）——初版 README 漏了 `sessions[]`，migrate 前被 schema 校验拦下。**教训：反向关系字段不是可选项**。

**索引怎么想出来的**：

- `Post @@index([deletedAt, createdAt])`：列表查询恒定 `where deletedAt = null order by createdAt/id`——复合索引按「等值列在前、排序列在后」的顺序排列才能被完整利用
- `Session @@index([family, revoked])`：重放检测的查询是「按 family 找所有未吊销会话」

### 字段修饰符速查（以本项目真实字段为例）

以 `User.id String @id @default(uuid())` 为例拆开读：

- `String` 是列类型；`@id` 是**主键**——唯一标识一行，隐含唯一 + 非空，PostgreSQL 会自动为它建唯一索引（所以「主键」比「索引」语义更强：索引只是查询加速，主键是行的身份证）
- `@default(uuid())` 是默认值：**插入时没提供 id**，由 Prisma 在应用层生成 uuid v4。注意与数据库默认值的区别——uuid() 是客户端生成，数据库列上并没有 DEFAULT（想数据库生成要用 `dbgenerated()`）

全部修饰符对照（都出自本 schema）：

| 修饰符 | 作用 | 项目实例 |
|--------|------|---------|
| `@id` | 主键：唯一标识一行，隐含唯一 + 非空 + 自动唯一索引 | 四表的 `id` |
| `@default(uuid())` | 插入未提供时由 Prisma 生成 uuid v4（应用层生成） | 四表的 `id` |
| `@unique` | 唯一约束：全表不重复，违反即报错 | `User.email`（重复注册 409 的依据） |
| `@default(USER)` / `@default(false)` | 枚举 / 布尔默认值 | `User.role`、`Session.revoked` |
| `@default(now())` | 默认当前时间（由**数据库**生成） | 各表 `createdAt` |
| `@updatedAt` | 每次 UPDATE 自动刷新时间戳，业务代码不用管 | `Post.updatedAt` |
| `?`（类型后缀） | 可空：允许 NULL——`deletedAt` 有值 = 已删除，NULL = 在线 | `Post.deletedAt`、`AuditLog.userId?` |
| `@relation(fields, references)` | 外键声明：`fields` 是本表列，`references` 指向对方主键 | `Session.user`、`Post.author` |
| `[]`（类型后缀） | 关系「多」侧的反向集合，**不落库**，只影响生成的 client 类型 | `User.posts`、`User.sessions` |
| `@@index([...])` | **表级**复合索引（双 `@` 作用于整张表；单 `@` 作用于单个字段） | `Post`、`Session` 的索引 |

记忆锚点：**单 `@` = 字段级，双 `@@` = 表级**；`?` 管可空、`[]` 管集合；`@default` 的三种取值来源——`uuid()/cuid()` 应用层生成、`now()` 数据库生成、字面量直接写死。

## Step 2：migrate dev（数据库侧发生了什么）

```bash
pnpm prisma migrate dev --name init
```

这一条命令做了四件事：

1. 对比 schema 与数据库现状，**生成 SQL**（`prisma/migrations/20260923021527_init/migration.sql`——建表、外键、索引都在里面，可读、可 review、可入库）
2. 在 shadow database 上试跑 SQL 确认无误
3. 应用到开发库，并把迁移记录写进 `_prisma_migrations` 表（这就是 `migrate status` 能看出「哪些迁移没应用」的依据）
4. 触发 `prisma generate`，让 `@prisma/client` 的 TS 类型带上四张表（`prisma.post.findMany` 能自动补全靠它）

此后**改表永远走「改 schema → migrate」，禁止手工改库**——08 篇「schema 单一事实源」的红利：TS 类型、迁移 SQL、数据库三者由一个源头驱动，不存在漂移。

> Prisma 7 注记：连接 URL 已移到根目录 [prisma.config.ts](../prisma.config.ts)（CLI/Migrate 读它），schema 的 `datasource` 只留 `provider`；运行时连接走 driver adapter（见 Step 3）。`pnpm add -D prisma` 会默认拉 8.0.0-rc，务必与 `@prisma/client` 钉同一版本线（本项目 7.10.0）。

## Step 3：PrismaService（src/infra/prisma/prisma.service.ts）

```ts
@Injectable()
export class PrismaService
  extends PrismaClient
  implements OnModuleInit, OnModuleDestroy
{
  constructor(config: ConfigService) {
    super({
      adapter: new PrismaPg({
        connectionString: config.getOrThrow('DATABASE_URL'),
      }),
    })
  }

  async onModuleInit() {
    await this.$connect()
  }

  async onModuleDestroy() {
    await this.$disconnect()
  }
}
```

三处值得停下来理解：

1. **`extends PrismaClient`**：继承让 `PrismaService` 拥有全部 `prisma.user/post/...` API，同时自己又是 Nest Provider——容器可以注入它，业务代码拿到的是「被容器管理的 PrismaClient」。测试时 `.overrideProvider(PrismaService)` 一换即可（12 篇会用到）
2. **v7 的 adapter 是必填**：Prisma 7 移除了 Rust query engine，连接由 driver adapter 承担——`new PrismaPg({ connectionString })`（node-postgres 驱动）。连接串从 `ConfigService.getOrThrow` 拿（06 篇已校验过它的存在与格式，这里 `getOrThrow` 拿不到就炸，属于「不可能发生的双重保险」）
3. **生命周期钩子**：`onModuleInit` 连库（依赖解析完成后自动触发）、`onModuleDestroy` 断开（优雅关闭链路的一环）——03 篇钩子表的第一个实战应用

## Step 4：PrismaModule 的 @Global（src/infra/prisma/prisma.module.ts)

```ts
@Global()
@Module({
  providers: [PrismaService],
  exports: [PrismaService],
})
export class PrismaModule {}
```

- `providers + exports`：模块内创建、对外提供
- `@Global()`：根模块 import 一次后，**任何模块都能注入 PrismaService，无需重复 imports**

> 为什么基础设施敢全局、业务模块不敢？数据库客户端是「上下文无关、全应用共识」的存在——全局它消除的是纯噪音（三十个模块各写一行 `imports: [PrismaModule]`）。业务 Service 全局化则会让依赖图退化成隐式魔法（doc/03 §4 的边界论述）。

`AppModule` 侧只需 `imports: [PrismaModule]` 一行。

## Step 5：PostRepository（src/modules/post/post.repository.ts)

**为什么存在这层**：M4 的 PostService 需要查文章；如果 Service 直接 `this.prisma.post.findMany(...)`，软删除过滤（`deletedAt: null`）就要在每个查询点手写——漏一处就是「已删除文章复活」的事故。Repository 把这类**不变式**收进一层。

构造函数的类型选择：

```ts
constructor(private readonly prisma: PrismaClient) {}
```

注入的实例实际是 `PrismaService`（PrismaClient 的子类，容器管理）——参数声明成父类 `PrismaClient` 的好处：`scripts/verify-cursor.ts` 这类**脱离 Nest 容器的脚本**可以 `new PostRepository(new PrismaClient(...))` 直接复用，不用为了类型硬拉起整个应用。

四个方法：

| 方法 | 说明 |
|------|------|
| `create` | 透传 create；authorId 由上层（M4 的 Controller `@CurrentUser()`）传入，Repository 不猜 |
| `findById` | `findFirst` 而非 `findUnique`——因为 where 里要加 `deletedAt: null`（findUnique 只接受唯一键） |
| `list` | cursor 分页正确版，见下 |
| `softDelete` | 只置 `deletedAt`，不物理删；事务包审计是 M4 Service 的事（09 篇穿层示范） |

**list 的 cursor 实现逐行看**（本项目验证过的最易错点）：

```ts
const items = await this.prisma.post.findMany({
  where: {
    deletedAt: null,                    // 软删过滤是恒定项
    ...(q.keyword
      ? { title: { contains: q.keyword, mode: 'insensitive' } }
      : {}),                            // keyword 可选：展开条件而不是 if/else 两个查询
  },
  orderBy: { id: 'asc' },               // cursor 需要稳定有序字段
  take: q.take + 1,                     // 探头：多取一条判断 hasNext
  ...(q.cursor ? { cursor: { id: q.cursor } } : {}),  // 从 cursor 起取（含），不 skip
})
const hasNext = items.length > q.take
return {
  items: items.slice(0, q.take),
  nextCursor: hasNext ? items[q.take]!.id : null,   // 探头行 = 下一页首条
}
```

⚠️ **两种机制不可混搭**：`take+1` 探头 + `nextCursor=探头行` 时，下一页**不能**再加 `skip: 1`——否则探头行被当 cursor 定位后又被跳过，每翻一页静默丢一条（playground 实测：25 条翻三页只剩 23 条）。等价写法是 `skip: 1` 且 nextCursor 用「本页末条 id」，二选一。验收标准见 Step 6。

`keyword` 过滤用 `contains + mode: 'insensitive'`（PostgreSQL 原生 ILIKE 语义）——README FR-2 的「标题模糊过滤」。

## Step 6：验证点（scripts/verify-cursor.ts）

```bash
pnpm exec tsx scripts/verify-cursor.ts
```

**为什么值得为它写脚本**：cursor 丢行是**静默错误**——编译器、类型检查、甚至「跑通不报错」的测试全抓不到，只有「断言行数守恒」能抓（doc-quality-reviewer §2.6 的核心论点）。脚本三段式：

1. **清场**：按外键依赖顺序 deleteMany（auditLog → session → post → user）
2. **造数**：1 个 ADMIN 用户 + 25 条 `post 01`~`post 25`
3. **翻页断言**：循环调 `repo.list({ take: 10, cursor })` 直到 `nextCursor === null`，收集全部 id → 断言 `collected.length === 25 && unique.size === 25`

实测输出：

```
pages=3 collected=25 unique=25 expect=25
PASS ✅ 行数守恒、无重复
```

- `pages=3`：10 + 10 + 5，末页 5 条且 nextCursor 为 null——**分页终点正确**
- 这个脚本留在 `scripts/` 里作为**回归工具**：以后改任何查询逻辑，重跑一次就知道有没有把分页改坏（12 篇正式测试栈进场后，它会被收编为 spec）
