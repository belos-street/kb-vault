## 速查总表：症状 → 手段

| 症状 | 手段 | 原理一句话 | 成本 |
|------|------|-----------|------|
| 多轮对话里「它怎么部署」搜不到 | 指代消解改写 | 用对话历史把代词/省略补成独立问题 | 1 次 LLM 调用 |
| 一个 query 有多种问法，单次召回不全 | Multi-Query | LLM 生成 N 个变体分别检索后合并 | N 路检索 + 融合 |
| query 和文档「词汇 gap」大（口语问专业库） | HyDE | 先让 LLM 编一个假设答案，拿答案的向量去搜 | 1 次 LLM + 1 次编码 |
| 问题太细，检索器需要上位概念 | Step-Back | 先抽象出上位问题检索，细节问题自己答 | 1 次 LLM 调用 |
| 简单寒暄也走全量检索 / 多库选错 | 查询路由 | 先分类：直答 / 走 RAG / 走哪个库 | 1 次轻量分类 |
| 上下文塞太满、token 贵 | LLMLingua 压缩 | 小模型删冗余 token，可达 2~20 倍压缩 | 一次小模型推理 |
| 上下文里一半是无关句子 | 抽取式压缩 | 按句子粒度只留与 query 相关的句子 | 一次 embedding/小模型 |
| 答案明明检回了 LLM 却没用上 | 摆放调整 | lost-in-the-middle：最相关的放开头结尾 | 零成本重排 |

> 💡 使用纪律：**按症状开，不默认全开**。每开一道工序 = 多一次 LLM/模型调用 = 延迟与成本上浮，先用 00 篇归因框架确认病灶在这里。

## 各手段要点

### 检索前：把 query 变好

**改写（Rewrite）**——多轮场景的必选项。模板思路：

```text
系统提示：根据对话历史，把用户的最新问题改写成一个不依赖上下文、
可独立检索的完整问题。只输出改写后的问题。
用户历史：… 最新输入：「它怎么部署」
期望输出：「Qwen3-Embedding 模型如何私有化部署」
```

**Multi-Query**——生成 3~5 个变体（同义/换视角/拆解），各自检索后用 RRF 合并。适合「一个问题多个命中角度」的语料。

**HyDE（Hypothetical Document Embeddings）**——query 和 doc 在向量空间不对称时（问题短、答案长），先让 LLM 写一段「假答案」，用假答案的向量去搜真文档：**答案与答案在空间里更近**。失效场景要记牢：query 含精确词（型号/错误码）时假答案可能把这些词编丢，反而不如直搜——所以 HyDE 适合与直搜并联，不是替换。

### 检索后：把上下文变精

**压缩**——LLMLingua 用小模型判断 token 重要性做删除（论文报告 2~20 倍压缩、复杂推理任务上保真）；更稳妥的替代是抽取式：句子级 embedding 相关分过滤。选择顺序：**先抽取式（便宜可控），不够再上 LLMLingua**。

**摆放（lost in the middle）**——LLM 对长上下文中间部分注意力弱（论文实测 U 形曲线）。零成本策略：**rerank 之后按相关分「头尾放最相关、中间放次相关」**再喂 LLM。

## 最小对比脚本（速查形态）

```ts
// rewrite-compare.ts —— 改写前后检索对比的流程骨架（LLM 调用按项目替换）
const retrieve = (q: string) => hybridSearch(q, { topK: 10 }) // 04 篇的混合检索
const llm = (p: string) => chat({ prompt: p })                // 项目现有 LLM 封装

const rewrite = (history: string[], q: string) =>
  llm(`根据对话历史，把最新问题改写成可独立检索的完整问题，只输出问题。
历史：${history.join('\n')}\n最新输入：${q}`)

// 同一 query，改写前 vs 改写后各检索一次，对比 gold chunk 是否进 top-10
const raw = await retrieve('它怎么部署')
const better = await retrieve(await rewrite(['在聊 Qwen3-Embedding 模型'], '它怎么部署'))
// gold：评测集的 gold chunk id（构造方式见 01 篇 §4 评测流程）
console.log('改写前命中:', raw.includes(gold), ' 改写后命中:', better.includes(gold))
```

## 练习（一段式）

**要求 + 提示 + 预期**：挑 5 条多轮对话 query（含指代、省略、口语化），跑 §「最小对比脚本」的改写前后对照，记录命中变化；再对其中 2 条含精确词的 query 追加 HyDE 对照，验证「HyDE 丢精确词」的失效场景。预期产出：一张「query 类型 × 手段 × 命中变化」表，能说出你的项目该默认开哪道工序、哪些留给路由判断。
