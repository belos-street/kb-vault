# Kern（Agent Kernel）架构评审报告

> **评审日期**：2026-11-02
> **评审对象**：`readme.md` + `doc/01`–`doc/10`
> **证据范围**：仅设计文档；未读源码，未跑基准，未验证外部框架内部实现。
> **评审立场**：独立评审，不假设设计正确；只基于文档证据。外部事实（LangChain / LangGraph / Bun / Zod 行为）未在文档中给出源码或版本位置的，标为「未验证」。
> **结论**：**Conditional Go**（有条件通过）

---

## 0. 结论摘要

- **Conditional Go**：定位成立，但协议还没有定死；先修 2 个 P0 与 K-04 / K-05 / K-06 三个协议级 P1，再开 v0.1。
- 两个 P0 会阻断现有计划：`wrapModelCall` 的 Promise 洋葱包不住流式 Provider；`Sandbox.execute(code)` 无法执行 bash。
- 一个 P1 是核心数据模型硬伤：保存点③不持久化 assistant `tool_use`，恢复后 `tool_result` 没有配对。
- 另一个 P1：保存点③不能防止「执行中被 kill」的副作用工具重放，「不重复执行」的承诺不成立。
- v0.2b 是最可能弃坑的版本：SQLite + OTel + todo + compaction + 审批同时上。
- T1–T8 目前不可测：缺 fixture、断言格式、崩溃注入点，以及 token / turn 上限的具体值。
- ≤10 文件可行，≤200 行偏紧；Zod → JSON Schema 的依赖归属未定，「core 仅依赖 Zod」有漏洞。
- 最值得保留：core / plugins / harness 的硬边界、`PendingCall` + 五保存点、用 T 任务集替代「能聊天」。

## 3. 分维度分析

### 3.1 定位与边界（4/5）

- 「single-agent runtime core，不是 workflow runtime」在 readme、01、10 三处一致；10 明确把图 / DAG / 多 Agent 放到 L3，且 core 不 import。这是本设计最扎实的部分。
- 唯一实质渗漏是 `awaiting-approval`：它是工具级 HITL，不是图节点闸门，放在 core 可以接受；但文档没有写下这条区分规则。建议补一句「core 只支持 tool-call 级审批；任何 turn / node / 多阶段闸门属于 graph」。
- harness 野心过大：09 列了 2.1–2.9 九个组件，还保留 TUI 开放问题。它不在 core，但它决定了 v0.2b–v0.4 的范围压力（K-25）。
- 「看起来分层、实际耦合」出现在 `ToolContext`：`userId` / `permissions` 是 harness 概念，core 却负责构造（K-16）。其余依赖方向（core 只依赖接口、插件不互相 import）是清楚的。

### 3.2 架构效率（3/5）

- 抽象有真实用例支撑：Loop、事件、钩子、Provider、工具、Checkpointer 都能对应到 T1–T8；`PendingCall` 和五保存点不是凭空设计，而是针对「副作用工具重放」和「部分完成」的现实问题。
- `onX / transformX / wrapX` 三分法清楚，职责基本不重叠。缺口是：resume 生命周期、工具进度通道、按钩子的 `critical`。这三个缺口会在 v0.2 / v0.3 暴露（K-03 / K-06 / K-11）。
- 事件协议对单本地消费者够用；`onEvent` 覆盖 telemetry。单消费者不是 v0.1–v0.3 的瓶颈。真正的成本是 `onEvent` 背压（K-19），以及 SSE 多客户端 / 断线重连需要 server 层补（K-29）。
- 工具管线「校验 → wrap → execute → transform → 回填」自洽；并发分组、超时、错误归一都有考虑。未定的是审批与并发批次的交互：一批工具里有一个 ask，其他工具是否先执行？文档没有写。
- Checkpointer 的五个保存点方向正确，但状态模型有两个硬伤：③ 缺 assistant `tool_use`（K-04）、③ 不能防止执行中重放（K-05）。这不是抽象错，是实现语义错。
- 插件协议静态注册、`dependsOn` 拓扑、`services` 注册表都合理；`dispose` 顺序（K-17）和插件级 `critical`（K-11）是生命周期缺口。

### 3.3 合理性与一致性（2/5）

跨文档冲突不是措辞问题，而是会直接变成实现分歧的协议问题：审批事件缺位（C-1）、abort 语义（C-2）、观察钩子能否写状态（C-3）、T3 并发验收（C-4）、回放是否硬要求（C-5）、dispose 顺序（C-6）、compaction 版本（C-7）。2.5 列出 11 处，其中 C-1 / C-2 / C-3 / C-9 / C-11 直接涉及 v0.1 冻结的协议。给 2 分不是因为文档写得差，而是因为「协议先行」的承诺与文档现状不一致。

### 3.4 轻量性（3/5）

- core 仅依赖 Zod 在类型层成立；但 `ToolDefinition`（Zod）→ `ToolSpec`（JSON Schema）的转换归属没有定，`zod-to-json-schema` 可能成为第二个依赖（K-12）。这是「零依赖」唯一的实质漏洞。
- v0.1 单包、v0.2 monorepo 的时机合理：v0.2a 要引入 sandbox、文件工具、harness，包边界开始有产品意义。Bun workspaces 本身成本低，缺的是机械化边界检查（K-26）。
- `Bun.serve` vs Hono：单端点 SSE + resume 用 `Bun.serve` 足够；Hono 的价值在路由、中间件、鉴权、OpenAPI，不在性能。文档没有过度贬低 Hono，判断公平。SSE 的 replay / 多客户端属于 server 包，不应进 core。
- Bun + TS 对本地 coding agent 足够；Rust / Go 现在不需要。未来可选场景：高并发 SSE 网关、CPU 密集解析 / 向量检索、海量 trace 聚合、容器编排。这些不进 core，作为旁路服务即可。
- 10 篇文档本身不算过重，但有重复：01 §4 与 02 §3、06 §2.1 与 02 §3、09 §1/§2.3 与 02/03 都在重述同一协议。维护成本会随版本增长；「文档回写」是必要的，但也是额外负担。
- ≤10 / ≤200 的约束互相挤压，详见 3.8 Q1；这是「设计纪律」与「自我束缚」混合，不是纯粹的优点。

### 3.5 可落地性（2/5）

- v0.1 的五步执行顺序是全文最可落地的部分：先定接口，再跑裸 loop，再加钩子，再加 checkpointer，最后套 CLI。T0 有明确载体（天气 Agent）。
- 但两个 P0 直接卡住计划：v0.1 步骤 3 的 model-retry 验收依赖 `wrapModelCall` 的流式签名（K-01）；v0.2a 的 bash 依赖 Sandbox 的命令形态（K-02）。
- 高风险技术点中，文档已经覆盖：流式工具调用聚合、`tool_use / tool_result` 配对、压缩成对删除、Bun × OTel、node-pty、MCP schema。仍然缺：`length` 截断时的 partial tool call（K-27）、审批暂停（K-06）、崩溃恢复的入口（K-07）、消费者退出（K-14）。
- 「文档里优雅、代码里难写」的具体位置：`wrapModelCall` 包流、`wrapToolCall` 内暂停审批、工具进度事件、Sandbox 命令模式、checkpoint 配对。这五处不是实现细节，是接口设计问题。
- T1–T8 的验收不可测（K-13）；这不是「加测试」的问题，是缺任务清单格式和崩溃注入矩阵。

### 3.6 对照公平性

- Vite / Koa 的对照公平：文档明确说「借鉴命名与组合模型」，没有声称等价；`enforce` 的取舍也写清楚了。
- LangChain v1 middleware 的对照部分公平：retry / HITL / PII / todo 的落点能对应上；但文档没有给版本、源码位置或行为证据，`createAgent` 内部循环、`streamEvents` v2 的映射属于「未验证」。
- LangGraph 的边界讲清楚了：core 不做图，Kern Graph 独立包。对照表在「生命周期 / 状态 / 中断 / 恢复」上是公平的；但在恢复能力上低估了 LangGraph 的 checkpointer（它存 channel values + pending writes，支持 time travel），文档只写「图状态 + pending writes」，没有写分支 / 回滚成本。这不是致命问题，但对照表应补一列「代价 / 适用条件」。
- Claude Code / DeepAgents 的对照是产品形态级，不是 API 级；「harness 本质」判断成立，但没有逐项比较 prompt 装配、工具 UX、权限策略。作为学习提纲够用，作为公平对照不够。
- 真正的差异化：core 可删插件、零依赖、显式 `PendingCall` + 五保存点、`transformEvent` 在 `onEvent` 之前、用 T 任务集替代「能聊天」。重复造轮子：Provider 适配、tool schema 转换、retry、todo、compaction、HITL、OTel、MCP 桥。对学习项目来说重复是合理的，但对照表应加一列「为什么自研：学习 / 差异化 / 别无选择」，否则读者会把重复当创新。
- Kern Graph 的独立包方案成立；但 10 §3.3 说「`resume()` 节点 / 工具级 HITL」偏乐观：core 的 `resume` 是 run 级续跑，graph 需要 node 级 interrupt 与自己的图状态。10 §7 已把这个列为开放问题，方向是对的，不要把它写成已可复用。

### 3.7 文档质量（3/5）

- 优点：状态行、开放问题、决策记录（`[x] 已定`）、风险表、文档回写机制、三问笔记，这些让文档可评审、可收敛。多数设计稿没有这些。
- 缺点：状态标签不统一（索引「草案」vs 正文「v2」）；3 处死链；「项目 04」链接指向不存在的项目；核心类型（`RunContext` / `ToolCall` / `Usage` / `ToolSpec`）没有定义（K-15）；至少 7 处跨文档冲突没有裁决（2.5）。
- 「文档先行」没有变成「文档膨胀」，但已经接近：09 / 10 是提纲，却进入了路线图承诺的讨论；01 / 02 / 03 / 06 重复描述同一时序。建议保留 01 / 02 / 03 / 05 / 06 五篇权威，09 并入 08，10 缩成一页边界备忘。

### 3.8 重点必答（10 问）

**1. 这套内核是否真的能控制在 10 文件 / 200 行？列出预计模块和风险。**

估算（未读源码，仅按文档职责）：

| # | 模块 | 内容 | 估算行数 | 200 行风险 |
| --- | --- | --- | --- | --- |
| 1 | `index.ts` / `runtime.ts` 出口 | `createRuntime`、`stream` / `resume` / `close` | 30 | 低 |
| 2 | `protocol.ts` | `Message` / `ContentBlock` / `ToolCall` / `ToolSpec` / `Usage` / `RunState` / `PendingCall` / `RunContext` / `Checkpointer` / `ModelProvider` / `KernelPlugin` | 300+ | 高 |
| 3 | `errors.ts` | 错误类与归一 | 70 | 低 |
| 4 | `hooks.ts` | 钩子类型、`compose`、transform 管道、`enforce`、`critical` | 220 | 高 |
| 5 | `events.ts` | 信封、seq、`transformEvent` / `onEvent` 分发 | 100 | 低 |
| 6 | `loop.ts` | 状态机、`finalize`、checkpoint、abort | 260 | 高 |
| 7 | `tools.ts` | 校验、调度、超时、错误归一、`AnyTool` | 260 | 高 |
| 8 | `runtime.ts` | 插件注册、setup / dispose、拓扑、thread 锁、checkpointer 胶水 | 320 | 高 |
| 9 | `state.ts` | 初始化、迁移、clone、保存点 | 140 | 中 |
| 10 | `config.ts` | limits、logger、默认值 | 80 | 低 |

**2. 钩子清单是否完备？缺哪个会导致 v0.2 / v0.3 返工？**

不完备。缺四类：

- **resume 生命周期**：`onRunResume` / `onRunSuspended`（或 `onRunStart` 带 `isResume` 标志）。T7 重启后，OTel span、临时目录、沙箱连接等 per-run 资源需要重新建立；没有这个钩子，插件只能在 `onEvent` 里猜。
- **工具进度通道**：`ToolContext.emit` + `tool-output-delta`。这不是「钩子」，但没有它，bash 流式 stdout 无法进入 TUI / SSE（K-03）。
- **按钩子的 `critical`**：插件级 `critical` 让预算插件和 telemetry 绑死（K-11）。没有它，预算熔断和 telemetry 容错不能同时成立。
- **钩子超时**：`transformInput` / `wrapModelCall` 没有超时或 `AbortSignal` 约束；一个挂死的插件会挂住整个 run。至少给 hook 一个可配置 timeout，或在 `RunContext` 暴露 signal。

`onAfterModelCall` 可以并入 `wrapModelCall` 的后置段，不算缺口。`onRunEnd` / `onError` 对正常结束够用；崩溃时不会触发，这是预期行为。

**3. 五保存点是否足以覆盖 HITL、崩溃恢复、并发工具和 abort？**

不够。缺口按场景：

- **HITL**：③ 只存 `pendingToolCalls`，不存 assistant `tool_use`，恢复后 `tool_result` 无配对（K-04）；审批决策本身也没有落盘，恢复会重新问一次。需要 `PendingCall.approval` 或在 `RunState` 加 `approvals`。
- **崩溃恢复**：`running` 状态没有恢复入口（K-07）；执行中的工具仍为 `pending`，会重放（K-05）。需要 `running` + `attemptId` + `replayPolicy`。
- **并发工具**：④ 每个完成都落盘，顺序正确；但「一批里一个 ask」没有定义：其他工具先执行还是整批暂停？需要一条批次规则。
- **abort**：消费者 `break` / SSE 断连不经过 catch，也不经过 finally，⑤ 不执行（K-14）。需要 `try/finally` 或 runtime 外层包装。
- **成本**：④ 每次写整份 `RunState`，T3 多文件编辑会产生多次全量写；本地可以接受，但应在文档里承认这是用写放大换恢复粒度，不要写成零成本。

**4. `AsyncGenerator` 单消费者是否会在 TUI / telemetry / SSE 场景受限？**

在 v0.1–v0.3 的单本地 CLI 场景不受限：telemetry / 日志走 `onEvent`，TUI 是唯一外部消费者。受限的是两个场景：

- **TUI + Web SSE 同时消费同一条 run**：一个生成器只能有一个外部消费者；需要 server 层的 broadcast / ring buffer。
- **SSE 断线重连**：`resume` 是 run 级续跑，不是事件流重放；客户端会丢中间事件。需要 `seq` + `Last-Event-ID` 的 replay buffer，属于 server 包。

结论：不要在 core 加事件总线；把「多客户端 / replay」明确划给 server 包。core 保持单消费者是对的。但要把 `onEvent` 的非阻塞写进协议，否则 telemetry 会变成生产者的背压（K-19）。

**5. v0.2 monorepo 是否过早？包边界能否被机械 enforce？**

不过早。v0.2a 要引入 sandbox、文件工具、harness，包边界开始对应产品承诺（插件可独立删除）。Bun workspaces 的脚手架成本低，收益是 smoke 脚本和依赖方向可见。

但「能否机械 enforce」目前是否定的：08 §6 只列了「插件独立性 smoke」，没有 import 边界检查，也没有 `tsc --noEmit`。Bun workspace 的提升可能让未声明依赖在本地通过。需要补 `check-boundaries`（core 禁止 import plugin / harness / server；插件禁止互相 import）和干净安装 CI。否则 monorepo 只是目录拆分，不是架构约束。

**6. Bun + TS 有哪些隐藏坑？哪些场景必须 Node / 原生模块 / Rust / Go？**

现在需要处理的：

- **Bun 不做类型检查**：`bun run` 只 strip 类型，TS strict 必须靠 `tsc --noEmit`（K-26）。
- **Bun × OTel SDK**：文档已列为风险；若 exporter 依赖 Node 原生模块，最稳的是降级为 HTTP exporter 或旁路 collector。
- **`Bun.spawn` 的 kill 语义**：文档没有进程树策略；bash / 测试进程可能留下子进程（K-21）。Windows 上还要确认 shell（Git Bash / WSL / PowerShell）与信号行为。
- **`bun:sqlite`**：只适合 Bun；如果未来要嵌 Node 20，checkpointer 需要换实现（插件化已覆盖）。
- **Zod → JSON Schema**：`zod-to-json-schema` 的版本兼容是已知风险；Zod 4 若已内置 `z.toJSONSchema`，可以消掉这个依赖（需验证版本）。
- **Bun workspaces**：未声明依赖 / hoisting 的隐性通过，靠干净安装 CI 抓。

必须 Node / 原生模块 / Rust / Go 的场景：高并发 SSE 网关（Go / Rust 可选）、CPU 密集解析 / 向量检索（Rust / 原生库）、海量 trace 聚合（旁路服务）、node-pty TUI（Node 原生模块，Bun 兼容性未验证）。这些都不进 core；现在不需要。

**7. T1–T8 / W1–W6 的验收是否可测？缺哪些 fixture 和断言？**

T1–T8 目前不可测。它们只有四要素的名称，没有格式和值。缺：

- **fixture 仓库**：固定 commit / 文件树，T1 读哪个文件、T2 改哪个文件、T3 重构哪几个文件。
- **模型录制**：每个任务的 SSE fixture id；若用真实模型，需要 seed / temperature / 重试策略，否则不可复现。
- **工具序列断言**：精确顺序还是子序列？允不允许模型换工具（read → grep）？
- **结果断言**：最终文件 diff、测试退出码、答案关键句；不能只看「有回答」。
- **预算断言**：max turns、max input / output tokens、max wall time；具体数值。
- **崩溃注入**：T7 只测审批中断，缺「执行中 kill」「第一个工具完成后 kill」「审批通过后、执行前 kill」。
- **checkpoint 不变量**：终态 `pendingToolCalls` 为空；每个 `ToolMessage` 有配对 `tool_use`；没有重复 `tool_result`。
- **审批日志**：T5 要断言「拦截 → 请求 → 允许 → 执行」，不只是最终执行。

W1–W6 是提纲，W3 的 fan-out / fan-in 合并语义未定义，W5 需要 graph checkpointer。10 明确不承诺，暂时不按承诺验收；一旦进 v0.4 spike，需要单独的任务清单。

**8. 与 LangChain / LangGraph 的对照是否公平？哪些是自研优势，哪些是重复造轮子？**

公平的部分：Vite / Koa 的命名与组合模型、LangGraph 的「图外置」边界、Claude Code / DeepAgents 的 harness 定位。这些是结构对照，不是功能等价声明。

不够公平 / 未验证的部分：LangChain v1 middleware 的具体行为、`createAgent` 内部循环、`streamEvents` v2 的粒度映射，文档没有给版本和源码位置；LangGraph checkpointer 的恢复能力被简化成「图状态 + pending writes」，没有展开 channel values、time travel、分支成本的代价。建议补一列「对照版本 / 证据 / 代价」。

自研优势：core 可删插件、零依赖、显式 `PendingCall` + 五保存点、两级出站顺序、T 任务集验收。重复造轮子：Provider 适配、schema 转换、retry、todo、compaction、HITL、OTel、MCP 桥。对学习项目，重复是合理的；但要在每行标「为什么自研」，否则简历读者会把「重复实现」当成「架构判断」。

**9. 「学习 + 简历」的定位是否导致过度设计或功能堆叠？**

core 没有过度设计；过度在 harness 和路线图。证据：

## 4. 三个视角结论

### A. 学习项目：能帮助理解 Agent 框架的设计动机吗？

能，但有前提。这套文档把「为什么不用图」「为什么保存点要在工具派发前」「为什么事件先于异常」写成了可检验的决策，而不是功能清单；对照笔记的三问（差异 / 它为什么那样设计 / 我什么时候会输）是比代码更值钱的产出。

前提是：先做两个 spike，再开 v0.1。第一个是「流式 Provider + 异步生成器中间件 + 零 chunk 重试」；第二个是「审批暂停 + checkpoint 恢复 + `tool_use` 配对」。这两个 spike 会逼出 K-01、K-04、K-06，也是整个框架最难的部分。如果不做，v0.1 会变成「调试自己的框架」，学习曲线从「理解设计动机」变成「修自己造的 bug」。

### B. 工程作品 / 简历：足以证明架构判断力，而不是功能堆叠吗？

有条件地足够。文档已经展示了判断力：core / plugins / harness 的边界、拒绝图进 core、五保存点、错误模型、依赖方向、T 任务集。这些比「我实现了 9 个组件」更能说明问题。

但作品化的门槛是「跑通 + 可验证」：v0.1 + v0.2a 跑通 T1–T4，附 trace、回归 fixture、对照笔记，才足以证明；如果停在 10 篇文档 + 9 个 harness 组件，读者会把它归为「设计文档型项目」。简历上最值得写的是「我拒绝了什么、代价是什么、怎么验收」，而不是组件数量。

### C. 真实可用：能否在本地 coding agent 场景稳定跑起来？

v0.1 天气 Agent 可用；v0.2a 的 read / edit / bash 在本地仓库可以跑，但「稳定」要打折：

- 审批协议未完成，`ask` 只能默认拒绝；无人值守 / 自动批准不可信。
- 崩溃恢复有 K-04 / K-05，kill 后可能重复执行副作用工具。
- L1 沙箱不隔离文件系统和网络，cwd 内 `.env` 可读；不能把它当安全边界。
- Windows 下的 shell、进程树、信号行为未定义。
- 压缩在 v0.2b 交付但 T6 在 v0.4 才验收，长会话稳定性没有回归。

结论：可以作为「有人看着的本地 coding agent」使用，配合 `safe` preset、git 作为 undo、敏感文件不在 cwd；不能作为生产级或无人值守 agent。这不是要求生产 SLA，而是文档承诺的恢复 / 审批语义还没有兑现。
