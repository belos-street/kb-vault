# 10 — 扩展能力与编排层

> **状态**：提纲 · 非当前里程碑承诺（v1.0 后评估）
> **定位**：回答「core 之后能长什么、长在哪一层、依赖方向如何」，防止把工作流编排塞进 core
> **关联**：[01-总体架构设计](01-总体架构设计.md) · [02-核心循环与事件系统](02-核心循环与事件系统.md) · [03-插件系统与钩子设计](03-插件系统与钩子设计.md) · [06-状态与记忆管理](06-状态与记忆管理.md) · [08-路线图与里程碑](08-路线图与里程碑.md) · [09-harness层设计](09-harness层设计.md)

## 1. 边界：core 是单 Agent 运行时，不是工作流引擎

- core 的一次 run：输入 → 模型调用 → 工具执行 → 结果回填 → 终止。
- core 的职责：Agent Loop、事件分发、钩子管线，以及 `RunState` / `Checkpointer` **契约**（接口在 core，存储在插件）。
- core 不负责：图 / DAG 调度、多阶段闸门、多 Agent 协作、工作流状态机、UI / TUI、MCP 网关、技能市场。

| 层 | 职责 | 例子 | 依赖 |
| --- | --- | --- | --- |
| L0 core | 单 Agent run | Loop / Event / Hooks | 仅 Zod |
| L1 plugins | 能力实现 | Provider / 工具 / Checkpointer / 沙箱 / OTel | core 接口 |
| L2 harness | 把 core 装配成 coding agent | 文件工具、bash、审批策略、压缩、preset | core + plugins |
| L3 orchestration（未来） | 确定性编排 | `Kern Graph`（`@kernjs/graph`，节点 / 边 / 状态 / 闸门） | core 公开 API |
| L4 app | 业务 Agent / 具体工作流 | 客服、PRD 工作流、数据分析 | L2 / L3 |

铁律：依赖只能自上而下；core 不 import L1–L4；L3 不 import core 内部实现。

## 2. 为什么图编排不能进 core

| 维度 | core 的单 Agent run | 图编排层 |
| --- | --- | --- |
| 生命周期 | run / turn / tool call | node / edge / superstep |
| 状态 | 消息历史 + `pendingToolCalls` + `pendingApprovals` + `metadata` | 图状态 + channel / reducer |
| 中断 | 工具调用前审批 | 节点边界人工闸门 |
| 恢复 | 五保存点 + ③b 审批决策（turn / tool 粒度；④ 含 `running` / `completed`） | 每个 superstep 一份图状态 |
| 调度 | 模型决定下一步 | 边与调度器决定下一步 |
| 验收 | T1–T8 单 Agent 任务 | W1–W6 工作流任务（见 §3.5） |

把两者塞进一个 core 的后果：

1. 违反内核 ≤10 文件 / 总 LOC ≤1800，最小化原则失效；
2. 钩子生命周期被图语义污染，`transformInput` / `wrapToolCall` 的时机不再自洽；
3. `RunState` 被扩展成图状态，checkpoint 语义分叉；
4. core 无法独立发布、独立测试，插件独立性 smoke 失去意义；
5. 「单 Agent runtime」的定位消失，退化成半成品 LangGraph。

> [02](02-核心循环与事件系统.md) 已明确：图模型留到后续编排层评估——这不是临时缺口，是刻意取舍。

## 3. LangGraph-like 编排层蓝图（`Kern Graph` / `@kernjs/graph`）

### 3.1 目标

**确定性骨架 + 开放式节点**：

- 图负责：顺序、分支、并行、闸门、恢复；
- Agent 节点负责：开放式推理与工具使用；
- 不追求 LangGraph 全量等价，只做「工作流需要的那部分图语义」。

### 3.2 节点类型（MVP）

| 节点 | 行为 | 与 core 的关系 |
| --- | --- | --- |
| agent | 调用 `runtime.stream()` 跑一个单 Agent run | 直接复用 core |
| function | 纯函数 / IO，无模型调用 | 不依赖 core |
| gate | 人工审批 / 输入，暂停图 | 复用 resume 思路，图状态独立 |
| subgraph | 嵌套子图 | 编译期展开或运行时调用 |

### 3.3 能复用的 core 能力

| core 能力 | 在编排层怎么用 |
| --- | --- |
| `runtime.stream()` | Agent 节点执行器 |
| `AgentEvent` + `spanId` | 跨节点 trace 树 |
| `RunState` / Checkpointer | 节点级恢复；图状态另存 |
| `resume()` | core 只到工具级审批；节点级 interrupt 由 graph 自己实现 |
| hooks | 节点级中间件、策略注入 |
| plugin registry | 节点类型、工具、服务 |
| OTel | 跨节点链路 |

### 3.4 必须新写的能力

| 能力 | 说明 | MVP 是否做 |
| --- | --- | --- |
| 图定义 / 编译 | 节点、边、条件、并行 | 是 |
| 调度器 | 顺序 / 分支 / fan-out / fan-in | 是 |
| 图状态 | Zod schema + 简单合并 | 是（先不做 channel / reducer） |
| superstep checkpoint | 每个超步保存图状态 | 是 |
| 节点级 interrupt | 闸门暂停 / 恢复 | 是 |
| subgraph | 嵌套图 | 是 |
| time travel / fork | 回滚到历史节点 | 否（可选） |
| 图可视化 / DSL | 可视化、声明式 DSL | 否（可选） |

### 3.5 MVP 验收草案（W1–W6）

| # | 任务 | 验证点 |
| --- | --- | --- |
| W1 | 线性 3 节点图（function → agent → function） | 节点调度 + 事件流 |
| W2 | 条件边（按状态分流） | 分支 + 状态传递 |
| W3 | 并行 fan-out / fan-in | 并发调度 + 结果合并 |
| W4 | gate 节点暂停 → resume | 节点级 HITL + checkpoint |
| W5 | 中途 kill → 重启续跑 | superstep 恢复 |
| W6（可选） | subgraph 嵌套 | 组合与隔离 |

> W1–W6 是编排层验收，不替代 T1–T8；两层各自有任务集，互不混用。

## 5. 扩展原则（红线）

1. **core 不 import 任何扩展**；扩展只依赖 core 公开 API。
2. **新能力优先做成插件 / 独立包**；只有「内核 API 不再自洽」时才考虑进 core。
3. **协议先行**：新扩展复用事件 / 钩子 / checkpointer；确需新协议时，先改文档、再升版本。
4. **每个扩展可独立删除**：smoke 脚本验证 core + 其余插件仍可启动。
5. **每个扩展有自己的验收任务集**：不拿「能聊天」当验收。
6. **不追求框架等价**：目标是理解设计动机与取舍，不是复制 LangGraph 全部功能。

## 6. 阶段建议（与 08 的关系）

- v0.1–v0.3：按 [08](08-路线图与里程碑.md) 主线走，不做图编排；先把单 Agent runtime + harness 打牢。
- v0.4a：plugin-otel / plugin-todo / compaction（T6）。
- v0.4b：子 agent / 模型路由 / 评测（T8）。
- v1.0：MCP / 技能 / RAG；编排层仍可选。
- v1.x：若确有工作流需求（如 PRD 14 步、多阶段闸门），再把 `Kern Graph` 独立成包 / 仓库；技术 spike 也在 v1.x，不占 v0.4。

> 08 是承诺路线；本文是扩展候选。两者冲突时以 08 为准。
