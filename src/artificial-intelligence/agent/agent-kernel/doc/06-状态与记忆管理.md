## 1. RunState

一次 thread 的全部可恢复信息，**纯数据、可 JSON 序列化**：

```ts
interface RunState {
  version: 1                  // schema 版本：迁移函数表预留，现在就加（零成本）
  threadId: string            // 会话隔离键
  runId: string               // 当前 run：resume 保持同一 id；新 run 重新生成
  status: 'running' | 'awaiting-approval' | 'done' | 'error' | 'aborted'
  phase: 'model' | 'tools' | 'turn-end'  // resume 重入点：不靠猜，直接按 phase 继续
  seq: number                 // 当前 run 的事件序号；resume 继续递增，不重置
  messages: Message[]         // 完整消息历史（含工具调用与结果）
  runStep: number             // 本次 run 的 turn 序号（maxIterations 与它比较，run 级）
  totalSteps: number          // thread 级累计 turn（每次模型调用计 1，审计 + 硬上限 maxTotalSteps 比较）
  usage: Usage                // thread 累计 token 用量
  runUsage: Usage             // 本次 run 累计 token 用量；新 run 重置
  pendingToolCalls: PendingCall[]// 工具派发前置 pending、执行前置 running、完成后置 completed；全部完成清空（结构见 [02](02-核心循环与事件系统.md)）
  pendingApprovals: PendingApproval[] // 审批挂起时的待决策项；终态清空
  principal?: Principal               // opaque 身份；首次 stream 写入，resume / 后续 stream 只读，不得替换
  metadata: Record<string, unknown>  // 插件命名空间键：metadata['plugin:todo']
}

type PendingCall = {
  call: ToolCall
  status: 'pending' | 'running' | 'completed'  // 业务失败 = completed + result.ok=false
  attemptId?: string                            // 每次真正开始执行时生成的 UUID，独立于事件 seq
  result?: ToolResult
}

interface PendingApproval {
  approvalId: string
  toolCallId: string
  call: ToolCall
  requestedAt: number
  options: Array<'allow' | 'deny'>
  decision?: 'allow' | 'deny'   // resume 后先落盘决策；崩溃后不重复询问
  decidedAt?: number
  expiresAt?: number            // 超时时间；过期后统一转 deny
}
```

**status 终态与恢复语义**（定稿）：

| 加载时 status | 含义 | `runStep` | 恢复行为 |
| --- | --- | --- | --- |
| `done` / `error` / `aborted` | 终态 | **重置为 0**（`maxIterations` 是 run 级，见 [01 术语表](01-总体架构设计.md)；不重置则第二次 run 只剩残余额度，跨 run bug 回归） | 开新 run：追加新输入，重新计数 |
| `awaiting-approval` | 审批挂起 | **保留**（仍在同一 run 内） | 审批恢复：`runtime.resume({ approvalId, decision })`；`pendingApprovals` 落盘，崩溃后也能恢复 |
| `running` | **崩溃残留**（thread 锁保证无并发进行中） | **保留**（同一 run 续跑） | 崩溃恢复：按 `phase` 重入；`pending` 重派；`running` 按 `sideEffect` 决定重试或失败；`completed` 复用结果；回填前补消息配对 |

> 终态开新 run：`runId` 重新生成、`phase = model`、`seq = 0`、`runStep = 0`、`runUsage = 0`；`totalSteps` / `usage` 保留（thread 级审计 / 熔断）。

**phase 与保存点 × resume 矩阵**（本表是 [02 §3](02-核心循环与事件系统.md) 的恢复映射；`phase` 赋值以 02 为准，不在此重复定义）：

| 保存点 / 崩溃点 | `phase` | 崩溃后状态 | `resume` 入口 |
| --- | --- | --- | --- |
| ① turn 开始 | `model` | 无 assistant tool_use | 重发当前 turn 的 callModel |
| ②a 回填后 | `turn-end` | 工具消息已回填、计数未变 | 只发 `turn-finished`、计数、保存点 ②b |
| ②b 计数后 | `model` | 计数已更新 | 进入下一轮 callModel |
| ③ 工具派发前 | `tools` | assistant tool_use + pending | **不 callModel**；继续执行工具 |
| ④a 工具执行前 | `tools` | `running + attemptId` | 按 `sideEffect` 重试或失败 |
| ④b 工具完成后 | `tools` | `completed + result` | **不 callModel**；补 ToolMessage → `turn-end` |
| ③b 审批决策 | `tools` | `pendingApprovals.decision` 已写 | 不重问；allow 执行 / deny 归一 failResult |
| ⑤ run 结束 | — | 终态 | 不可 resume；开新 run |

**审批状态矩阵**：

| 当前状态 | 条件 | 行为 |
| --- | --- | --- |
| `awaiting-approval` | 无 `decision`，未过期 | 发 `approval-requested`，保持挂起 |
| `awaiting-approval` | `decision = allow` | 执行挂起工具 |
| `awaiting-approval` | `decision = deny` | `failResult('APPROVAL_DENIED')` + `tool-call-cancelled(denied)` |
| `running` | 已有 `allow` / `deny` | 不重问，按 decision 继续 |
| `awaiting-approval` / `running` | `expiresAt` 已过 | 转 deny + `failResult('APPROVAL_EXPIRED')` + `tool-call-cancelled(expired)` |

> `expiresAt` 优先于任何 late decision：过期后即使收到 `allow`，也按 `APPROVAL_EXPIRED` 处理，不允许晚到决策覆盖超时策略。

> 💡 设计决策：**无隐藏状态**。循环里的任何信息（todo 计划、待审批项、工具执行进度）都挂到 `metadata` / `pendingApprovals` / `pendingToolCalls`，checkpoint 后才可能完整恢复。这是对 LangGraph「状态即图状态」的简化版——没有图，状态就是消息历史 + 计数 + 扩展槽。

`metadata` 约束：单 thread ≤ 64KB；插件必须通过 `ctx.metadata('<plugin-name>')` 读写，内核负责命名空间隔离、JSON 序列化校验与**超限拒绝写入**（WARN 日志 + 保留既有键），不允许静默截断或拖垮 checkpoint 写入。

## 2. Checkpointer 接口

```ts
interface Checkpointer {
  save(state: RunState): Promise<void>   // threadId 已在 state 内
  load(threadId: string): Promise<RunState | null>
  delete?(threadId: string): Promise<void>
}
```

**`save` 失败语义（定稿）**：`save` 抛错视为 **fatal**。

- 业务保存点失败 → 终止 run（`CheckpointError`，`KernelError` 家族），锁由 runtime 释放；
- 终态保存点 ⑤ 只做**一次** best-effort 写入；失败不重试、不在 `finalize` 内递归收口，记录原始错误后释放锁并把 `CheckpointError` 交给调用方；
- 禁止「保存失败 → 再走一次 finalize → 再保存」的递归路径；`persistTerminal` 必须幂等（`finalized` 标志见 [02 §3](02-核心循环与事件系统.md)）。

### 2.1 五个保存点 + ③b 审批决策（定稿）

| 保存点 | 时机 | 保护的场景 |
| --- | --- | --- |
| ① turn 开始 | 每轮 `turn-started` | 常规断点 |
| ②a 回填后 | ToolMessage 回填、`phase = turn-end`，`turn-finished` 前 | 崩溃后不重复回填 |
| ②b turn 结束 | 计数 + `phase = model` 后 | 下一轮入口，`runStep` 已递增 |
| ③ 工具派发前 | assistant `tool_use` 先入 `messages`；`pendingToolCalls` 全部置 `pending` 落盘 | **配对不变量**：恢复后 `ToolMessage` 一定有对应 `tool_use`；HITL 审批恢复的前提 |
| ③b 审批决策 | `resume` 写入 `decision / decidedAt` 后立即落盘 | 决策后崩溃不重问；allow / deny 都能恢复 |
| ④ 工具生命周期 | 执行前置 `running + attemptId` 落盘；完成后置 `completed + result` 落盘（每个工具两次写） | **部分完成不丢结果**；能区分「未开始」与「执行中崩溃」，按 `sideEffect` 决定是否重试 |
| ⑤ run 结束 | `persistTerminal` / `finalize` 收口：补未完成 `ToolMessage` + 写终态 + 清空 `pendingToolCalls` / `pendingApprovals` | 终态完整落盘，无漏存出口；消费者 break 也走这里 |

> ⚠️ 保存点 ③ / ④ **不承诺 exactly-once**：任意副作用工具在执行中崩溃后，无法仅凭 checkpoint 判断副作用是否已生效。诚实语义是 **at-least-once**：
> - `sideEffect: 'idempotent'`：`running` 可重试（新 `attemptId`）；
> - `sideEffect: 'non-idempotent'`：默认标记为失败 / 转人工，不自动重放。
>
> 💡 每个工具完成的持久化走 `PendingCall`（结构见 [02](02-核心循环与事件系统.md)），**不在 ④ 直接 push ToolMessage**——并发完成顺序会打乱消息顺序，回填统一按模型产出原始顺序执行。

**消息不变量**（checkpoint / 恢复必须满足）：

1. 每个 assistant `tool_use` 在落盘前已进入 `messages`；
2. 每个 `tool_use` 必须有且只有一个对应 `ToolMessage`；完成、业务失败、审批拒绝、abort 都补 `failResult`；
3. `ToolMessage` 按模型产出的原始顺序回填，不按并发完成顺序；
4. 终态 `pendingToolCalls` 与 `pendingApprovals` 为空。

### 2.2 会话恢复语义

```ts
// 伪代码：多轮对话 = threadId 关联的多次 run
const runtime = createRuntime({ plugins: [modelPlugin, checkpointerPlugin] })

// 第一轮（principal 可选，透传给 ToolContextFactory）
for await (const e of runtime.stream({ threadId: 't1', input: '杭州天气如何', principal: { id: 'u1' } })) { ... }

// 第二轮：内核从 checkpointer 加载 t1 的 state，追加新输入后继续
for await (const e of runtime.stream({ threadId: 't1', input: '那明天呢？' })) { ... }

// 审批恢复（v0.2）：status === 'awaiting-approval'
// principal 不在 resume 参数里：core 以 RunState.principal 为准
for await (const e of runtime.resume({
  threadId: 't1',
  approvalId: 'ap-1',
  decision: 'allow',
})) { ... }

// 崩溃恢复（v0.3）：status === 'running'
for await (const e of runtime.resume({ threadId: 't1' })) { ... }
```

> **principal 生命周期**：首次 `stream({ principal })` 写入 `RunState.principal` 并落盘；`resume` 与后续 `stream` 只使用持久化值，不接受新的 `principal`。若调用方传入不同的 `principal`，按 `PrincipalMismatchError` 处理（v0.2），不静默覆盖。

`resume` 的唯一签名：

```ts
resume(req: {
  threadId: string
  approvalId?: string          // status = awaiting-approval 时必填
  decision?: 'allow' | 'deny'  // status = awaiting-approval 时必填
  reason?: string
  signal?: AbortSignal
}): AsyncGenerator<AgentEvent>
```

按加载时 `status` 分支：

| status | 行为 |
| --- | --- |
| `awaiting-approval` | 校验 `approvalId` 与 `decision`；先把 `decision / decidedAt` 写入 `pendingApprovals` 并落盘（保存点 ③b），再执行挂起工具或归一为 `failResult('APPROVAL_DENIED')`；无 decision 且未过期 → 重新发 `approval-requested`；过期 → deny / `APPROVAL_EXPIRED`；决策落盘后崩溃不重复询问 |
| `running` | 崩溃恢复：按 §1 的 `phase` + `pending` / `running` / `completed` 规则续跑；已有审批 decision 不重问 |
| `done` / `error` / `aborted` | 抛 `ThreadNotResumableError`；开新会话走 `stream()`，不复用终态 thread |

**`stream()` vs `resume()`**：

- `stream()` 只用于新 run 或终态 thread；加载到 `awaiting-approval` / `running` 且已有 `messages` 时抛 `ThreadNotResumableError`，必须走 `resume()`；
- `resume()` 保持**同一 `runId`**，`seq` 从 checkpoint 继续递增；`run-started` 只在新 run 发，resume 发 `run-resumed`。

### 2.3 并发控制（定稿）

v0.1 起内核内置**进程内 per-thread 锁**（锁按 `threadId`，不是 runtime 实例级）：同一 `threadId` 并发 `stream` 直接抛 `ThreadBusyError`（`KernelError` 家族，见 [01 错误模型](01-总体架构设计.md)）。理由：并发写 state 的合并逻辑复杂度远超收益，拒绝比仲裁便宜。

**获取顺序（定稿）**：`stream()` / `resume()` 一律**先获取 per-thread 锁，再 `load` state**。顺序颠倒会出现两个调用先读同一份 state、再互相覆盖；也让「锁失败」与「状态不可恢复」的判定不确定。

**错误优先级（定稿）**：同一 thread 上同时可能触发两种错误时，**`ThreadBusyError` 先于 `ThreadNotResumableError`**——锁是进入条件，状态检查是锁内行为。错误信息可按 `{ code: 'THREAD_BUSY' | 'THREAD_NOT_RESUMABLE' }` 细分。

- **审批挂起时释放锁**：`awaiting-approval` 不持有锁，否则 `resume` 会被自己的锁挡住；
- **`resume` 重新获取锁**：进入后先在锁内校验 `status`，再续跑；校验失败即抛错；
- **崩溃恢复**：进程重启后锁自然消失，`resume` 重新获取锁并从 checkpoint 续跑。

## 4. 上下文窗口管理

**不进内核**——通过 `transformInput` 钩子以插件实现：

| 策略 | 插件行为 | 适用场景 |
| --- | --- | --- |
| 滑动截断 | 保留 system + 最近 N 轮，丢弃更早历史 | 简单客服，成本敏感 |
| 滚动摘要 | 超阈值时把旧历史压缩成摘要消息注入 | 长会话助手 |
| 工具结果瘦身 | 旧轮次的工具结果替换为 `[已省略]` 占位 | 工具密集型任务（结果占上下文大头） |

触发线：`contextWindow × 70%`（读 `Provider.capabilities.contextWindow`，见 [04](04-模型Provider抽象.md)），压缩自身成本（摘要调用的 token）计入 usage 统计。

> `context-overflow` 不走 70% 预压缩路径：由 `wrapModelCall` 捕获后调用 compaction 服务再重发一次，见 [04 §4](04-模型Provider抽象.md)。70% 只做预防性压缩。

### 压缩的硬约束（高频 bug 防线）

1. **成对删除**：`transformInput` 压缩时必须保证 `tool-use` 与对应 `tool_result` **成对增删**——单删一侧 API 直接报错，这是实践中最高频的上下文 bug
2. **system prompt 永不压缩**
3. **压缩点尽量靠后**：保持前缀稳定以命中 prompt cache（详见 [09](09-harness层设计.md) 2.4）

此约束同时写进 [03](03-插件系统与钩子设计.md) 的 compaction 试金石。

## 6. 对照 LangChain / LangGraph

| 维度 | 本内核 | LangChain `MemorySaver` | LangGraph checkpointer |
| --- | --- | --- | --- |
| 粒度 | 5 个保存点 + ③b（见 2.1） | 每次调用后 | 每个超步（superstep） |
| 恢复单元 | 整个 `RunState`（含 `pendingToolCalls`） | channel values | 图状态 + pending writes |
| 恢复能力 | resume（审批 / 崩溃恢复） | 时间旅行 | 时间旅行 |
| 存储 | 插件：内存 / SQLite / PG | 内置多种 | 内置多种 |

不支持时间旅行是有意取舍：无图就没有分支执行，全量覆盖足够。**v0.x 不提供 `rewind` / `fork`**；需要时由调用方新建 threadId 做「分支」，不绕开 core 的状态模型。若 v1.x 引入子 Agent 编排再评估历史快照 API（见 [09](09-harness层设计.md) 2.5）。
