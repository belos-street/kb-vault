## 1. RunState

一次 thread 的全部可恢复信息，**纯数据、可 JSON 序列化**：

```ts
interface RunState {
  version: 1                  // schema 版本：迁移函数表预留，现在就加（零成本）
  threadId: string            // 会话隔离键
  runId: string               // 当前 run（恢复时由 runtime 重置）
  status: 'running' | 'awaiting-approval' | 'done' | 'error' | 'aborted'
  messages: Message[]         // 完整消息历史（含工具调用与结果）
  runStep: number             // 本次 run 的 turn 序号（maxIterations 与它比较，run 级）
  totalSteps: number          // thread 级累计 turn（审计 + 硬上限 maxTotalSteps 比较）
  usage: Usage                // thread 累计 token 用量
  pendingToolCalls: PendingCall[]// 工具派发前置 pending、每个完成后更新、全部完成清空（结构见 [02](02-核心循环与事件系统.md)）
  metadata: Record<string, unknown>  // 插件命名空间键：metadata['plugin:todo']
}
```

**status 终态与恢复语义**（定稿）：

| 加载时 status | 含义 | `runStep` | 恢复行为 |
| --- | --- | --- | --- |
| `done` / `error` / `aborted` | 终态 | **重置为 0**（`maxIterations` 是 run 级，见 [01 术语表](01-总体架构设计.md)；不重置则第二次 run 只剩残余额度，跨 run bug 回归） | 开新 run：追加新输入，重新计数 |
| `awaiting-approval` | 审批挂起 | **保留**（仍在同一 run 内） | 走审批恢复：`runtime.resume(approval)` |
| `running` | **崩溃残留**（thread 锁保证无并发进行中） | **保留**（同一 run 续跑） | 崩溃恢复：只重派 `pendingToolCalls` 中 `status === 'pending'` 的调用；`completed` / `failed` 的 result 保留用于按原始顺序回填 |

> 💡 设计决策：**无隐藏状态**。循环里的任何信息（todo 计划、待审批项）都挂到 `metadata` / `pendingToolCalls`，checkpoint 后才可能完整恢复。这是对 LangGraph「状态即图状态」的简化版——没有图，状态就是消息历史 + 计数 + 扩展槽。

`metadata` 约束：单 thread ≤ 64KB；**超限行为 = WARN 日志 + 拒绝写入超限键**（保留既有键），不允许静默截断或拖垮 checkpoint 写入。

## 2. Checkpointer 接口

```ts
interface Checkpointer {
  save(threadId: string, state: RunState): Promise<void>
  load(threadId: string): Promise<RunState | null>
  delete?(threadId: string): Promise<void>
}
```

### 2.1 五个保存点（定稿）

| 保存点 | 时机 | 保护的场景 |
| --- | --- | --- |
| ① turn 开始 | 每轮 `turn-started` | 常规断点 |
| ② turn 结束 | 每轮 `turn-finished` | 常规断点（含助手回答已入历史） |
| ③ 工具派发前 | `wrapToolCall` 执行前，`pendingToolCalls` 全部置 `pending` 落盘 | **崩溃后恢复不重复执行副作用工具**；HITL 审批恢复的前提 |
| ④ 每个工具完成 | 更新对应 `PendingCall`（`status` + `result`）后立即落盘 | **部分完成不丢结果**：A 完成、B 崩溃时，恢复只重派 `pending` 的 B，A 不重复执行 |
| ⑤ run 结束 | `finalize` 收口：写终态 + 清空挂起，`run-finished` / `error` / `aborted` 前 | 终态完整落盘，无漏存出口 |

> ⚠️ 保存点 ③ / ④ 是评审补充的关键点：没有 ③，「跑测试 → 改文件 → 崩溃重启」会把 edit 类副作用工具重复执行一遍；没有 ④，「A 完成 → B 崩溃」会把已完成的 A 也重复执行。
>
> 💡 每个工具完成的持久化走 `PendingCall`（结构见 [02](02-核心循环与事件系统.md)），**不在 ④ 直接 push ToolMessage**——并发完成顺序会打乱消息顺序，回填统一按模型产出原始顺序执行。

### 2.2 会话恢复语义

```ts
// 伪代码：多轮对话 = threadId 关联的多次 run
const runtime = createRuntime({ plugins: [modelPlugin, checkpointerPlugin] })

// 第一轮
for await (const e of runtime.stream({ threadId: 't1', input: '杭州天气如何' })) { ... }

// 第二轮：内核从 checkpointer 加载 t1 的 state，追加新输入后继续
for await (const e of runtime.stream({ threadId: 't1', input: '那明天呢？' })) { ... }

// HITL 恢复（v0.2）：status === 'awaiting-approval' 的 thread
for await (const e of runtime.resume({ threadId: 't1', approval: 'allow' })) { ... }
```

### 2.3 并发控制（定稿）

v0.1 起内核内置**进程内 per-thread 锁**：同一 `threadId` 并发 `stream` 直接抛 `ThreadBusyError`（`KernelError` 家族，见 [01 错误模型](01-总体架构设计.md)）。理由：并发写 state 的合并逻辑复杂度远超收益，拒绝比仲裁便宜。

## 3. 实现路线

| 版本 | 实现 | 存储形态 | 说明 |
| --- | --- | --- | --- |
| v0.1 | 内存 Map | `Map<string, RunState>` | 等价 `MemorySaver`，开发测试用 |

## 4. 上下文窗口管理

**不进内核**——通过 `transformInput` 钩子以插件实现：

| 策略 | 插件行为 | 适用场景 |
| --- | --- | --- |
| 滑动截断 | 保留 system + 最近 N 轮，丢弃更早历史 | 简单客服，成本敏感 |
| 滚动摘要 | 超阈值时把旧历史压缩成摘要消息注入 | 长会话助手 |
| 工具结果瘦身 | 旧轮次的工具结果替换为 `[已省略]` 占位 | 工具密集型任务（结果占上下文大头） |

触发线：`contextWindow × 70%`（读 `Provider.capabilities.contextWindow`，见 [04](04-模型Provider抽象.md)），压缩自身成本（摘要调用的 token）计入 usage 统计。

### 压缩的硬约束（高频 bug 防线）

1. **成对删除**：`transformInput` 压缩时必须保证 `tool-use` 与对应 `tool_result` **成对增删**——单删一侧 API 直接报错，这是实践中最高频的上下文 bug
2. **system prompt 永不压缩**
3. **压缩点尽量靠后**：保持前缀稳定以命中 prompt cache（详见 [09](09-harness层设计.md) 2.4）

此约束同时写进 [03](03-插件系统与钩子设计.md) 的 compaction 试金石。

## 6. 对照 LangChain / LangGraph

| 维度 | 本内核 | LangChain `MemorySaver` | LangGraph checkpointer |
| --- | --- | --- | --- |
| 粒度 | 5 个保存点（见 2.1） | 每次调用后 | 每个超步（superstep） |
| 恢复单元 | 整个 `RunState`（含 `pendingToolCalls`） | channel values | 图状态 + pending writes |
| 恢复能力 | resume（续跑 / 审批） | 时间旅行 | 时间旅行 |
| 存储 | 插件：内存 / SQLite / PG | 内置多种 | 内置多种 |

不支持时间旅行是有意取舍：无图就没有分支执行，全量覆盖足够；若 v0.3 引入子 Agent 编排再评估 `fork`（见 [09](09-harness层设计.md) 2.5）。
