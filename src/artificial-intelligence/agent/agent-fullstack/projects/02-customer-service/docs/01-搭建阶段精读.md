## 1. §0 工程初始化——每个文件为什么存在

### 1.1 package.json：脚本即接口

关键不是依赖列表，而是 [scripts](../package.json) 区——`db:up` / `db:seed` / `cli` / `tickets:list` / `eval`。**把每个高频动作做成一条 `bun run xxx`**，后续 README 的验收走查全部通过这些脚本执行，避免「文档一个命令、手敲另一个」的漂移。

依赖只有 6 个：`langchain`（框架主包）、`@langchain/langgraph`（MemorySaver / Command）、`@langchain/langgraph-checkpoint-postgres`（持久化 checkpoint）、`pg`（业务数据访问）、`zod`（全链路校验）、`dotenv`。没有数据库 ORM——这个项目的数据访问就是裸 SQL。

### 1.2 tsconfig.json：Bun 时代的 TS 配置

沿用 01 项目，几个关键项：

- `module: Preserve` + `allowImportingTsExtensions: true` + `noEmit: true`：**Bun 直接执行 TS，没有构建产物**，所以 import 可以带 `.ts` 后缀（本文所有 `import ... from '../config.ts'` 依赖此项）
- `verbatimModuleSyntax: true`：强制区分 type import 与 value import
- `strict` + `noUncheckedIndexedAccess`：数组取值 `rows[0]` 的类型是 `T | undefined`，逼你处理空结果（db.ts 里到处能看到这个纪律）

### 1.3 .oxlintrc.json / .oxfmtrc.jsonc：工具链约定

仓库根 [agents.md §5.6](../../../../../../agents.md) 规定：学习类 Demo 统一 Bun + oxlint + oxfmt，且**参考配置就指向本项目的这两个文件**。风格要点：单引号、无分号、2 空格、无尾逗号、行宽 80。唯一的项目级豁免是 `import/no-unassigned-import: off`——`import 'dotenv/config'` 是刻意的副作用导入。

### 1.4 .env 与 .env.example：一对分工

| 文件           | 提交？           | 内容                                        |
| -------------- | ---------------- | ------------------------------------------- |
| `.env.example` | ✅               | 全部配置项 + 注释说明，作为「配置清单文档」 |
| `.env`         | ❌（.gitignore） | 你的真实 Key                                |

本项目**唯一的外部 Key 是 LLM API Key**（LangSmith 已移除、RAG/Embedding 已砍）。其余全是本地项。

### 1.5 src/config.ts：所有环境变量的唯一入口

三个设计点：

1. **Zod 校验 + 默认值**：`safeParse` 失败直接退出并列出每个字段的问题——配置错误在进程启动第一秒暴露，而不是运行到一半炸
2. **`normalizeModel`**：`deepseek-v4-flash`（无前缀）→ `openai:deepseek-v4-flash`。无 provider 前缀的模型串按 OpenAI 兼容端点处理，配合 `OPENAI_BASE_URL` 指向 DeepSeek——你的 `.env` 可以用最自然的写法
3. **单模型 + 可覆盖位**：`mainModel` / `classifierModel` 两个运行时字段，`CLASSIFIER_MODEL` 不配就回落主力。1.1 的「模型分层」概念保留在结构上，但**不强迫你配两把 Key**

> 学习要点：配置模块的职责是「读一次、校验、归一化、导出常量」，不要出现 `process.env.XXX` 散落在业务代码里。

## 2. §1 本地基建与两个 Spike

### 2.1 docker-compose.yml：为什么只有一个服务、为什么是 5433

- 业务数据（orders/tickets）和会话快照（checkpoint）**同库不同表**，一个 pg 全搞定——这是当初「同库方案」的取舍，换来的是零跨库一致性心智负担
- 端口映射 `5433:5432`：宿主机 5432 已被共享 pg 容器占用，本项目映射 5433 避让（[docker-compose.yml](../docker-compose.yml) 注释），`.env` / `.env.example` / `config.ts` 默认值三处已同步
- `volume: pgdata` + healthcheck：数据持久化在命名卷里，容器重建不丢

### 2.2 什么是 Spike

XP/敏捷术语 _spike solution_，借自攀岩——冲顶前先钉岩钉试探岩壁承力。定义为：**为消除一个具体的技术不确定性而写的最小探针代码，产出是结论而不是功能**。本项目有两个：Checkpoint 持久化能不能跨进程？HITL 的 resume 字段到底长什么样？这两个问题在教程文档里只有语义级描述，不实测就没法放心写主循环。

### 2.3 Spike A：PostgresSaver 持久化（[spike-a-checkpoint.ts](../scripts/spike-a-checkpoint.ts)）

**验证方式**：`write` 模式写 2 轮对话 → 换一个进程跑 `resume` 模式 → 同 `thread_id` 读回消息数 + 续聊计数。两个独立进程 = 模拟「客服换班次再上线」。

**实测结论**（已回填 todo.md「Spike 结论」）：

| 结论     | 内容                                                                                                          |
| -------- | ------------------------------------------------------------------------------------------------------------- |
| API 形态 | `PostgresSaver.fromConnString(url)` 直接返回实例（不是 `{ pool, checkpointer }` 包装）                        |
| 建表     | `await setup()` 建 4 张表：`checkpoints` / `checkpoint_blobs` / `checkpoint_writes` / `checkpoint_migrations` |
| 持久化   | 跨进程同 `thread_id`：写 4 条 → 读 4 条 → 续聊后 6 条 ✓                                                       |
| 收尾     | 实例有 `.end()` 关连接池；**不调用则 pg 连接挂住进程**（Bun 不会替你强退）                                    |
| 坑       | invoke 中途抛错，已完成 super-step 的消息也会被 checkpoint——失败重试要用新 `thread_id`，否则计数被脏数据污染  |

### 2.4 Spike B：HITL 中断与恢复（[spike-b-hitl.ts](../scripts/spike-b-hitl.ts)）

三个场景各跑一个独立 thread，实测三件事：

1. **中断在哪**：invoke 结果的 `result.__interrupt__`（数组），元素含 `value.actionRequests`（工具名 + 参数 + 描述）和 `value.reviewConfigs`（该工具允许的决策集）——CLI 审批 UI 就靠这两个字段渲染
2. **恢复怎么发**：`agent.invoke(new Command({ resume: { decisions: [{ type: 'approve' | 'edit' | 'reject', ... }] } }), 同 thread_id config)`——`{ decisions: [...] }` 形态实测可用
3. **三决策行为**：`approve` 按原参执行；`edit` 带 `editedAction: { name, args }` 且**修订参数直达工具**；`reject` 带 `message`，工具**不执行**，以 `ToolMessage(status: 'error', content: message)` 进上下文让模型体面收尾

**附带沉淀——fakeModel 测试手法**（后续所有 `test/*.ts` 的模板）：

- `fakeModel` 自 `"langchain"` 主包导入（官方 unit-testing 指南推荐，实测可用，无需回退 core/testing）
- 响应是 **FIFO 队列**：`.respondWithTools([...])` 排第一轮的工具调用，`.respond(factory)` 排恢复后的最终话术轮——一次 invoke 消费一条，队列空了就抛错
- `createAgent` 的 `model` 参数对 FakeBuiltModel 类型不认，运行时兼容，用 `as never` 绕过

> Spike 方法论：探针脚本里对不确定的 API 做**形态探测**（try 主路径 → catch 回退路径，打印各自结果），跑完把结论回填 todo.md——结论是资产，脚本是证据。

## 3. §2 数据与 FAQ 底座

### 3.1 db/schema.sql：一个「为 Agent 设计」的数据集

[schema.sql](../db/schema.sql) 四个值得学的设计：

1. **相对时间偏移**：种子数据不用硬编码日期，全部 `now() - INTERVAL '6 days'`——重跑多少次，「已签收 6 天」「7 天无理由窗口内」的语义都不漂移。Few-shot 和评估用例依赖的正是这种**时间不变性**
2. **`delivered_at` 独立列**：退款时效的窗口起点。后续 `process_refund` 的可退校验（纯代码判定，不让 LLM 比较数值）就查这个字段
3. **两个刻意数据坑**：坑 A `SO-2026-0702` 已发货但 `tracking_number` 为 NULL；坑 B `SO-2026-0950` 昨天下单今天已签收（状态矛盾）。考察 Agent「如实告知矛盾而非编造」——这是客服场景最真实的幻觉测试点
4. **COMMENT 全覆盖**：每个字段的业务含义写在库里，`query_order` 工具的描述和它天然对齐

另一张表 `tickets`（工单）初始为空，`type` / `status` 用 CHECK 约束枚举，`id` 是 `GENERATED ALWAYS AS IDENTITY`（对外展示 `TK-0001` 形态）。

### 3.2 db/seed.ts：幂等重建 + 自校验

[seed.ts](../db/seed.ts) 的模式值得复用：

- `readFileSync` 整个 `schema.sql` 一次 `client.query()` 执行——schema 文件即迁移文件
- 执行完**立刻跑一条校验查询**：总数 20、坑 A 计 1、坑 B 计 1——seed 的输出自带断言，跑完看一眼日志就知道数据对不对
- 只 `DROP` 两张业务表，**不碰 checkpoint 四张表**（删 checkpoint 表是另一件事，`setup()` 会自动重建）

### 3.3 src/services/db.ts：薄访问层，业务规则后置

[db.ts](../src/services/db.ts) 的边界划得很清楚：**只有 CRUD，没有业务规则**。「订单可不可退」（状态 + 签收时效判定）留给后续 `order-service.ts`——因为那是**纯代码判定，绝不让 LLM 比较数值**（LLM 做数值比较不可靠）。

几个 TS 细节：

- `amount: string`——pg 的 `NUMERIC` 返回字符串，注释写明「原样使用避免浮点误差」，钱永远不用 number
- `OrderRow` / `TicketRow` 接口与 schema 的列一一对应，`pg` 泛型查询 `pool.query<OrderRow>(...)`
- 模块级单例 `Pool`，`closePool()` 供进程退出前调用（Spike A 的纪律落地）

### 3.4 src/memory/checkpointer.ts：双档切换

[checkpointer.ts](../src/memory/checkpointer.ts) 把 Spike A 的结论固化成 10 行代码：

- 环境变量 `CHECKPOINTER=memory|postgres`（默认 postgres）
- `setup()` 幂等（靠 `checkpoint_migrations` 表记账），重复调用安全
- `close()` 统一收尾——Postgres 档 `end()` 关池，Memory 档空操作。调用方再也不用关心两种实现的差异

**两档怎么选？一个常见误会：「开发用 memory、生产用 postgres」——本项目的默认恰恰是反过来的：**

| 档位 | 状态存哪 | 适合场景 |
| --- | --- | --- |
| `MemorySaver` | 进程内存（重启即失） | 跑测试（每个进程天然隔离、互不污染）；想让调试会话每次从零开始 |
| `PostgresSaver` | pg 数据库 | **默认档，包括日常开发调试** |

反直觉的原因：HITL 调试的主线动作就是「中断 → **杀进程** → 坐席审批 → 恢复」——memory 档下进程一死，中断现场就没了，跨进程审批根本没法测。生产多实例部署同理：memory 档每个实例各存一份，用户会话在实例间漂移就「失忆」；pg 档天然共享。

> 学习要点（2.5）：**Checkpointer 的价值 = 把「对话状态」变成可持久化的数据**。同一个 `thread_id` 跨进程读回上下文，客服场景的「换个班次接着聊」就是这么实现的。

#### 为什么叫 Checkpointer（而不是「记忆」组件）

名字借自数据库 / 分布式系统 / 游戏领域的 **checkpoint（检查点）**：在执行过程的特定时刻把完整状态拍一张快照，之后可以从任一快照恢复执行。它强调的不是「记住你说过什么」，而是「**记录执行到哪了、每一步的输入输出**」——所以它存的不只是聊天历史，还有 pending writes 和中断现场。HITL 之所以能跨进程等审批，靠的正是这份「执行现场」。

最贴切的类比是**游戏存档**：每个存档槽 = 一个 `thread_id`；读档 = 按 `thread_id` 恢复；存档内容 = 完整执行状态（角色位置 + 进度），而不只是对话文本。

#### 与短期记忆 / 长期记忆的关系（1.3 × 2.5）

| 维度 | 短期记忆 | 长期记忆 |
| --- | --- | --- |
| 范围 | 单个 thread（会话内） | 跨 thread / 跨会话 |
| 内容 | 消息历史 + agent 执行状态 | 用户偏好、历史工单、画像 |
| 谁负责 | **Checkpointer**（持久化层）+ `summarizationMiddleware`（体积管理，超窗压缩） | **Store**（`InMemoryStore` / `PostgresStore`，2.5）或 Mem0（1.3）——Checkpointer 不管这块 |
| 生命周期 | 会话结束即归档 | 长期累积 |

一句话：**Checkpointer 是「短期记忆的持久化机制」**——它把 1.3 说的「短期记忆：会话上下文」从内存变量变成可恢复的数据；长期记忆走 Store / Mem0，是完全另一套接口，两者不要混为一谈。社区里常说的分工就是「**checkpointer 管 thread 内，store 管 thread 间**」。

#### 用「和 LLM 助手对话」串一遍这些概念

你每天都在体验这套机制——以 Trae / ChatGPT 类助手为例，逐条对照：

| 你的日常体验 | 底下发生的事 | 对应概念 |
| ---------------------------- | ---------------------------------------- | ------------------------------- |
| 左侧栏每一条独立对话 | 每次新开对话 = 新建一个 `thread_id`，互不串扰 | thread 隔离 |
| 明天打开昨天的对话，接着问「刚才那点展开讲」 | 平台把每轮交互快照进了数据库，跨进程读回上下文 | **PostgresSaver**（跨进程恢复） |
| 你从没点过「保存」按钮，但历史从不丢 | 每个执行步骤后自动快照，对你透明 | Checkpointer 自动 `put` |
| 聊到几万 token 后助手说「早期内容可能已不在上下文」 | 窗口超限，早期历史被压缩成摘要 | `summarizationMiddleware`（2.5） |
| 对话删了，但新对话里它还记得「用户是 Rust 工程师」 | thread 没了（短期记忆没了），偏好还在（跨对话存储） | **长期记忆**：Store / Mem0 |
| 「编辑你之前发的消息」→ 从那条重新生成，还能切回原分支 | 回退到某个快照走另一条分支 | 时间旅行（checkpoint 链） |
| Trae 执行命令前弹「允许 / 跳过」、改文件前弹 diff 确认 | 工具调用前挂起，等人类决策再继续 | **HITL**（`__interrupt__` → approve） |

两个最有说服力的对照：

1. **短期 vs 长期记忆的分界**：删掉一条长对话——全部上下文（短期记忆）消失；但设置里的偏好、Memory 里存的画像（长期记忆）还在，新对话依然生效。同一个产品里**两套独立存储并存**，就是 1.3 讲的分层
2. **HITL 的日常形态**：「命令需要确认」弹出的瞬间就是一次 `__interrupt__`——Agent 挂起、执行现场被存档、等你决策；点「允许」= `decisions: [{ type: 'approve' }]`。与本项目唯一的差别是：Trae 的确认发生在同一进程生命周期内，而客服项目要求「坐席明天上班再批」——所以才需要 checkpoint 落库，中断才能**跨进程、跨天**存活

一句话：**开新对话、断线重连接着聊、编辑消息重新生成、点「允许执行」——全是 Checkpointer / thread / HITL 在产品里的日常化身。本项目要做的就是把这套体验自己实现一遍。**

### 3.5 kb/policy-faq.json：13 条结构化政策知识

每条 `{ id, keywords[], answer, source }`：关键词数组供检索、标准答案供引用、**出处（政策文档版本 + 条款号）**供溯源。覆盖退款 5 条 / 物流 2 条 / 会员 / 账号 / 发票等。它与 Few-shot、评估用例**共用同一套事实**——改政策只需要改这个文件。

> 注意：这是「检索即工具」的最简后端（§3 的 `search_policy` 工具将关键词匹配它）。向量检索整条线刻意留到第四章，届时只换检索实现、Agent 零改动。

### 3.6 附：checkpoint 四张表速记

| 表                      | 职责                                                           |
| ----------------------- | -------------------------------------------------------------- |
| `checkpoints`           | 快照主表：每个 thread 每个 super-step 一条记录（不含数据本体） |
| `checkpoint_blobs`      | 序列化大对象：消息历史 / channel values 的二进制存储           |
| `checkpoint_writes`     | 增量写入暂存：节点写下的 pending writes；HITL 恢复靠它回放     |
| `checkpoint_migrations` | setup() 的迁移账本：幂等的实现机制                             |

它们由 `setup()` 自动创建/重建（实测：DROP 后调用 `createCheckpointer()` 立刻长回来），**清空会话历史用 `TRUNCATE` 这四张表**即可。
