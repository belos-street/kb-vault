# 教学文档质量审查器 (Doc Quality Reviewer)

审查技术教学文档（含代码示例的 markdown 教程）的质量，对照参考模板给出逐篇评分与修改建议。

---

## 触发条件

当用户提出以下请求时，应调用此 Skill：

- "review 一下这份文档质量如何"
- "检查这些教程写得好不好"
- "评估一下学习资料的完整性"
- "对照模板审查文档"
- "这批 doc 有什么改进空间"

---

## 审查流程

### 1. 先读取参考模板（Reference）

如果用户未提供模板路径，询问用户。模板通常定义了：

- 文档命名规范
- 章节结构要求
- 代码示例标准
- 练习与面试要求

若用户提供了模板（如项目根 `readme.md`），从中提取**格式规范清单**作为评审基线。

### 2. 逐篇通读所有文档

同时读取所有目标文档，避免逐篇串行阅读导致的低效。对每篇文档做以下维度的评估。

### 3. 六维评分模型

对每篇文档按以下 6 个维度打分（1-5 星），并给出总评（满分 10）：

#### 维度 A：格式规范性

对照模板检查：

- 文件命名是否符合 `XX-模块名` 规范
- 头部元信息（模块映射、预计时间、面试可答）是否完整
- 代码块是否有语言标记（如 ` ```js `）
- 练习环节是否包含「要求 + 提示 + 预期效果」三段
- 面试回答模板是否使用 `> **问：**` 格式

#### 维度 B：代码可运行性

检查每个代码片段：

- **是否为可独立运行的完整代码**（非伪代码）
- 依赖是否明确（import/CDN 引入是否给出）
- 关键变量是否已声明
- 是否有明显的语法错误或逻辑遗漏

````markdown
✅ 正面示例：

```js
const stage = new Konva.Stage({ container: 'root', width: 800, height: 600 })
const layer = new Konva.Layer()
stage.add(layer)
layer.add(new Konva.Circle({ x: 100, y: 100, radius: 50, fill: 'red' }))
layer.draw()
```
````

❌ 反面示例：

```js
// 伪代码
circle.fill('red') // 这样就变红了
```

```

#### 维度 C：面试导向性
- 面试回答模板是否紧扣知识点
- 回答内容是否「拿来就能用」（即答即中的水平）
- 是否有自问自答式的深入追问（如「面试常问：为什么没有自动渲染？」）
- 是否覆盖了面试常见的追问点（陷阱、对比、原理）

#### 维度 D：知识覆盖度
- 核心 API 是否全部涉及
- 边缘情况是否有说明（如序列化不保留事件、图片异步加载）
- 常见踩坑点是否提醒到位
- 是否有进阶延伸（性能优化、设计模式）

#### 维度 E：渐进式学习
- 各篇之间是否有自然的递进关系
- 每篇是否在前一篇基础上扩展能力
- 练习难度是否递增
- 实战整合篇是否串联了前面所有知识点

#### 维度 F：对比完整性
检查每篇是否包含「与同类库/原生方案」的对比：
- 01 核心概念：Konva vs 原生 Canvas（架构对比）
- 02 基础图形：Konva Shape vs SVG Element
- 03 变换拖拽：Konva 拖拽 vs fabric.js vs 原生
- 04 事件系统：Konva 事件 vs DOM 事件 vs 原生 Canvas
- 05 序列化：Konva 序列化 vs fabric.js vs 原生
- 06 实战整合：整体对比总结

**对比应出现在每篇文末（面试模板之前），至少覆盖 Konva + 1 个同类方案 + 原生方案的三角对比。**

## 输出格式

### 总体评分（必须先输出）

```

## 📊 Konva Doc 文档质量 Review

### 一、格式规范度（对照 readme 模板）

| 规范要求                       | 01  | 02  | 03  | 04  | 05  | 06  |
| ------------------------------ | :-: | :-: | :-: | :-: | :-: | :-: |
| 文件命名 `XX-模块名.md`        | ✅  | ✅  | ✅  | ... | ... | ... |
| 头部元信息                     | ✅  | ... | ... | ... | ... | ... |
| 代码示例完整可运行             | ✅  | ... | ... | ... | ... | ... |
| 练习环节（要求+提示+预期效果） | ... | ... | ... | ... | ... | ... |
| 面试回答模板                   | ... | ... | ... | ... | ... | ... |
| 对比说明                       | ... | ... | ... | ... | ... | ... |

````

### 二、逐篇亮点与不足（⭐评分）

每篇都使用以下格式：

```markdown
#### [01-核心概念与初始化.md](file:///absolute/path) ⭐⭐⭐⭐⭐

**亮点**：
- xxx（具体指出哪个设计好、为什么好）
- xxx

**不足**：
- xxx（明确指出缺失什么、影响是什么）
- 无（如果确实完美）
````

### 三、整体评价表

| 维度         |   评分   | 说明           |
| ------------ | :------: | -------------- |
| 格式规范性   |   X/10   | ...            |
| 代码可运行性 |   X/10   | ...            |
| 面试导向性   |   X/10   | ...            |
| 知识覆盖度   |   X/10   | ...            |
| 渐进式学习   |   X/10   | ...            |
| 练习设计     |   X/10   | ...            |
| **总评**     | **X/10** | **一句话总结** |

### 四、改进建议（按优先级排序）

每条建议格式：

```
1. **模块 XX 补充 XXX**：当前只 YYY，建议增加 ZZZ。影响：XXX。
```

### 五、总体结论

一段话总结文档的整体质量水平，是否达到教学目标。

---

## 审查原则

1. **以模板为准**：格式检查严格对照用户提供的参考模板，不自行发明标准
2. **以可运行为底线**：代码片段必须完整可运行，这是教学文档的生命线
3. **以面试为导向**：技术教学的最终验收标准是「面试能答、功能能做」，评估时要时刻对照这个目标
4. **指出具体位置**：每一条不足都要指向具体的文件、行号或段落，附带修改方向
5. **正面引导**：评分可以严格，但表述要建设性——不只说「缺了什么」，还要说「加什么、加在哪里」

## 使用示例

**用户输入**：

> review 一下 `konva/doc` 文档质量，参考 `readme.md` 的格式规范

**Skill 执行步骤**：

1. 读取 `readme.md`，提取「学习文档统一格式」中的 7 项格式要素
2. 批量读取 6 篇 doc 文档全文
3. 逐篇按六维度评分，生成格式规范度矩阵表
4. 撰写逐篇亮点/不足
5. 给出整体评价 + 改进建议
6. 输出结论
