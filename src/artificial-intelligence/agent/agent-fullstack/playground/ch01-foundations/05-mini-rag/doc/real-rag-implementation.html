01先想清楚在做什么

RAG 不是「把整篇文档塞进 prompt」，而是把「找依据」和「说人话」拆成两个阶段： 索引期只做一次，查询期每次只处理一个问题。

这条链路里有四个可以独立验证的动作： 切块决定检索单元， 召回决定依据够不够， 编排决定模型看到什么， 评估决定你能不能判断改动有没有用。 练习版把这四件事拆成四个函数，正好一一对应。

维度 练习版 src/index.ts 真实版 src/real-rag/
目的 手写核心算法，建立可提取的记忆 工程分层，接真实依赖
模型 ScriptedModel，按剧本返回 DeepSeek / OpenAI 兼容接口
向量 shared/embed 的哈希词袋 bge-m3，1024 维语义向量
数据 三篇制度文档，硬编码 120 回《三国演义》，按章加载
索引 每次调用现算，数据量小 索引只建一次，交互问答复用
验证 bun test，精确断言 evaluate + 人工检查 + 日志
关于答案 src/real-rag/ 是已经跑通的参考实现。本文档刻意不贴四个练习函数的完整代码， 只给规格、步骤、伪代码和检查点。先做完练习，再打开 real-rag 对照， 否则你只是把「看懂」误当成「会写」。

  3. 测试是契约 不修改 index.test.ts 和 shared/；测试红了先读断言，不要先怀疑测试。
  4. 卡住按级别要提示 提示 1 方向 → 提示 2 关键 API → 提示 3 伪代码。不要直接搜完整实现。
  5. 通过不等于掌握 第二天换一个业务场景，把同一结构重写一遍；第 7 天从空文件重写。

02练习一 · 切块

切块是唯一一个「纯字符串」的步骤，但它决定了后面所有检索的上限： 块太大，召回不精确；块太小，一句话被切断，两边都检索不到。

src/index.ts · 函数签名 
function chunkDocuments(
  docs: Doc[],
  chunkSize = 80,
  chunkOverlap = 20
): Chunk[]

行为规则

  • 步长 = chunkSize - chunkOverlap，按字符窗口切，允许相邻块重叠。
  • 块 id 是 <docId>#<序号>，序号从 0 开始。
  • chunkSize <= 0、chunkOverlap < 0、chunkOverlap >= chunkSize 都抛 RangeError。
  • 空白块没有检索价值：跳过，而且不占用序号。
  • 最后一块可以短于 chunkSize，但不能因为越界产生空块。

验收标准

  • 20 个字符、chunkSize = 10、chunkOverlap = 2，切出 3 块，id 为 a#0、a#1、a#2，最后一块是 ij。
  • 三组非法参数都抛 RangeError。

实现步骤

  1. 先写参数校验 三个条件分别抛错，错误信息带上实际收到的值。不要留到循环里才发现步长为 0。
  2. 外层遍历文档，内层滑动窗口 每篇文档先 trim()；空文档直接跳过。索引变量从 0 开始。
  3. 截取后检查是否空白 用 text.slice(start, start + chunkSize)；空白块跳过，且不要递增序号。
  4. 处理最后一块 slice 越界会自动截断；当 start + chunkSize >= text.length 时结束循环。
  5. 跑测试 bun test ch01-foundations/05-mini-rag -t chunkDocuments，两条都绿再进入下一节。
提示 1 · 方向

把「切块」当成两个独立动作：先算窗口的起点序列，再对每个起点做一次截取。 不要在循环里修改字符串，也不要用正则去切。

提示 2 · 关键 API

String.prototype.slice(start, end)、String.prototype.trim()、 Array.prototype.push()。序号用模板字符串拼： `${doc.id}#${index}`。

提示 3 · 伪代码
step = chunkSize - chunkOverlap for doc of docs: text = doc.text.trim() if text === '' continue index = 0 for start = 0; start < text.length; start += step: piece = text.slice(start, start + chunkSize) if piece.trim() !== '': push { id: `${doc.id}#${index}`, docId: doc.id, text: piece } index += 1 if start + chunkSize >= text.length: break
常见错误
  • 循环条件写成 start <= text.length，多切出一个空块。
  • 空白块也递增 index，导致 id 出现空洞。
  • 先 trim() 整篇文档再按原偏移切，或反过来；两种做法都可以，但要保持一致。
  • 忘记 break 不会死循环，因为步长大于 0，但会多做一次无意义截取。

03练习二 · 召回

召回只做一件事：把问题和每个块都变成向量，算余弦相似度，过滤噪声，取前 K 个。 练习版的向量是哈希词袋，只反映字面重叠，这是刻意的简化。

src/index.ts · 函数签名 
function retrieve(
  question: string,
  chunks: Chunk[],
  topK = 3
): RankedChunk[]

行为规则

  • 用 @/shared/embed 的 embed() 和 cosineSimilarity() 打分。
  • 过滤掉得分低于 0.1 的块，阈值用来过滤哈希碰撞产生的噪声。
  • 按分数降序取前 topK；topK < 1 抛 RangeError。
  • 没有相关块时返回空数组，不要抛错。

验收标准

  • 「年假怎么申请」「报销发票什么时候交」「远程办公每周几天」三条 query 的第一名分别命中 leave、expense、remote。
  • 与语料无重叠的 query 返回空数组。
  • topK = 0 抛 RangeError。

实现步骤

  1. 先校验 topK 放在最前面，避免算完所有向量才发现参数非法。
  2. 问题只向量化一次 answerWithCitations 会反复调用 retrieve，但单次调用里 query 只 embed 一次。
  3. 逐块打分 把每个 chunk 转成 { chunk, score }；score 用余弦相似度。
  4. 过滤、排序、截断 先 filter(score >= 0.1)，再降序，再 slice(0, topK)。顺序不要反。
  5. 跑测试 bun test ch01-foundations/05-mini-rag -t retrieve。
提示 1 · 方向

召回是「问题向量」和「块向量」的批量比较，不是文本匹配。 先理解 embed() 返回什么形状，再决定在哪一层循环。

提示 2 · 关键 API

embed(texts: string[]): number[][]，一次可以传多个文本； cosineSimilarity(a, b): number； toSorted((a, b) => b.score - a.score) 不修改原数组。

提示 3 · 伪代码
if topK < 1: throw RangeError queryVec = embed([question])[0] ranked = [] for chunk of chunks: score = cosineSimilarity(queryVec, embed([chunk.text])[0]) ranked.push({ chunk, score }) return ranked .filter(item => item.score >= 0.1) .toSorted((a, b) => b.score - a.score) .slice(0, topK)
为什么「量子纠缠实验」会返回空 哈希词袋只统计字面 token 的重叠。查询和语料没有任何共同字符时，余弦相似度接近 0， 会被 0.1 阈值过滤掉。这不是 bug，而是练习版的边界； 真实版换成 bge-m3 后，语义相近但字面不同的查询也能召回。

04练习三 · 编排与引用

这一节把前面两个函数串成一条链路，并加上两个真实系统必须有的行为： 没有依据时拒答、答案里的引用能映射回原文。

src/index.ts · 函数签名 
async function answerWithCitations(
  question: string,
  docs: Doc[],
  model: ScriptedModel,
  options?: RagOptions
): Promise<RagAnswer>

行为规则

  • 先切块再召回；一个都没召回时直接返回 知识库中没有找到相关内容。，不调用模型。
  • 上下文每行格式：[序号] (chunkId) 文本，总长不超过 maxContextChars，至少保留一行。
  • 消息为一条 system（只依据资料、用 [序号] 标注引用）+ 一条 user（资料 + 问题）。
  • 模型返回 final 后，从答案里解析 [n]，映射回 chunk id，去重；越界序号忽略。
  • 模型只被调用一次。

上下文长什么样

[1] (leave#0) 员工每年享有 10 天年假，需要提前三天在系统里提交申请。 [2] (expense#0) 差旅报销须在出差结束后 7 天内提交发票，逾期需要主管审批。 [3] (remote#0) 远程办公每周最多两天，需要提前一天获得主管批准。

编号从 1 开始，模型引用 [1] 时，映射的是 chunks[0]。 这个一一对应的关系，是后面解析引用时最容易出错的地方。

实现步骤

  1. 按顺序串起来 切块 → 召回 → 空结果判断 → 拼上下文 → 组装 messages → 调用模型 → 解析引用。
  2. 先在函数内部拼上下文 不要在测试里拼。逐行累加长度，超过预算就停；第一条无论多长都要放进去。
  3. 组装两条消息 system 里写清楚「只依据资料」和「用 [n] 标注」；user 里放资料和问题。
  4. 调用一次模型 model.complete(messages) 返回 { type: 'final', content }；不要循环调用。
  5. 解析并映射引用 content.matchAll(/\[(\d+)\]/g)，序号减 1 取 chunk，去重，越界跳过。
  6. 跑测试 bun test ch01-foundations/05-mini-rag -t answerWithCitations，两条都绿。
提示 1 · 方向

这个函数只负责编排，不负责实现切块和召回。把它写成一条直线： 每一步的输出是下一步的输入，中间只有「空结果」一个分支。

提示 2 · 关键 API

createScriptedModel([final('...')]) 创建剧本模型； model.calls 记录每次 messages； String.prototype.matchAll 返回迭代器，用 for...of 遍历。

提示 3 · 伪代码
chunks = chunkDocuments(docs, chunkSize, chunkOverlap) ranked = retrieve(question, chunks, topK) if ranked.length === 0: return { answer: REFUSAL, citations: [], chunks: [] } lines = [] used = [] length = 0 for item of ranked: line = `[${used.length + 1}] (${item.chunk.id}) ${item.chunk.text}` if lines.length > 0 and length + 1 + line.length > maxContextChars: break lines.push(line) used.push(item.chunk) length += (lines.length === 1 ? 0 : 1) + line.length messages = [ { role: 'system', content: '只依据资料作答，用 [n] 标注引用...' }, { role: 'user', content: `资料：\n${lines.join('\n')}\n\n问题：${question}` } ] result = model.complete(messages) citations = [] for match of result.content.matchAll(/\[(\d+)\]/g): chunk = used[Number(match[1]) - 1] if chunk and not citations.includes(chunk.id): citations.push(chunk.id) return { answer: result.content, citations, chunks: used }
验收时看什么
  • 答案里出现 [1] 时，citations 等于对应 chunk id。
  • model.calls.length 恰好为 1；无召回时为 0。
  • user 消息里能看到 [1] 标记和原始问题。

05练习四 · 评估

评估不是「跑几个例子看看」，而是用带标注的用例算一个可比较的数字。 练习版只算命中率，但已经足够暴露切块和 topK 的问题。

src/index.ts · 函数签名 
function evaluate(
  cases: Array<{ query: string; expectedDocId: string }>,
  docs: Doc[],
  options?: RagOptions
): { hits: number; total: number; hitRate: number }

行为规则

  • 每条用例召回后，只要任意一个 chunk 的 docId 等于 expectedDocId，就算命中。
  • hitRate = hits / total；total 为 0 时返回 0。
  • 只评估检索，不调用对话模型。

实现步骤

  1. 先切一次块 所有用例共用同一批 chunks，不要每条用例重新切。
  2. 逐条召回并判断 用 ranked.some(item => item.chunk.docId === expectedDocId)。
  3. 处理空用例 total === 0 时直接返回 hitRate: 0，避免除零。
  4. 跑测试 bun test ch01-foundations/05-mini-rag -t evaluate，三条用例全部命中。
练习通过后 把 topK 改成 1、把 chunkSize 改成 20，各跑一次评估， 观察命中率怎么变。这比继续加功能更能建立「参数 → 指标」的直觉。

06从练习到真实版

练习版是「一个文件里塞下整条链路」；真实版要解决的是网络、配置、复用和可观测性。 拆文件的判断标准只有一条：如果两个代码块的修改原因不同，它们就不该待在同一个文件。

DEPENDENCY

依赖方向是单向的

main → rag → prompt / model / retriever / embedding / chunker；所有模块只依赖 contracts/types。没有环。

INDEX ONCE

索引只建一次

整本书 1909 块向量化约 95 秒；交互问答必须复用索引，每次只向量化问题。

BOUNDARY

协议细节不外泄

只有 providers/model.ts 和 providers/embedding.ts 知道 OpenAI SDK；generation/rag.ts 只认内部消息类型。

FALLBACK

配置缺失要早失败

对话 Key 缺失在启动时抛错；向量 Key 缺失时退回本地哈希，保证离线可跑。

想完全手写真实版 不要直接改 src/real-rag/，否则你会失去可对照的答案。 建议新建 src/real-rag-practice/，按下一节顺序逐个文件写； 每写完一个，再打开 src/real-rag/ 对应文件对照。

07真实版逐层实现

按依赖顺序从底向上写：先定契约，再写配置和数据层，最后写编排和入口。 每个小节给出任务、验收和常见错误；完整答案在 src/real-rag/。

7.1 contracts/types.ts · 契约层

先把所有流转的数据形状定下来，不写逻辑。真实版和练习版最大的不同是 RagOptions 多了 minScore 和 expandToDocs， RagAnswer 多了 ranked（带相似度的召回结果）。

src/real-rag/contracts/types.ts · 关键契约 
export interface RagOptions {
  topK?: number
  chunkSize?: number
  chunkOverlap?: number
  maxContextChars?: number
  minScore?: number
  expandToDocs?: boolean
}

export const DEFAULT_RAG_OPTIONS: Required<RagOptions> = {
  topK: 3,
  chunkSize: 400,
  chunkOverlap: 80,
  maxContextChars: 2000,
  minScore: 0.1,
  expandToDocs: false
}

export interface RagAnswer {
  answer: string
  citations: string[]
  chunks: Chunk[]
  ranked: ScoredChunk[]
  usage?: TokenUsage
}

验收：不 import 任何运行时模块；所有其他文件都能只依赖这个文件拿到类型。

7.2 config/env.ts · 配置层

对话模型和向量模型分开配置。对话 Key 缺失时立刻抛错，不要等到第一次请求； 向量 Key 缺失时返回 null，由调用方退回本地哈希。 DeepSeek 只提供 chat，没有 /embeddings，所以向量要单独配。

验收：删掉 OPENAI_API_KEY 启动时立即报「缺少 OPENAI_API_KEY」；删掉 EMBEDDING_API_KEY 时自动走哈希向量。

7.3 ingest/chunker.ts · 切块层

和练习一的算法一致，只是默认值从 80/20 变成 400/80，参数从 DEFAULT_RAG_OPTIONS 取。 先校验，再滑动窗口；空白块跳过且不占序号。

验收：120 回语料切出 1909 块；第一块 id 是 第一回#0，最后一块是 第一百二十回#20。

7.4 providers/embedding.ts · 向量层

定义一个 Embedder 接口，两个实现： 本地 FNV-1a 哈希词袋（零依赖、确定性）和 OpenAI 兼容 /embeddings。 API 版必须分批：整本书一千多块，一次发完会超限也会超时。

interface Embedder { readonly id: string embed(texts: string[]): Promise<number[][]> } EMBED_BATCH_SIZE = 64 for start in 0..texts.length step 64: batch = texts.slice(start, start + 64) response = client.embeddings.create({ model, input: batch }) push response.data sorted by index

验收：日志里 embedder id 是 bge-m3；1909 块约 95 秒；返回向量数等于输入数。

7.5 retrieval/retriever.ts · 检索层

三件事：cosineSimilarity、indexChunks、search。 建索引只做一次；查询时只向量化问题，然后打分、过滤、排序、截断。

验收：维度不一致时抛 RangeError；零向量返回 0；topK < 1 抛错；检索耗时 20-30ms。

7.6 retrieval/prompt.ts · 提示词层

三块内容：系统提示、上下文拼接、引用解析。真实版多了 expandToDocs： 把召回的小块按 docId 聚合，同一文档内多个命中的分数相加， 再按总分取整篇，直到用完上下文预算。

buildContext(ranked, maxChars): for item of ranked: line = `[${used.length + 1}] (${item.chunk.id}) ${item.chunk.text}` 第一条无论多长都放；后续超预算就停 return { text, used } parseCitations(answer, used): for match of answer.matchAll(/\[(\d+)\]/g): chunk = used[Number(match[1]) - 1] 越界跳过；重复只保留第一次 expandToDocs(ranked, docs, maxChars): 按 docId 累加分数 按总分降序 每篇截到剩余预算，放满为止

验收：答案里的 [1] 能映射到上下文第一条；越界序号不产生引用；整回聚合后「诸葛亮之死」能答出来。

7.7 providers/model.ts · 协议层

只负责一次 Chat Completions 调用：发出去、收回来、映射 usage。 它不知道 RAG，也不知道循环；换供应商时只改这里。

验收：返回 { content, usage }；temperature = 0；响应缺少 choices[0].message 时抛错。

7.8 generation/rag.ts · 编排层

唯一知道整条链路长什么样：切块 → 建索引 → 召回 → 空结果拒答 → 拼上下文 → 调模型 → 解析引用。 AnswerDeps 支持注入 embedder 和已建好的 index，交互问答才不会每次重算。

验收：无召回时返回固定拒答且不调用模型；传入 index 时不再向量化文档；expandToDocs 为真时上下文是整章。

7.9 evaluation/eval.ts · 评估层

只评估检索：建一次索引，所有用例共用；逐条召回，任意 chunk 命中期望 docId 就算命中。 返回 hits、total、hitRate、misses。

验收：三条制度用例全命中；misses 能定位未命中的 query。

7.10 cli/main.ts · 入口

加载语料 → 打印章数和字数 → 建一次索引 → 单问或进入交互循环。 每个问题都复用索引，只向量化 query；输出召回片段、引用、上下文篇章和 token 用量。

验收：bun run cli/main.ts "问题" 能回答；不带问题进入交互模式；exit 退出。

08接真实语料与 bge-m3

这一节把制度文档换成《三国演义》，把哈希向量换成 bge-m3。 数据从哪来、章节怎么切、索引为什么慢、召回为什么会答偏，都在这里。

8.1 语料：任意 UTF-8 txt

RAG 的数据就是你能读到的文本。小说完全可以，建议用公版书（《三国演义》、 Project Gutenberg、中文维基文库）或自己的笔记。中文 txt 常见 GBK 编码， 先用 file -I 文件名.txt 检查，必要时 iconv 转 UTF-8。

本项目使用的是 1.7 MB、UTF-8、120 回、60.2 万字的《三国演义》，放在：

src/real-rag/data/sanguo.txt

ingest/corpus.ts 读取文件后做三件事：去掉 BOM、统一换行、按 ^第[〇零一二三四五六七八九十百千两0-9]+[回章] 切分。 每回变成一个 Doc，id 就是「第一回」「第二回」这样的回目。

为什么不按固定长度切 Doc 按回切分保留了章节语义：引用能直接定位到回目，整回聚合时也有明确的父文档边界。 固定长度切 Doc 会让引用变成「第 37 块」，对小说没有意义。

8.2 向量服务：bge-m3

本机原生 Ollama 已安装并拉取 bge-m3（1024 维，约 1.16 GB）。 macOS 上原生 Ollama 走 Metal；Docker 版用不了 GPU，还会多一份镜像和模型，不建议。

src/real-rag/.env 
OPENAI_API_KEY=...            # 对话模型
OPENAI_BASE_URL=https://api.deepseek.com
DEFAULT_MODEL=deepseek-v4-flash

EMBEDDING_API_KEY=ollama
EMBEDDING_BASE_URL=http://localhost:11434/v1
EMBEDDING_MODEL=bge-m3

验证端点是否可用：

终端 
curl -s http://localhost:11434/v1/embeddings \
  -H "Content-Type: application/json" \
  -d '{"model":"bge-m3","input":["年假怎么申请"]}'

返回的 data[0].embedding 应该是 1024 个数。 ollama ps 可以看到模型当前加载了多少、占多少显存、还有多久卸载。

8.3 分批与耗时

1909 个块如果一次发给 /embeddings，请求体过大，服务端会拒绝或超时。 providers/embedding.ts 按 64 条一批发送，30 批左右完成。

指标 实测值 说明
语料 120 回 / 602,198 字 UTF-8，1.7 MB
切块 1909 块 400 字 / 80 重叠
建索引 95 秒左右 bge-m3，M1 Max，Ollama 原生
单次检索 20-30 ms 1909 条向量暴力余弦
单次回答 1-2 秒 含一次对话模型调用

8.4 为什么答偏，以及怎么修

只用 dense 向量时，召回会把「语义相近但词面不精确」的块排前面。 实测「赤壁之战是谁放的火」召回的是第五十回（战后清点），而不是第四十九回（三江口纵火）。 这不是向量库能修的，Qdrant 只负责存和查，不改变排序质量。

真实版用了一个最简单的「小块召回、整篇喂模型」： expandToDocs 先按 docId 聚合分数，再把命中回的整章文本放进上下文。 这样「诸葛亮最后是怎么死的」虽然只召回到第一百四回末尾的碎片， 整回上下文里仍然包含五丈原病逝的完整段落。

召回 topK=12 个小块 → 按 docId 累加分数 → 按总分降序取回 → 每回截到剩余预算（总预算 12000 字） → 作为上下文送入模型

想进一步提升，下一步不是换数据库，而是混合检索： 把 dense 分数和 BM25 / 字符 bigram 的稀疏分数融合，或者加一个 rerank 模型。 这些改动都能用 evaluate 的命中率验证。

8.5 CLI 的两种用法

终端 · 在 src/real-rag 目录

# 单问：进程结束就退出，下次启动会重新建索引

10验收与进阶

验收清单

  • 四个练习函数全部实现，bun test ch01-foundations/05-mini-rag 全绿。
  • 能解释为什么索引只建一次，以及查询期只 embed 问题。
  • 能解释 [1] 如何映射到 used[0]，越界为什么忽略。
  • 能在真实版里换一本书，只改语料路径就能跑。
  • 能说出「赤壁」答偏的原因，以及为什么 Qdrant 不解决它。

进阶顺序

  1. 评估集 给三国语料写 10-20 条 query → 期望回目，跑 evaluate，得到 baseline hitRate。
  2. 混合检索 dense + 字符 bigram BM25，用 RRF 或加权融合；对比 baseline。
  3. Rerank 召回 top20 后用交叉编码器重排，观察命中率和延迟的取舍。
  4. 索引缓存 把向量写成 Float32Array 二进制，按语料 hash + 模型 id 失效，省掉 95 秒重建。
  5. Qdrant 只有需要持久化、metadata 过滤、十万级以上规模时才上；它不会自动提升排序。
学习节奏 当天闭卷写完并通过测试；第 2 天换一个业务场景重写核心 30 行； 第 7 天从空文件重写，并用 90 秒讲清「为什么这样设计」。
