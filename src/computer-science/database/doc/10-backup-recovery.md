## 1. 备份分层：从"定期导出"到"任意时间点"

| 层级 | 工具 | 能还原到 | 成本 |
|------|------|---------|------|
| **逻辑备份** | `pg_dump` | 某个时刻的"整库快照" | 低，天级 |
| **物理备份 + WAL 归档** | `pg_basebackup` + `archive_mode` | **任意时间点（PITR）** | 中 |
| **流复制** | `pg_standby` / 云托管从库 | 秒级丢数据的近实时 | 高 |
| **云托管自动备份** | RDS/Neon/Supabase 内置 | PITR + 自动周期 | 折中 |

> 💡 演进路线（贴合你的真实工程）：**开发库 → 定时 pg_dump；生产 → 云托管自动备份 + PITR；再往后才考虑自建从库。** "先 PG 后专用"同样适用备份——自己搭全套只在你明确"云不可用"或"成本>人力"时。

## 2. 逻辑备份：pg_dump 一条命令讲清

```bash
# 打包成自定义格式（压缩、可选表、可并行恢复）
pg_dump -h localhost -U shop_app -d shop -Fc -f shop.dump

# 恢复（新库先建好）：--jobs 并行加速
createdb -h localhost -U postgres shop_restored
pg_restore -h localhost -U postgres -d shop_restored --jobs=4 shop.dump

# 只要一张表 / 只要结构
pg_dump -h localhost -U shop_app -d shop -t orders -Fc -f orders.dump
pg_dump -h localhost -U shop_app -d shop --schema-only -f schema_only.sql   # 只结构
```

三个使用要点：

- **`-Fc` 自定义格式**是恢复的黄金选择：压缩、可选表、`--jobs` 并行、可中途互动；
- 恢复前确认**目标库表结构与应用角色**（第 8 章最小权限的"新库要补授权"同理）；
- 数据量 > 几十 GB 后逻辑备份变慢，就该考虑物理层级。

```sql
-- 兄弟工具：COPY 单表导出/导入（CSV 场景）
COPY orders TO STDOUT WITH (FORMAT csv, HEADER);
COPY orders FROM STDIN WITH (FORMAT csv, HEADER);
```

## 3. 物理备份与 PITR：日志重放救回最后 5 分钟

要讲清楚"任意时间点恢复"，只需一句话模型：

> **全量备份（某个时刻的照片）+ WAL 日志（之后每一笔操作）→ 恢复 = 照片 + 按时间重放日志。**

```bash
# 1. 开启 WAL 归档（postgresql.conf）
archive_mode = on
archive_command = 'test ! -f /backup/archive/%f && cp %p /backup/archive/%f'

# 2. 做一次基础备份（照片）
pg_basebackup -h localhost -D /backup/base -Fp -Xs

# 3. 误删后：应用全量 + 重放到事故前一刻
pg_ctl -D /backup/base 启动前，把 archive/ 里的 WAL 按顺序重放，停在目标时间
```

PITR 的工程定位一句话：**它不是高频操作，是"出了事能保住最后一段数据"的保险**。自建需要规划归档目录、备份机、演练；云托管把这套打包成"控制台点个时间点、恢复、克隆"。

> ⚠️ 自建 PITR 的灵魂是**定期演练**——备份不行=没有备份。每月挑一个时间真的恢复一次，验证归档链路没断。

## 4. 流复制 / 只读副本 / 读写分离：概念定位

| 术语 | 是什么 | 解决什么 |
|------|--------|---------|
| 流复制 | 主库把 WAL 流式推给从库 | **灾备**：主挂从顶上（RPO≈秒级） |
| 只读副本 | 从库可对外提供只读查询 | **读扩展**：报表/读多写少减主库压力 |
| 读写分离 | 应用把读路由到副本 | 架构层配合，读写一致性要自己权衡 |

> ⚠️ **坑**：主从是异步时，副本读到的是**落后数据**。别拿副本给"用户刚提交的订单"查询——一致性要求高的读留在主库（或者忍几毫秒延迟）。这是大部分"做了读写分离第一次事故"的根源。

## 5. 你的实操建议（直接照做）

| 场景 | 做法 |
|------|------|
| 本地/开发库 | cron 每天 `pg_dump -Fc`，保留 7 天 |
| Docker 学习环境 | `-v` 挂载数据卷，另定期 dump 到宿主 |
| 生产自建 | `pg_basebackup` 日级 + WAL 归档 + 季度演练 |
| 生产云托管 | 开自动备份 + PITR，只读副本按查询压力再加 |

> 兜底心法：**"能在异地再挖出一份库"才算备份。** 备份文件放完全不依赖本机的介质（对象存储/另一台机），否则"服务器没了备份也没了"。

## 🎯 练习

**要求**：完整走一遍第 2 节流程——`pg_dump -Fc` 整库 → drop 掉 `shop` 库 → `pg_restore` 到新库 `shop_restored` → 跑一条业务 SQL 验证数据一致；再做一次 `--schema-only` 备份和单表恢复。

**提示**：drop 库需要没有连接占用（退出 psql 或删掉 `pg_stat_activity` 里相关连接）；恢复后记得把应用角色授权补上（第 8 章）。

**预期效果**：`shop_restored` 里的订单样例数据完好，`SELECT count(*) FROM orders` 与恢复前一致——**你现在可以说"我的数据不依赖这台机器"了**。

## 🎤 面试问答

> **问：逻辑备份和物理备份有什么区别？**
> **答：** 逻辑备份（pg_dump）导出的是 SQL/自定义格式数据，**跨版本、跨机性好、可选择性导出**，但大表慢；物理备份（pg_basebackup 拷贝数据文件）是**位级一致**、快，但只能同版本同平台、恢复粒度更粗。二者用途不同：前者日常+迁移，后者宽灾难快速恢复。
>
> **问：PITR 是怎么工作的？**
> **答：** 三步模型：基础备份（全量快照）+ WAL 归档（之后所有变更的日志）+ 恢复时重放日志到指定时间点。所以 **RPO（丢多少数据）取决于 WAL 归档频率**。
>
> **问：读写分离带来了什么坑？**
> **答：** 主从异步复制下副本**数据滞后**，刚写的查询可能查不到——一致性敏感场景需强路由。其次要警惕副本上跑重型报表把实例拖垮。
>
> **追问：备份要多久验一次？**
> **答：** 定时（月度/每季）完整恢复演练。备份从没有被恢复成功过 = 不是备份，是心理安慰。云托管同样要主动做一下"恢复/克隆到测试环境"验证。

## 🔁 对比板块：逻辑备份 vs 物理备份 vs 云托管自动备份

| 维度 | pg_dump（逻辑） | pg_basebackup（物理） | 云托管自动备份 |
|------|----------------|----------------------|----------------|
| 速度 | 大表慢 | 快（拷贝文件） | 厂商实现 |
| 版本迁移 | ✅ 可跨版本 | ❌ 必须同版本 | 厂商支持 |
| 选表恢复 | ✅ | ❌ 全量 | 往往全量 |
| PITR | ❌（除非配 WAL） | ✅（+ 归档） | ✅ 开箱 |
| 演练成本 | 低 | 中 | 中（点按钮） |

> 一句话：**自己管自建 → 逻辑备份保底 + 物理并行；能选云托管 → 自动备份 + PITR 是最优解**，省下的运维时间去做演练和核对。
