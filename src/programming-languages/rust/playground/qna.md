## Q3：`todo!()` 是什么意思？它没有声明，为什么能编译过？

**日期**：2026-10-05 · **场景**：第一次打开 [[playground/README|练习]]，看到 `let mut count: i32 = todo!()`

**一句话**：`todo!()` 不是函数，是**宏**；它能编译过，是因为它的类型是 `!`（never type），可以协变成任何类型。

三个关键点：

1. **宏不是函数**。带 `!` 的都是宏（[[doc/01-basic-syntax|doc §1.2]] 的 `println!` 同款），由编译器在编译期直接展开，无需声明。`todo!()` 在标准库 **prelude** 里，默认就在作用域，连 `use` 都不用写。
2. **类型 `!` 万能协变**。`!` 的含义是"这行永远不会正常产生值"，所以它能协变成任何类型：

   ```rust
   let mut count: i32 = todo!();       // ! 协变成 i32 ✓
   fn foo() -> String { todo!() }      // ! 协变成 String ✓
   ```

   这就是练习册"交付即可编译"的原理——`todo!()` 占着任意类型的位置，类型检查完全通过。
3. **panic 推迟到运行期**。`todo!()` 展开后就是 `panic!("not yet implemented")`，但只有**真正执行到那一行**才炸。所以练习每实现一个 todo，程序往前多走一步，✅ 逐个亮起。

宏家族速查：

| 宏 | 语义 | 使用场景 |
|---|---|---|
| `todo!()` | "还没写" | 练习/开发占位 |
| `unimplemented!()` | "故意留空的功能" | 同上，更正式的措辞 |
| `unreachable!()` | "逻辑上不可能到达" | 防御性编程，到达即 bug |
| `panic!()` | "立即崩溃" | 不可恢复错误的最终手段 |

**动手验证**：跑 `cargo run -p ch01-syntax --bin ex01-variables-shadowing` 观察 panic 输出；把 L14 换成 `0` 再跑，看程序推进到任务 2。

## Q2：直接在练习文件上写答案吗？会不会破坏测试题？

**日期**：2026-10-04 · **场景**：准备开始做第一题

**一句话**：在 `playground-work/` 副本里直接写；`playground/` 是 git 管理的 pristine 题库，破坏不了。

- **原地写是设计如此**：rust-analyzer 实时反馈 + `cargo run` 验证的循环，复制文件到别处反而丢掉这套体验
- **副本模式**：`playground/`（题库，入库）+ `playground-work/`（答题副本，已 gitignore）
- **复原 ch01~05**：从题库 rsync 覆盖副本，支持全量或单章，命令见 [[playground/README|作答工作流]]
- **评估过的替代方案**：`git restore` 单文件重置（git-native 但重做整章麻烦）、`practice` 分支（保留答题轨迹但多一步切换）——最终选了副本模式，最省心

⚠️ 副本不入库：换设备后重新 rsync 一次即可，想留答案轨迹需自行备份。

## Q1：有没有必要为 doc 目录设计一个 playground 练习册？

**日期**：2026-10-04 · **场景**：读完 doc/01、doc/02，犹豫要不要动手

**一句话**：有必要，但做成轻量「练习册」而不是重项目。

- **doc 是输入，所有权光读不练等于没学**——outline 里"多写多编译"的落地就缺一个和文档进度对齐的动手层
- **外部 Rustlings 不贴合**：题目顺序和自己的 6 章划分对不上；自建练习可按 doc 小节逐节出题，做完即读完
- **与 CLI TODO 互补不重复**：CLI TODO 是第 11-12 天的综合 capstone，playground 填 1-10 天的逐章练习空白
- **落地形态**：cargo workspace，每章一个 crate；练习 = `todo!()` 脚手架 + 🧪 编译错误实验（E0382/E0502/E0597…）+ 可运行的 `solutions/`

后续演进见 [[playground/README|README]]：ch03~05 已补齐，下一站是 doc/05.5 的 CLI TODO 综合项目。
