## 3. React DevTools

React DevTools 可以查看组件树、Props、State、Hooks，用法跟 Web 完全一样。

### 3.1 启动方式

```bash
# 独立运行（推荐）
npx react-devtools

# 或者在 Flipper 中以插件形式使用
```

启动后自动连接到设备上的 RN 应用（需要在同一网络）。

### 3.2 核心功能

| 功能 | 说明 |
|------|------|
| 组件树 | 查看完整的组件层级结构 |
| Props/State | 实时查看和修改组件的 props 和 state |
| Hooks | 查看每个 Hook 的当前值 |
| Profiler | 录制渲染性能，找出重渲染瓶颈 |
| 搜索 | 按组件名搜索 |

### 3.3 Profiler 使用技巧

```
Profiler 录制结果：
┌──────────────────────────────────────────┐
│  Flamegraph 视图                          │
│                                           │
│  App          [8ms]                       │
│    └─ Header   [2ms]                      │
│    └─ List     [5ms]  ← 耗时最多           │
│       ├─ Item   [0.3ms] × 50              │
│       └─ Footer [0.2ms]                   │
│                                           │
│  Ranked 视图（按渲染时间排序）               │
│  1. List        5ms    render 2 times     │
│  2. Header      2ms    render 1 time      │
│  3. Item        0.3ms  render 150 times   │
└──────────────────────────────────────────┘
```

**找出重渲染原因**：开启 "Record why each component rendered while profiling"，可以看到每个组件因为什么触发了重渲染（props 变化、state 变化、父组件重渲染等）。

## 4. Flipper

Flipper 是 Meta 出品的桌面调试平台，通过插件支持网络、存储、布局等多种调试。

### 4.1 安装与连接

1. 下载 [Flipper](https://fbflipper.com/)
2. 启动模拟器/连接真机
3. Flipper 自动发现设备和应用

### 4.2 核心插件

| 插件 | 功能 | 使用场景 |
|------|------|---------|
| **Network** | 查看所有 HTTP 请求 | 接口调试、查看请求/响应 |
| **Databases** | 查看 AsyncStorage / SQLite / MMKV 数据 | 本地存储调试 |
| **Layout Inspector** | 查看原生视图层级和样式 | 布局问题排查 |
| **Images** | 查看图片缓存 | 图片加载问题 |
| **Crash Reporter** | 查看崩溃日志 | 排查崩溃 |
| **React DevTools** | 集成版 React DevTools | 一站式调试 |

### 4.3 Network 插件

Flipper 的 Network 插件可以直接拦截 RN 的所有网络请求：

```
请求列表：
┌───────────────────────────────────────────────┐
│ Method │ URL                │ Status │ Time   │
│ GET    │ /api/users         │ 200    │ 120ms  │
│ POST   │ /api/login         │ 401    │ 85ms   │ ← 失败，点击查看
│ GET    │ /api/articles      │ 200    │ 230ms  │
└───────────────────────────────────────────────┘

点击请求 → 查看：
- Request Headers / Body
- Response Headers / Body
- Timing（DNS/TCP/TLS/响应）
```

> **注意**：RN 0.73+ 的新架构下，部分 Flipper 插件可能需要额外配置。如果 Flipper 连不上，检查 `metro.config.js` 中是否正确配置了 Flipper 的端口。

## 6. 性能调试

### 6.1 Perf Monitor

在开发者菜单中打开 "Show Perf Monitor"，显示：

```
┌────────────────────┐
│ FPS: 58    JS: 5ms │  ← JS 线程每帧耗时
│ UI: 3ms   Mem: 85M │  ← UI 线程耗时 + 内存
└────────────────────┘
```

| 指标 | 健康值 | 警告值 |
|------|-------|-------|
| FPS | 55-60 | < 30 明显卡顿 |
| JS 线程 | < 16ms | > 16ms 会掉帧 |
| 内存 | < 200MB | > 300MB 需要排查 |

### 6.2 常见性能问题

| 问题 | 现象 | 排查方式 |
|------|------|---------|
| 列表卡顿 | 滚动时 FPS 骤降 | Profiler 看 FlatList renderItem 耗时 |
| 页面切换慢 | 导航动画掉帧 | 检查目标页面的渲染量 |
| 内存泄漏 | 用久了越来越卡 | Flipper Memory 插件跟踪 |
| JS 线程阻塞 | 点击后延迟响应 | 检查 onPress 中的同步计算 |
| 大量重渲染 | FPS 低但 UI 线程正常 | React DevTools Profiler |

### 6.3 why-did-you-render

```bash
npm install @welldone-software/why-did-you-render
```

```tsx
// 在入口文件顶部（仅开发环境）
if (__DEV__) {
  const whyDidYouRender = require('@welldone-software/why-did-you-render');
  whyDidYouRender(React, { trackAllPureComponents: true });
}
```

它会在控制台打印每次不必要的重渲染及原因。

## 7. 构建：Expo 项目

### 7.1 EAS Build（推荐）

Expo 的云构建服务，不需要本地安装 Xcode / Android Studio。

```bash

```

      "developmentClient": true,
      "distribution": "internal"
    },

      "distribution": "internal",
      "android": { "buildType": "apk" }
    },
    "production": {

```bash
# 构建 Android APK（测试用）
eas build --platform android --profile preview

# 构建 Android AAB（上架用）
eas build --platform android --profile production

# 构建 iOS
eas build --platform ios --profile production

# 同时构建双端
eas build --platform all --profile production
```

## 8. 构建：Bare Workflow 项目

### 8.1 Android 构建

```bash
cd android

# Debug 版本
./gradlew assembleDebug
# 产物：android/app/build/outputs/apk/debug/app-debug.apk

# Release 版本
./gradlew assembleRelease
# 产物：android/app/build/outputs/apk/release/app-release.apk

# AAB（Google Play 要求）
./gradlew bundleRelease
# 产物：android/app/build/outputs/bundle/release/app-release.aab
```

### 8.2 Android 签名配置

```properties
# android/gradle.properties
MYAPP_RELEASE_STORE_FILE=my-release-key.keystore
MYAPP_RELEASE_KEY_ALIAS=my-key-alias
MYAPP_RELEASE_STORE_PASSWORD=*****
MYAPP_RELEASE_KEY_PASSWORD=*****
```

> ⚠️ **安全提醒**：以上将密码写在 `gradle.properties` 中仅为示例。生产环境**不要将密码提交到 Git**，推荐使用环境变量或 CI 密钥：
> ```bash
# 在 CI 中注入环境变量
export MYAPP_RELEASE_STORE_PASSWORD=${{ secrets.KEYSTORE_PASSWORD }}
```
> ```properties
# gradle.properties（只读变量名，不留值）
MYAPP_RELEASE_STORE_PASSWORD=\${env.MYAPP_RELEASE_STORE_PASSWORD}
```

```groovy
// android/app/build.gradle
android {
    signingConfigs {
        release {
            storeFile file(MYAPP_RELEASE_STORE_FILE)
            storePassword MYAPP_RELEASE_STORE_PASSWORD
            keyAlias MYAPP_RELEASE_KEY_ALIAS
            keyPassword MYAPP_RELEASE_KEY_PASSWORD
        }
    }
    buildTypes {
        release {
            signingConfig signingConfigs.release
            minifyEnabled true
            proguardFiles getDefaultProguardFile('proguard-android-optimize.txt'), 'proguard-rules.pro'
        }
    }
}
```

```bash
# 生成签名密钥
keytool -genkeypair -v -storetype PKCS12 -keystore my-release-key.keystore -alias my-key-alias -keyalg RSA -keysize 2048 -validity 10000
```

### 8.3 iOS 构建

## 9. 发布上架

### 9.1 上架前检查清单

| 项目 | 说明 |
|------|------|
| App 图标 | 1024x1024 PNG，iOS 需要额外尺寸（EAS 自动生成） |

```

### 9.3 Google Play 上架

```
上架流程：
1. 注册 Google Play 开发者账号（$25 一次性）
2. 创建应用 → 填写基本信息
3. 上传 AAB 文件（App Bundle）
4. 填写内容评级问卷
5. 设置定价和分发区域
6. 提交审核（通常 1-3 天）
```

```bash
# EAS Submit 自动上传
eas submit --platform android

# 或手动上传到 Google Play Console
```

### 9.4 App Store 上架

```
上架流程：
1. 注册 Apple Developer Program（$99/年）
2. 在 App Store Connect 创建应用
3. 填写应用信息（描述、截图、分类、关键词）
4. 上传构建产物（通过 Xcode 或 EAS Submit）
5. 填写审核信息（测试账号、隐私政策等）
6. 提交审核（通常 1-3 天，首次可能更久）
```

```bash
# EAS Submit 自动上传到 App Store Connect
eas submit --platform ios
```

### 9.5 App Store 审核常见拒绝原因

| 原因 | 说明 | 解决方案 |
|------|------|---------|
| 崩溃或 Bug | 审核时 App 崩溃 | 充分测试后再提交 |
| 隐私问题 | 缺少隐私政策或权限说明 | 补充完整的隐私政策 URL |
| 元数据不符 | 截图与实际界面不符 | 用真实截图 |
| 未登录功能 | 审核人员无法体验核心功能 | 提供测试账号 |
| 引导付费 | 未使用 Apple 内购 | 数字内容必须用 IAP |
| 性能差 | 启动慢或卡顿 | 优化启动时间和渲染性能 |

## 10. OTA 热更新

### 10.1 Expo Updates（EAS Update）

Expo 的 OTA 热更新方案，不需要重新发版就能修复 JS 层的 Bug。

```bash
# 发布热更新
eas update --branch production --message "修复登录 Bug"
```

### 10.2 热更新原理

```
App 启动
  ↓
检查是否有新的 JS Bundle
  ↓
有 → 下载新 Bundle → 替换本地 → 加载新代码
没有 → 加载本地 Bundle

注意：只能更新 JS 代码，不能更新原生代码
```

### 10.3 热更新 vs 发版

| 维度 | OTA 热更新 | 发版（App Store） |
|------|----------|------------------|
| 更新内容 | JS/TS 代码 | 任意（包括原生代码） |
| 用户感知 | 无感（下次打开生效） | 需要手动更新 |
| 审核 | 不需要 | 需要 App Store 审核 |
| 回滚 | 即时回滚 | 需要重新发版 |
| 限制 | 不能改原生代码 | 无限制 |

> **重要**：Apple 允许 OTA 热更新，但要求不能改变 App 的主要功能或绕过审核。只用于 Bug 修复和小功能调整是合规的。

## 📝 面试回答模板

> **问：RN 中怎么调试？**
>
> 分四个层次。最基础的是 Metro 终端看 console.log，所有日志直接输出在这里。第二层是 React DevTools，可以查看组件树、Props、State 和 Hooks，用 Profiler 录制渲染性能找出重渲染瓶颈。第三层是 Flipper，它的 Network 插件可以拦截所有 HTTP 请求，Databases 插件可以查看本地存储。第四层是 Chrome DevTools 或 VS Code 调试器做断点调试。实际开发中，80% 的问题用前两层就能解决。

> **问：RN App 怎么上架到应用商店？**
>
> Android 上架 Google Play：用 EAS Build 或 Gradle 构建 AAB 文件，在 Google Play Console 创建应用、填写信息、上传 AAB、提交审核（通常 1-3 天）。iOS 上架 App Store：用 EAS Build 或 Xcode Archive，在 App Store Connect 创建应用、填写信息、上传构建产物、提交审核（通常 1-3 天）。上架前需要准备好 App 图标、截图、隐私政策 URL、权限说明等材料。Expo 项目用 EAS Build + EAS Submit 可以全程在命令行完成，不需要本地安装 Xcode。

> **问：OTA 热更新是怎么实现的？Apple 允许吗？**
>
> OTA 热更新的原理是：App 启动时检查服务端是否有新的 JS Bundle，如果有就下载替换本地的，下次打开就加载新代码。它只能更新 JS/TS 层的代码，不能更新原生代码。Apple 允许热更新，但要求不能改变 App 的主要功能或绕过审核流程——只用于 Bug 修复和小功能调整是合规的。Expo 的 EAS Update 是官方的热更新方案，支持按分支发布、即时回滚、增量更新。
