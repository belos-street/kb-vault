# 13 — 新手高频坑点与解决方案

> 对应大纲：工程层 · 速查 | 预计时间：1 天
> 面试可答：Electron 新手最常踩的坑包括：打包后路径失效（`__dirname` 在 asar 中的行为）、CORS 跨域问题（file:// 协议的限制）、preload 脚本打包后路径错误、原生模块编译失败（node-gyp / ABI 不匹配）、macOS 签名和公证流程复杂。解决方案是：用 `app.getPath` 管理资源路径、用 Vite/Webpack 统一构建 main/renderer/preload、原生模块用 prebuild 或 electron-rebuild。

## 1. 路径问题

### 1.1 `__dirname` 在开发 vs 打包后的差异

```
开发时：
  src/main.ts  →  __dirname = /project/src/
  src/preload.ts →  __dirname = /project/src/

打包后（asar 压缩包内）：
  app.asar/main.js  →  __dirname = /path/to/app.asar/
  app.asar/preload.js →  __dirname = /path/to/app.asar/
```

### 1.2 正确的路径处理方式

```typescript
import { app } from 'electron';
import path from 'node:path';

// ❌ 硬编码相对路径
const iconPath = './assets/icon.png';

// ❌ 依赖 __dirname（打包后可能在 asar 内）
const iconPath = path.join(__dirname, 'assets', 'icon.png');

// ✅ 使用 app.getAppPath()（asar 自动解包）
const iconPath = path.join(app.getAppPath(), 'assets', 'icon.png');

// ✅ 对于用户数据，使用 app.getPath
const dbPath = path.join(app.getPath('userData'), 'data.db');

// ✅ 对于资源文件，使用 path.join + process.resourcesPath
const resourcePath = path.join(process.resourcesPath, 'assets', 'icon.png');
```

### 1.3 路径速查表

| 场景 | 推荐方式 | 说明 |
|------|---------|------|
| 应用内资源（图标、HTML） | `path.join(app.getAppPath(), ...)` | asar 内自动处理 |
| 用户数据（配置、数据库） | `path.join(app.getPath('userData'), ...)` | 用户目录下 |
| 临时文件 | `path.join(app.getPath('temp'), ...)` | 系统临时目录 |
| 打包后的额外资源 | `path.join(process.resourcesPath, ...)` | asar 外 |

### 1.4 asar 压缩包问题

Electron 默认将应用代码打包为 `app.asar`（一个压缩的归档文件）。

```typescript
// asar 内的文件可以正常读取
const content = fs.readFileSync(path.join(app.getAppPath(), 'config.json'), 'utf-8');

// 但某些场景需要 asar 外的文件：
// 1. 原生模块（.node 文件）
// 2. 子进程的可执行文件
// 3. 需要修改的文件

// 解决：将这些文件放在 extraResources 中
// forge.config.ts
{
  packagerConfig: {
    extraResource: ['./assets/native-module.node'],
  },
}
```

## 2. CORS 跨域问题

### 2.1 问题描述

当渲染进程加载本地 `file://` 协议的页面时，请求远程 API 会遇到 CORS 错误：

```
Access to fetch at 'https://api.example.com' from origin 'null' 
has been blocked by CORS policy
```

### 2.2 解决方案

**方案一：主进程代理请求（推荐）**

让主进程负责所有 HTTP 请求，渲染进程通过 IPC 调用，这是 Electron 中处理网络请求的最佳实践：

```typescript
// 主进程：代理 API 请求
ipcMain.handle('api:fetch', async (_event, url: string, options?: RequestInit) => {
  const response = await fetch(url, options);
  const data = await response.json();
  return { status: response.status, data };
});

// 渲染进程：通过 IPC 请求，不直接 fetch
const result = await window.electronAPI.apiFetch('https://api.example.com/data');
```

为什么推荐主进程代理？

| 优势 | 说明 |
|------|------|
| 无 CORS 问题 | 主进程是 Node.js 环境，不受浏览器同源策略限制 |
| 更安全 | API token、密钥等凭据只存在主进程中，XSS 无法窃取 |
| 更灵活 | 可用 Node.js 的 `fetch`、`got` 等库，支持更多协议特性 |
| 统一管控 | 请求/响应拦截、错误处理、重试逻辑集中在一处 |

> **注意**：每次请求都要经过 IPC 序列化/反序列化，对高频请求有额外开销。WebSocket 和 Server-Sent Events 等场景见下方特殊处理。

**方案二：加载 localhost 服务器**

```typescript
// 开发环境：Vite dev server
win.loadURL('http://localhost:5173');

// 生产环境：启动本地服务器
import express from 'express';
const server = express();
server.use(express.static(path.join(__dirname, 'renderer')));
server.listen(0, () => {
  const port = server.address().port;
  win.loadURL(`http://localhost:${port}`);
});
```

**方案三：禁用 webSecurity（不推荐）**

```typescript
// ❌ 仅开发环境临时使用
webPreferences: {
  webSecurity: false,  // 禁用同源策略
}
```

### 2.3 特殊场景：WebSocket 与流式请求

WebSocket 不受 CORS 限制，渲染进程可以直接连接：

```typescript
// 渲染进程直接建立 WebSocket 连接（无需主进程代理）
const ws = new WebSocket('wss://api.example.com/ws');
ws.onmessage = (event) => console.log(event.data);
```

对于 SSE（Server-Sent Events）等需要主进程代理的流式场景，可以通过 IPC 分块推送：

```typescript
// 主进程：流式读取后分块推送给渲染进程
ipcMain.handle('api:stream', async (event, url: string) => {
  const response = await fetch(url);
  const reader = response.body!.getReader();
  const decoder = new TextDecoder();

  while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    event.sender.send('api:stream-chunk', decoder.decode(value));
  }

  event.sender.send('api:stream-end');
});

// 渲染进程：监听流式数据
window.electronAPI.onStreamChunk((chunk) => {
  output.textContent += chunk;
});
```

## 3. preload 脚本打包后失效

### 3.1 问题描述

使用 Vite/Webpack 构建时，preload 脚本需要单独的构建配置。如果 preload 和渲染进程共用一个构建配置，打包后 preload 可能无法正常工作。

### 3.2 正确的 Vite 配置

```typescript
// vite.preload.config.ts
import { defineConfig } from 'vite';

export default defineConfig({
  build: {
    lib: {
      entry: 'src/preload.ts',
      formats: ['cjs'],  // preload 必须是 CJS 格式
      fileName: 'preload',
    },
    outDir: 'out/preload',
    rollupOptions: {
      external: ['electron'],  // 不打包 electron
    },
    ssr: true,  // Node.js 环境
  },
});
```

### 3.3 正确的路径引用

```typescript
// main.ts 中引用 preload
const preloadPath = path.join(__dirname, 'preload.js');

// ❌ 开发时可以，打包后不行
const preloadPath = path.join(__dirname, '../preload/preload.js');

// ✅ 根据环境判断
const preloadPath = app.isPackaged
  ? path.join(__dirname, 'preload.js')     // 打包后：同一目录
  : path.join(__dirname, '../preload/preload.js');  // 开发时：相对路径
```

## 4. Native Node.js 模块编译

### 4.1 常见编译失败场景

| 错误 | 原因 | 解决方案 |
|------|------|---------|
| `node-gyp` 编译失败 | 缺少编译工具链 | macOS: `xcode-select --install`；Windows: 安装 Visual Studio Build Tools（C++ 桌面开发工作负载）+ Python 3 |
| `MODULE_VERSION` 不匹配 | Node ABI 版本不一致 | 使用 `electron-rebuild` |
| `prebuild` 找不到对应版本 | Electron 版本太新/太旧 | 手动编译或降级 Electron |
| `sharp` 安装失败 | 平台架构不匹配 | `npm install --platform=darwin --arch=arm64 sharp` |

### 4.2 electron-rebuild

```bash
npm install --save-dev @electron/rebuild

# 重新编译所有原生模块
npx electron-rebuild

# 在 package.json 中添加 postinstall
{
  "scripts": {
    "postinstall": "electron-rebuild"
  }
}
```

### 4.3 prebuild / prebuildify

`prebuildify` 让原生模块作者预编译各平台的二进制文件，用户安装时直接下载，无需本地编译：

```bash
# 如果原生模块支持 prebuildify，安装时会自动下载预编译的二进制
npm install better-sqlite3  # 自动下载预编译版本
```

### 4.4 N-API / node-addon-api

N-API（Node-API）是 Node.js 的稳定 ABI 接口，一次编译可以在多个 Node.js 版本上运行：

```cpp
// 使用 N-API 的原生模块不需要针对每个 Electron 版本重新编译
// 推荐优先选择支持 N-API 的原生模块
```

### 4.5 Electron 版本与 Node ABI 对应关系

```bash
# 查看当前 Electron 使用的 Node ABI 版本
npx electron -e "console.log(process.versions.modules)"
# Electron 43（Node 24） → Node ABI 137
# Electron 35（Node 22） → Node ABI 127
# Electron 33（Node 20） → Node ABI 115
```

> 规律：Electron 30~34 捆绑 Node 20（ABI 115），35~39 捆绑 Node 22（ABI 127），40~43 捆绑 Node 24（ABI 137）。同一 Node 大版本内 ABI 不变，跨大版本才需要重新编译。完整映射见官方仓库 electron/node-abi 的 abi_registry.json。

### 4.6 常用原生模块速查

| 模块 | 用途 | prebuild 支持 | N-API 支持 |
|------|------|:---:|:---:|
| `better-sqlite3` | SQLite 数据库 | ✅ | ❌（ABI 特定） |
| `sharp` | 图片处理 | ✅ | ✅ |
| `node-pty` | 伪终端 | ✅ | ❌ |
| `ffi-napi` | 调用动态库 | ✅ | ✅ |
| `keytar` | 系统密钥链 | ✅ | ✅ |
| `serialport` | 串口通信 | ✅ | ✅ |

## 5. macOS 签名与公证

### 5.1 常见错误

**错误 1："App is damaged and can't be opened"**

原因：应用未签名，macOS Gatekeeper 阻止运行。
解决：配置代码签名（需要 Apple Developer 账号）。

**错误 2："App can't be opened because the developer cannot be verified"**

原因：应用已签名但未公证。
解决：完成公证流程（`xcrun notarytool submit`）。

**错误 3：开发阶段如何跳过签名**

```bash
# 临时允许未签名应用
xattr -cr /path/to/MyApp.app

# 或者在系统偏好设置中允许
```

## 6. Windows 杀毒软件误报

### 6.1 问题描述

未签名的 Electron 应用在 Windows 上经常被杀毒软件标记为病毒。

### 6.2 解决方案

1. **代码签名**：购买 EV 证书（Extended Validation），杀毒软件对 EV 签名的信任度更高
2. **提交白名单**：向杀毒软件厂商提交应用，申请加入白名单
3. **NSIS 打包**：使用 NSIS 安装包格式（而不是便携版），减少误报
4. **更新 Electron**：使用最新版 Electron，已知漏洞会被杀软标记

## 8. 常见错误速查表

| 错误信息 | 原因 | 解决方案 |
|---------|------|---------|
| `require is not defined` | 渲染进程不能 require（nodeIntegration: false） | 通过 preload + contextBridge 暴露 API |
| `Cannot find module` | 模块路径错误或未安装 | 检查 import 路径，运行 npm install |
| `ERR_FILE_NOT_FOUND` | 文件路径错误 | 检查 `__dirname`、`app.getAppPath()` |
| `net::ERR_FAILED` | CORS 跨域请求被阻止 | 主进程代理或加载 localhost |
| `MODULE_VERSION` 不匹配 | 原生模块 ABI 不兼容 | `npx electron-rebuild` |
| `A JavaScript error occurred` | 主进程未捕获异常 | 添加 `process.on('uncaughtException')` |
| 白屏 | 页面加载失败 | 检查 loadFile/loadURL 路径、检查 CSP |
| 窗口不显示 | `show: false` 后忘记调用 `win.show()` | 在 `ready-to-show` 中调用 `win.show()` |

## 📝 面试回答模板

> **问：Electron 打包后最常见的问题是什么？**
>
> 最常见的三个问题是路径、CORS 和原生模块。路径问题是因为 `__dirname` 在打包后指向 asar 压缩包内部，需要使用 `app.getAppPath()` 处理应用资源，`app.getPath('userData')` 处理用户数据。CORS 问题是本地 file:// 协议请求远程 API 被阻止，解决方案是主进程代理请求或加载 localhost 服务器。原生模块问题是 ABI 版本不匹配，用 `electron-rebuild` 重新编译。

> **问：如何处理 Electron 中的原生模块？**
>
> 原生模块（如 better-sqlite3、sharp）需要针对 Electron 的 Node.js 版本重新编译。三个解决方案：1）`electron-rebuild` 自动重新编译所有原生模块；2）选择支持 prebuildify 的模块，安装时直接下载预编译的二进制文件；3）选择支持 N-API 的模块，一次编译可以在多个 Node.js 版本上运行。打包时需要注意原生模块的 .node 文件不能放在 asar 内，需要通过 `asarUnpack` 或 `extraResource` 配置。

> **问：macOS 和 Windows 开发 Electron 应用有什么主要差异？**
>
> 五个主要差异：1）菜单栏——macOS 在屏幕顶部，Windows 在窗口内，macOS 第一个菜单项会被系统替换为应用名；2）关闭行为——macOS 关闭窗口不退出应用（需要 Cmd+Q），Windows 关闭窗口就退出；3）签名——macOS 需要 Developer ID 证书 + 公证，Windows 需要 EV 证书；4）路径——macOS 用 `/`，Windows 用 `\`，用 `path.join` 自动适配；5）通知——macOS 需要应用签名才能正常显示通知。
