# 10 — 安全进阶与反模式排查

> 对应大纲：工程层 | 预计时间：1 天
> 面试可答：Electron 官方安全清单（Security Checklist）现行 20 条，核心是"最小权限"——渲染进程不应有 Node.js 能力，所有 IPC 通道应经过审查并校验 sender，远程内容应受 CSP 限制。CSP 高级配置包括 nonce（一次性脚本标识）和 hash（脚本内容哈希），比 `'unsafe-inline'` 更安全。安全审计时重点排查：`nodeIntegration` 是否关闭、preload 是否暴露了通用 invoke、CSP 是否配置、IPC handler 是否校验 sender、fuses 是否按生产要求配置、第三方依赖是否有已知漏洞。

> 本篇是 05 安全基础的进阶，适合在写完应用层功能后回来深入学习。

## 1. Electron 官方安全清单（Security Checklist）

Electron 官方 Security 文档列出了 **20 条**安全最佳实践（早期版本为 8 条，后持续扩充）。完整清单如下，随后对其中最关键的条目逐一解读：

| # | 准则 | 一句话说明 |
|---|------|-----------|
| 1 | 只加载安全的内容 | 不要加载不可信的远程 URL |
| 2 | 远程内容禁用 nodeIntegration | 加载远程内容时 nodeIntegration 必须为 false |
| 3 | 启用 context isolation | 保持默认值 true（Electron 12+ 默认开启） |
| 4 | 启用进程沙箱 | 保持 sandbox 开启（Electron 20+ 渲染进程默认沙箱化） |
| 5 | 安全处理 session 权限请求 | 用 setPermissionRequestHandler 白名单审批 |
| 6 | 不要禁用 webSecurity | 禁用会关闭同源策略 |
| 7 | 定义安全的 CSP | 配置 Content-Security-Policy 头或 meta |
| 8 | 不要启用 allowRunningInsecureContent | 禁止 HTTPS 页面加载 HTTP 脚本 |
| 9 | 不要启用实验性功能 | experimentalFeatures 保持关闭 |
| 10 | 不要启用 allowBlinkFeatures | 不要开启额外的 Blink 特性 |
| 11 | WebView 不要启用 allowpopups | 使用 `<webview>` 时禁止弹窗 |
| 12 | 校验 WebView 创建选项 | 创建 webview 前检查并清理 options |
| 13 | 限制 navigation | 用 will-navigate 白名单拦截导航 |
| 14 | 限制新窗口创建 | 用 setWindowOpenHandler 控制 window.open |
| 15 | shell.openExternal 只用白名单 URL | 防止被诱导打开恶意协议/链接 |
| 16 | 使用当前版本的 Electron | 及时升级，旧版本有已知漏洞 |
| 17 | 校验所有 IPC 消息的 sender | 只响应来自可信 webContents 的 IPC |
| 18 | 避免 file://，优先自定义协议 | 自定义协议可精细控制访问范围 |
| 19 | 检查 fuses 配置 | 生产环境按需配置 Electron fuses |
| 20 | 不要向不可信内容暴露 Electron API | preload 暴露面遵循最小化原则 |

> 其中 #2/#3/#4 已在 05 篇详解，#13/#14 即下文 1.6 节。下面对剩余关键条目展开。

### 1.1 只加载安全的内容（主进程 · BrowserWindow 配置）

主进程负责创建窗口并决定渲染进程加载什么内容。`win.loadURL()` / `win.loadFile()` 虽然在主进程中调用，但直接影响渲染进程加载的页面。

```typescript
// ❌ 危险：渲染进程加载远程不可信内容
win.loadURL('https://some-random-website.com');

// ❌ 危险：渲染进程加载用户提供的 URL（可能被注入恶意站点）
win.loadURL(userProvidedURL);

// ✅ 安全：渲染进程加载本地打包的 HTML
win.loadFile(path.join(__dirname, 'renderer', 'index.html'));

// ✅ 安全：渲染进程加载可信的自有服务
win.loadURL('https://app.yourcompany.com');
```

如果必须加载远程内容，应该：
- 验证 URL 白名单
- 配置严格的 CSP
- 使用 `webContents.on('will-navigate')` 阻止意外导航

### 1.2 不要禁用 webSecurity（主进程 · webPreferences 配置）

在主进程创建 BrowserWindow 时设置，影响渲染进程的安全策略。

```typescript
// ❌ 永远不要这样做
webPreferences: {
  webSecurity: false,  // 渲染进程禁用同源策略 → 允许任意跨域请求
}

// ✅ 保持默认
webPreferences: {
  webSecurity: true,   // 渲染进程保持同源策略
}
```

### 1.3 不要设置 allowRunningInsecureContent（主进程 · webPreferences 配置）

在主进程创建 BrowserWindow 时设置，控制渲染进程是否允许混合内容。

```typescript
// ❌ 渲染进程中 HTTPS 页面可以加载 HTTP 资源（中间人攻击风险）
webPreferences: {
  allowRunningInsecureContent: true,
}

// ✅ 保持默认
webPreferences: {
  allowRunningInsecureContent: false,
}
```

### 1.4 不要启用 nodeIntegration（主进程 · webPreferences 配置 → 影响渲染进程）

在主进程创建 BrowserWindow 时设置，决定渲染进程是否可以直接 `require()` Node.js 模块。

已在 05 篇详细讲解。核心：`nodeIntegration: false`（默认值）。

### 1.5 不要禁用 contextIsolation（主进程 · webPreferences 配置 → 影响 preload + 渲染进程）

在主进程创建 BrowserWindow 时设置，决定 preload 脚本和渲染进程的 JS 上下文是否隔离。

已在 05 篇详细讲解。核心：`contextIsolation: true`（默认值）。

### 1.6 限制 navigation 能力（主进程 · 监听 webContents 事件）

主进程监听渲染进程的导航事件，防止渲染进程被导航到不可信的页面：

```typescript
win.webContents.on('will-navigate', (event, url) => {
  // 只允许导航到白名单 URL
  const allowed = ['http://localhost:5173', 'https://app.yourcompany.com'];
  const isAllowed = allowed.some((prefix) => url.startsWith(prefix));

  if (!isAllowed) {
    event.preventDefault(); // 阻止导航
    console.warn('阻止导航到:', url);
  }
});

// 阻止新窗口打开（除非是可信 URL）
win.webContents.setWindowOpenHandler(({ url }) => {
  if (url.startsWith('https://yourcompany.com')) {
    return { action: 'allow' };
  }
  // 用默认浏览器打开外部链接
  shell.openExternal(url);
  return { action: 'deny' };
});
```

### 1.7 使用 session 的 will-download 处理下载（主进程 · session 事件）

主进程监听渲染进程中触发的下载事件，控制下载行为和保存路径。

```typescript
win.webContents.session.on('will-download', (event, item) => {
  // 设置下载路径
  const savePath = path.join(app.getPath('downloads'), item.getFilename());
  item.setSavePath(savePath);

  item.on('done', (_event, state) => {
    if (state === 'completed') {
      console.log('下载完成:', savePath);
    }
  });
});
```

### 1.8 自定义协议要安全地处理内容（主进程 · protocol 模块）

主进程中注册自定义协议时，应验证请求来源，防止渲染进程通过自定义协议加载恶意内容。

> **注意**：早期的 `protocol.registerHttpProtocol` / `registerFileProtocol` 等 `register*` 系列 API 自 Electron 25 起已弃用（由 `protocol.handle` 取代），新代码一律使用 `protocol.handle`。

自定义协议应设置适当的安全头：

```typescript
protocol.handle('my-protocol', (request) => {
  // 验证请求来源
  const url = new URL(request.url);
  if (url.hostname !== 'trusted-source') {
    return new Response('Forbidden', { status: 403 });
  }
  // 返回内容...
});
```

## 2. CSP 高级配置

### 2.1 Nonce 模式（主进程生成 → 注入渲染进程 HTML）

主进程生成 nonce，通过 IPC 传给渲染进程的 HTML `<meta>` 标签。浏览器只执行带有正确 nonce 的 `<script>` 标签。

```typescript
// 主进程：生成 nonce
import crypto from 'node:crypto';

function generateNonce(): string {
  return crypto.randomBytes(16).toString('base64');
}

ipcMain.handle('get-nonce', () => generateNonce());
```

```html
<head>
  <meta http-equiv="Content-Security-Policy"
    content="script-src 'nonce-{NONCE}'">
</head>
<body>
  <!-- ✅ 带正确 nonce 的脚本可以执行 -->
  <script nonce="{NONCE}">
    console.log('这个脚本有正确的 nonce');
  </script>

  <!-- ❌ 没有 nonce 的脚本被阻止 -->
  <script>
    console.log('这个脚本没有 nonce，会被 CSP 阻止');
  </script>
</body>
```

### 2.2 Hash 模式

如果脚本内容固定，可以用 hash：

```html
<meta http-equiv="Content-Security-Policy"
  content="script-src 'sha256-{HASH}'">
```

计算 hash：

```bash
echo -n "console.log('hello')" | openssl dgst -sha256 -binary | base64
```

### 2.3 违规上报（report-to）

`report-uri` 指令已被 CSP3 的 `report-to` 取代。桌面应用中更实用的做法是在渲染进程监听 `securitypolicyviolation` 事件，将违规事件转发到主进程记录：

```typescript
// 渲染进程：监听 CSP 违规并上报（logCspViolation 由 preload 通过 contextBridge 暴露）
document.addEventListener('securitypolicyviolation', (e) => {
  window.electronAPI?.logCspViolation?.({
    directive: e.violatedDirective,   // 被违反的指令，如 'script-src'
    blockedURI: e.blockedURI,         // 被阻止的资源
    sourceFile: e.sourceFile,         // 违规发生的文件
  });
});
```

### 2.4 严格 CSP 配置模板

```typescript
// 生产环境严格 CSP
const strictCSP = [
  "default-src 'self'",
  "script-src 'self'",
  "style-src 'self' 'unsafe-inline'",
  "img-src 'self' data: blob:",
  "font-src 'self'",
  "connect-src 'self'",
  "media-src 'self'",
  "object-src 'none'",
  "base-uri 'self'",
  "form-action 'self'",
  "frame-ancestors 'none'",
  "upgrade-insecure-requests",
].join('; ');
```

## 3. 常见安全反模式排查清单

### 3.1 致命级反模式（必须修复）

| 反模式 | 所在进程 | 风险 | 修复 |
|--------|---------|------|------|
| `nodeIntegration: true` | 主进程配置 → 影响渲染进程 | XSS → RCE | 改为 `false`（默认） |
| `contextIsolation: false` | 主进程配置 → 影响 preload + 渲染进程 | preload API 被劫持 | 改为 `true`（默认） |
| 暴露整个 `ipcRenderer` | preload 脚本 | 渲染进程可发送任意 IPC | 只暴露特定方法 |
| 暴露通用 `invoke(channel)` | preload 脚本 | 渲染进程可调用任意 handler | 只暴露特定 channel |
| 加载不可信远程 URL | 主进程（`win.loadURL`） | 远程页面可执行恶意代码 | 配置 CSP + URL 白名单 |

### 3.2 高危级反模式（强烈建议修复）

| 反模式 | 所在进程 | 风险 | 修复 |
|--------|---------|------|------|
| `webSecurity: false` | 主进程配置 → 影响渲染进程 | 允许任意跨域请求 | 保持 `true` |
| 未配置 CSP | 主进程或渲染进程 HTML | XSS 攻击无防护 | 添加严格 CSP |
| IPC handler 未校验输入 | 主进程 | 路径遍历、注入攻击 | 添加输入校验 |
| `innerHTML` 插入未转义内容 | 渲染进程 | XSS | 使用 `textContent` 或转义 |
| 使用 `eval()` | 渲染进程 | 代码注入 | 使用 `JSON.parse` 等替代 |

### 3.3 中危级反模式（建议修复）

| 反模式 | 所在进程 | 风险 | 修复 |
|--------|---------|------|------|
| 未限制 `will-navigate` | 主进程 | 渲染进程可导航到恶意站点 | 添加 URL 白名单 |
| 未处理 `setWindowOpenHandler` | 主进程 | 弹出新窗口加载恶意内容 | 拦截并验证 URL |
| 未清理 IPC 监听器 | 渲染进程 / preload | 内存泄漏 | 添加清理逻辑 |
| preload 中存储敏感数据 | preload 脚本 | XSS 可窃取 | 敏感数据存主进程 |

### 4.4 审计 Electron 特有的依赖风险

| 依赖类型 | 运行位置 | 风险 | 建议 |
|---------|---------|------|------|
| 原生模块（node-gyp） | 主进程 | 可执行任意 C++ 代码 | 选择维护活跃、下载量大的库 |
| Electron 相关库 | 主进程 / preload | 可能绕过安全配置 | 检查是否修改了 webPreferences |
| 远程代码执行类库 | 渲染进程 | eval、vm2 等 | 避免使用，或限制输入来源 |

## 6. 安全编码 Code Review 检查点

### 6.1 新功能上线前的安全审查清单

## 📝 面试回答模板

> **问：Electron 官方的安全准则有哪些？**
>
> 官方 Security Checklist 现行 20 条（早期是 8 条，后持续扩充），核心思想是"最小权限"。最重要的几条是：1）不要启用 `nodeIntegration`，防止 XSS 升级为 RCE；2）不要禁用 `contextIsolation`，防止 preload API 被页面脚本劫持；3）保持渲染进程沙箱开启（Electron 20+ 默认）；4）不要禁用 `webSecurity`，保持同源策略；5）限制渲染进程的导航能力，通过 `will-navigate` 和 `setWindowOpenHandler` 阻止加载不可信内容；6）校验所有 IPC 消息的 sender，只响应可信窗口；7）生产环境检查 fuses 配置。此外还有配置 CSP、处理下载安全、审计第三方依赖等。这些准则形成多层防御，即使一层被突破，其他层仍然能保护用户。

> **问：CSP 的 nonce 和 hash 模式有什么区别？**
>
> nonce 是每次请求生成的随机字符串，只有标签上带正确 nonce 的脚本才能执行，适合动态生成的脚本。hash 是对脚本内容计算 SHA-256 哈希，只有内容匹配的脚本才能执行，适合内容固定的脚本。两者都比 `'unsafe-inline'` 安全——`unsafe-inline` 允许所有内联脚本，等于没有防护。在 Electron 中，如果使用 Vite/Webpack 打包，通常所有 JS 都打包到外部文件，`script-src 'self'` 就够了，不需要 nonce 或 hash。

> **问：如何审计 Electron 项目的第三方依赖安全性？**
>
> 三个层面：第一，`npm audit` 检查已知漏洞，CI/CD 中可以 `npm audit --audit-level=high` 只关注高危漏洞。第二，审查依赖类型——原生模块（node-gyp 编译的）风险最高，因为它们可以执行任意 C++ 代码；Electron 相关库需要检查是否修改了安全配置。第三，锁定版本——用 `package-lock.json` 锁定精确版本，CI 中用 `npm ci` 而不是 `npm install`，避免自动升级引入问题。
