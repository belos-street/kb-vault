## 一、CSS 工程化要解决什么问题

原生 CSS 是一门"全局的、无作用域的、声明式的"语言，直接用于大型项目会遇到四类问题：

| 问题 | 表现 | 典型场景 |
|------|------|---------|
| **命名冲突** | 全局选择器互相覆盖，改一处崩一片 | 多团队协作、引入第三方库 |
| **样式复用** | 复制粘贴样式代码，改一处漏十处 | 多个页面有相似卡片/按钮 |
| **代码组织** | 单文件上万行，不知道样式在哪、谁在用 | 老项目维护 |
| **产物体积** | 历史样式不敢删，CSS 越积越大 | 首屏加载慢 |

**所有 CSS 工程化方案，本质都是在回答两个问题：**

1. **作用域怎么隔离？**（BEM 约定 / CSS Modules 编译 / CSS-in-JS 运行时 / 原子化不存在冲突）
2. **样式怎么组织？**（按组件 / 按层级 / 按功能原子）

## 二、BEM 命名规范

BEM = **B**lock（块）+ **E**lement（元素）+ **M**odifier（修饰符），是最经典的 CSS 命名约定。

### 2.1 命名规则

```css
/* Block：独立的功能组件 */
.search-form { }

/* Element：Block 的组成部分，用双下划线连接 */
.search-form__input { }
.search-form__button { }

/* Modifier：状态或变体，用双连字符连接 */
.search-form--disabled { }
.search-form__button--primary { }
```

### 2.2 核心原则

```html
<!-- ✅ 元素只属于直接的 Block，不嵌套命名 -->
<div class="search-form">
  <div class="search-form__field">
    <input class="search-form__input" />  <!-- 不写 search-form__field__input -->
  </div>
</div>

<!-- ✅ 状态用 Modifier，不用单独的类名或 !important -->
<button class="btn btn--primary btn--loading">提交</button>
```

```css
.btn { padding: 8px 16px; border-radius: 4px; }
.btn--primary { background: #1677ff; color: #fff; }
.btn--loading { opacity: 0.6; pointer-events: none; }
```

### 2.3 BEM 的取舍

- **优点**：零构建依赖、类名即文档（看类名就知道层级和状态）、优先级扁平（全是单类选择器，特异性一致）
- **缺点**：类名长、HTML 冗长；只解决命名冲突，不解决复用和组织问题
- **适用**：原生 CSS 项目、需要长期维护且无构建流程的场景

> BEM 是一种**约定**，靠团队自觉遵守；CSS Modules 用**编译**强制实现同样的隔离。

## 三、CSS Modules：编译时作用域

### 3.1 基本原理

CSS Modules 在构建时把类名编译成唯一哈希，实现局部作用域：

```css
/* button.module.css */
.button { padding: 8px 16px; }
.primary { background: #1677ff; }
```

```jsx
// Button.jsx
import styles from './button.module.css';

function Button({ variant }) {
  // 编译后：styles.button → "button_button_x7s2d"
  return (
    <button className={`${styles.button} ${styles[variant]}`}>
      提交
    </button>
  );
}
```

编译产物：

```css
.button_button_x7s2d { padding: 8px 16px; }
.button_primary_k9f3a { background: #1677ff; }
```

### 3.2 关键语法

```css
/* :global 声明全局样式（用于覆盖第三方库） */
.wrapper :global(.ant-modal-body) {
  padding: 0;
}

/* composes 实现样式复用（类似继承，但是编译时组合） */
.base { padding: 8px 16px; border-radius: 4px; }
.primary {
  composes: base;
  background: #1677ff;
}
```

### 3.3 优势与局限

| 优势 | 局限 |
|------|------|
| 类名自动隔离，杜绝冲突 | 动态类名需 `styles[...]` 查表，略繁琐 |
| 与组件文件同目录，组织清晰 | 无法处理运行时动态样式（如根据 props 算颜色） |
| 构建时完成，零运行时开销 | 类名哈希导致调试时需 source map |
| Vite / webpack / Next.js 均原生支持 | 全局样式（reset、主题）仍需单独处理 |

> **Vite 中约定**：`*.module.css` 自动启用 CSS Modules，无需额外配置。

## 四、预处理器与 PostCSS

### 4.1 Sass / Less：编译时增强

预处理器在 CSS 语法之上增加变量、嵌套、混入、函数等编程能力：

```scss
// Sass 示例
$primary: #1677ff;
$radius: 4px;

@mixin flex-center {
  display: flex;
  align-items: center;
  justify-content: center;
}

.card {
  border-radius: $radius;

  &__title {           // 嵌套 + & 父选择器
    @include flex-center;
    color: $primary;
  }

  &:hover {
    box-shadow: 0 4px 12px rgb(0 0 0 / 0.15);
  }
}
```

**Sass 与 Less 对比**：

| 维度 | Sass (SCSS) | Less |
|------|-------------|------|
| 生态 | 更成熟，社区更大 | Ant Design 早期使用 |
| 功能 | 函数/混入/模块系统更强 | 够用，语法更接近 CSS |
| 现状 | 仍是主流选择 | 新项目较少采用 |

> **注意**：随着 CSS 原生能力增强（自定义属性、`color-mix()`、原生嵌套、`@layer`），预处理器的很多功能已可被原生替代。新项目建议**优先原生 CSS + 构建工具**，只在需要大量混入复用时引入 Sass。

### 4.2 CSS 原生嵌套（Baseline 2023-12）

```css
/* 现代浏览器已原生支持，无需预处理器 */
.card {
  border-radius: 4px;

  & .title { color: var(--primary); }
  &:hover { box-shadow: 0 4px 12px rgb(0 0 0 / 0.15); }

  @media (width <= 600px) {
    padding: 8px;
  }
}
```

### 4.3 PostCSS：CSS 的"babel"

PostCSS 本身**不是**预处理器，而是一个 CSS 转换管道——通过插件对 CSS AST 做任意变换：

```js
// postcss.config.js
export default {
  plugins: {
    'postcss-preset-env': { stage: 1 },  // 把新语法降级为兼容写法
    autoprefixer: {},                     // 自动加浏览器前缀
    cssnano: {},                          // 压缩优化
  },
};
```

常见插件：

| 插件 | 作用 |
|------|------|
| `autoprefixer` | 根据 browserslist 自动添加 `-webkit-` 等前缀 |
| `postcss-preset-env` | 让你提前使用未来 CSS 语法并自动降级 |
| `cssnano` | 压缩、合并、优化产物 |
| `postcss-px-to-viewport` | px 自动转 vw（移动端适配） |

> **定位区分**：Sass 是"增强语言"，PostCSS 是"转换管道"。Tailwind CSS、Autoprefixer 底层都是 PostCSS 插件。

## 五、CSS-in-JS

### 5.1 运行时方案（styled-components / Emotion）

样式写在 JS 中，运行时生成 `<style>` 标签注入：

```jsx
import styled from 'styled-components';

const Button = styled.button`
  padding: 8px 16px;
  background: ${props => props.primary ? '#1677ff' : '#f0f0f0'};
  color: ${props => props.primary ? '#fff' : '#333'};

  &:hover { opacity: 0.85; }
`;

function App() {
  return <Button primary>提交</Button>;
}
```

**优势**：样式与逻辑同文件、props 驱动的动态样式、自动作用域、死代码消除。

**代价**：

- 运行时开销（序列化样式、插入 style 标签）
- SSR 需要额外配置抽取样式
- React 18+ 并发渲染下有序列化瓶颈

### 5.2 零运行时方案（vanilla-extract / Linaria / Panda CSS）

构建时把 JS 样式**编译成静态 CSS 文件**，运行时零开销：

```ts
// button.css.ts（vanilla-extract）
import { style, styleVariants } from '@vanilla-extract/css';

const base = style({
  padding: '8px 16px',
  borderRadius: 4,
});

export const button = styleVariants({
  default: [base, { background: '#f0f0f0' }],
  primary: [base, { background: '#1677ff', color: '#fff' }],
});
```

```jsx
import * as styles from './button.css';

function Button({ variant = 'default' }) {
  return <button className={styles.button[variant]}>提交</button>;
}
```

### 5.3 CSS-in-JS 的现状（2024-2026）

- styled-components / Emotion 维护趋缓，React 官方文档已不再推荐运行时方案
- **趋势**：零运行时编译方案（vanilla-extract、Panda CSS）或回归原子化 CSS（Tailwind）
- Next.js App Router 官方明确不支持运行时 CSS-in-JS 的 SSR

> **选型建议**：新项目优先 Tailwind / CSS Modules / vanilla-extract；存量 styled-components 项目可渐进迁移。

## 六、原子化 CSS

### 6.1 核心思想

不再写"语义化类名 + 自定义样式"，而是直接组合**预定义的原子工具类**：

```html
<!-- 传统写法 -->
<button class="btn btn-primary">提交</button>
<style>
  .btn { padding: 8px 16px; border-radius: 4px; }
  .btn-primary { background: #1677ff; color: #fff; }
</style>

<!-- 原子化写法（Tailwind） -->
<button class="px-4 py-2 rounded bg-blue-500 text-white hover:opacity-85">
  提交
</button>
```

### 6.2 Tailwind CSS 关键机制

```js
// tailwind.config.js
export default {
  theme: {
    extend: {
      colors: {
        brand: {
          500: '#1677ff',   // 生成 bg-brand-500、text-brand-500 等
        },
      },
      spacing: { 18: '4.5rem' },
    },
  },
};
```

```html
<!-- 变体：响应式 / 状态 / 暗色，都是前缀 -->
<div class="flex-col sm:flex-row dark:bg-gray-900 group-hover:visible">
  <span class="group-hover:underline">悬停组内显示下划线</span>
</div>

<!-- 任意值：跳出预设刻度 -->
<div class="w-[37rem] text-[#bada55]">自定义</div>
```

**Tailwind 4.0（2025）变化**：配置从 JS 迁移到 CSS-first：

```css
@import "tailwindcss";

@theme {
  --color-brand-500: #1677ff;
}
```

### 6.3 UnoCSS：即时原子化引擎

UnoCSS 不预设工具类，而是按**规则引擎**即时生成，性能更高、可扩展：

```ts
// uno.config.ts
import { defineConfig, presetUno, presetAttributify } from 'unocss';

export default defineConfig({
  presets: [presetUno(), presetAttributify()],
  rules: [
    // 自定义规则：m-任意数字 → margin
    [/^m-(\d+)$/, ([, d]) => ({ margin: `${Number(d) * 4}px` })],
  ],
});
```

```html
<!-- attributify 模式：原子类写成属性，HTML 更清爽 -->
<button bg="blue-500" text="white sm" p="x-4 y-2">提交</button>
```

### 6.4 原子化 CSS 的取舍

| 优势 | 代价 |
|------|------|
| 彻底杜绝命名冲突（不存在自定义类名） | HTML 类名长，可读性依赖团队习惯 |
| 样式天然复用，产物体积极小且随规模趋于恒定 | 复杂组件需 `@apply` 或组件抽象 |
| 删除 HTML 即删除样式，无死代码 | 设计约束强，自由定制需 escape hatch（任意值） |
| 响应式/状态变体统一、可枚举 | 与现有语义化 CSS 体系混用需约定边界 |

> **实践共识**：原子类用于**布局与间距**，复杂交互样式抽成组件（Vue SFC / React 组件 + 少量自定义 CSS）。

## 七、CSS 架构方法论

### 7.1 ITCSS（倒三角 CSS）

按**特异性从低到高**分层组织，越往下越具体，保证样式只向下覆盖：

```
┌─────────────────────────────┐
│ Settings    变量、Token（无 CSS 输出） │
│ Tools       混入、函数（无 CSS 输出） │
│ Generic     reset / normalize        │
│ Elements    裸标签默认样式（h1、a）    │
│ Objects     结构性布局（.o-layout）    │  ← 不带视觉
│ Components  具体组件（.c-button）     │  ← 带视觉
│ Utilities   工具类（.u-text-center）  │  ← 最高优先级
└─────────────────────────────┘
```

### 7.2 SMACSS

按职责把样式分五类：Base（基础）、Layout（布局 `l-`）、Module（模块 `m-`）、State（状态 `is-`）、Theme（主题 `theme-`）。

### 7.3 方法论的现状

- ITCSS / SMACSS 诞生于"大型全局 CSS"时代，核心价值是**分层与命名纪律**
- 在 CSS Modules / 原子化方案中，"作用域"问题已被工具解决，但**分层思想仍然适用**——例如 Tailwind 项目中依然建议：reset → 设计 Token → 组件 → 工具类的顺序组织 `@layer`

```css
/* 用原生 @layer 落地分层思想（回顾模块 1） */
@layer reset, tokens, base, components, utilities;

@layer components {
  .card { /* ... */ }
}
@layer utilities {
  .u-center { display: grid; place-items: center; }
}
```

## 八、构建与性能优化

### 8.1 压缩与 Tree Shaking

```bash
# cssnano：压缩、合并重复声明、缩短颜色值
npx cssnano input.css output.css
```

```css
/* 压缩前 */
.card { margin: 16px 16px 16px 16px; color: #ffffff; }
/* 压缩后 */
.card{margin:16px;color:#fff}
```

**PurgeCSS**：扫描 HTML/JSX 中实际使用的类名，删除未引用的样式：

```js
// postcss.config.js
export default {
  plugins: {
    '@fullhuman/postcss-purgecss': {
      content: ['./src/**/*.{html,jsx,tsx}'],
      // 动态类名需加入白名单，防止误删
      safelist: [/^ant-/, 'is-active'],
    },
  },
};
```

> Tailwind CSS 内置按需生成，天然只产出用到的类，无需 PurgeCSS。

### 8.2 Critical CSS（关键渲染路径）

首屏只内联渲染所需的最小 CSS，其余异步加载，消除渲染阻塞：

```html
<head>
  <!-- 首屏关键样式：内联 -->
  <style>/* critical.css 内容 */</style>
  <!-- 其余样式：异步加载，不阻塞渲染 -->
  <link rel="preload" href="main.css" as="style" onload="this.rel='stylesheet'">
  <noscript><link rel="stylesheet" href="main.css"></noscript>
</head>
```

工具：`critical`（自动生成）、Next.js / Astro 等框架内置按页拆分 CSS。

### 8.3 其他优化手段

| 手段 | 说明 |
|------|------|
| **按路由分割** | 每个页面只加载自己的 CSS chunk（构建工具自动完成） |
| **字体优化** | `font-display: swap`、`preload` 关键字体、子集化（subset） |
| **图片替代** | 用 CSS 渐变/SVG 替代装饰性图片 |
| **避免 @import** | `@import` 会串行阻塞加载，用 `<link>` 并行加载 |
| **contain 属性** | `contain: layout paint` 限制重排重绘范围 |
| **content-visibility** | `content-visibility: auto` 跳过屏外内容渲染 |

```css
/* content-visibility：长列表/长文章性能优化（Baseline 2024-09，Safari 18 支持） */
.article-section {
  content-visibility: auto;
  contain-intrinsic-size: auto 500px;  /* 占位高度，避免滚动条跳动 */
}
```

## 九、方案选型决策

```
项目规模 / 团队情况
│
├─ 个人项目 / 静态站点
│   └─ 原生 CSS（+ 自定义属性 + @layer），可选 Tailwind
│
├─ 中小型组件化项目（React / Vue）
│   ├─ React → CSS Modules 或 Tailwind
│   └─ Vue  → SFC <style scoped> 或 Tailwind
│
├─ 大型多团队项目
│   ├─ 设计体系完善 → Tailwind / UnoCSS + 设计 Token
│   └─ 强动态样式需求 → vanilla-extract / Panda CSS
│
└─ 存量老项目
    └─ BEM 重构 + @layer 隔离 + PurgeCSS 瘦身，渐进迁移
```

**没有银弹**——选型看三个维度：团队熟悉度、设计体系成熟度、性能预算。

## 常见误区

### 误区 1：CSS Modules 能解决所有样式问题

CSS Modules 只解决**作用域隔离**。样式复用、组织、体积问题仍需配合设计 Token、组件抽象、PurgeCSS 等手段。

### 误区 2：用了 Tailwind 就不需要写 CSS 了

复杂交互（多步动画、复杂选择器逻辑）用原子类硬拼反而难维护。正确做法是抽组件 + 少量自定义 CSS，原子类负责常规布局。

### 误区 3：预处理器过时了就该全删

原生 CSS 已覆盖变量、嵌套、颜色函数，但 Sass 的 `@mixin`/`@use` 模块系统在大型项目中仍有价值。按实际需求取舍，不为新而新。

### 误区 4：!important 是样式冲突的解法

`!important` 破坏层叠规则（回顾模块 1），让后续维护者只能用更多 `!important` 覆盖。冲突的根因通常是**特异性失控或架构分层混乱**，应从源头解决。

### 误区 5：忽视动态类名被 PurgeCSS 误删

```jsx
// ❌ 拼接类名，PurgeCSS 静态扫描不到，样式被删
<div className={`alert-${type}`} />

// ✅ 完整类名映射
const cls = { success: 'alert-success', error: 'alert-error' };
<div className={cls[type]} />
```

## 面试回答模板

> **问：CSS 有哪些模块化方案？各自的原理和适用场景？**
>
> | 方案 | 原理 | 场景 |
> |------|------|------|
> | BEM | 命名约定，人工保证唯一性 | 无构建的原生项目 |
> | CSS Modules | 构建时类名哈希化 | React/Vue 组件化项目 |
> | Vue scoped style | 编译时加 `data-v-xxx` 属性 + 属性选择器 | Vue 项目 |
> | Shadow DOM | 浏览器级别的样式隔离 | Web Components |
> | CSS-in-JS | 运行时/编译时生成唯一类名 | 强动态样式需求 |
> | 原子化 CSS | 不存在自定义类名，无冲突可言 | 设计体系驱动的项目 |

> **问：Tailwind CSS 为什么产物体积小？有什么缺点？**
>
> Tailwind 在构建时扫描源码，**只生成实际用到的工具类**，且工具类全局复用（100 个按钮用同一个 `.px-4`），因此产物体积随项目规模增长趋于恒定。缺点：HTML 类名冗长影响可读性；复杂样式需要组件抽象或任意值语法；强依赖设计约束，自由定制需 escape hatch；团队需统一使用习惯。

> **问：CSS-in-JS 运行时方案有什么问题？为什么社区在转向零运行时？**
>
> 运行时方案（styled-components/Emotion）在渲染时序列化样式字符串、创建并插入 `<style>` 标签，存在三个问题：① 运行时性能开销，组件多时明显；② SSR 需额外抽取样式，配置复杂；③ React 18 并发渲染下样式插入顺序可能出错。零运行时方案（vanilla-extract、Panda CSS）在构建时把样式编译为静态 CSS 文件，保留 JS 写样式的全部开发体验，但没有运行时开销，SSR 也天然兼容。

> **问：大型项目 CSS 体积过大，如何优化？**
>
> 分四步：① **度量**——用 bundle 分析工具（如 `source-map-explorer`）定位大块样式来源；② **删除**——PurgeCSS 清理未使用类名，审查并删除死代码；③ **拆分**——按路由分割 CSS chunk，首屏用 Critical CSS 内联 + 其余异步加载；④ **压缩与替代**——cssnano 压缩、字体子集化、装饰图用渐变/SVG 替代。架构层面用设计 Token 统一变量、用 `@layer` 分层防止样式膨胀。

> **问：@layer、CSS Modules、BEM 都能"管理样式优先级"，区别是什么？**
>
> 三者作用层次不同：**BEM** 是命名约定，通过统一单类选择器让特异性扁平，靠纪律避免冲突；**CSS Modules** 是编译手段，类名哈希化实现物理隔离，让"冲突"不再发生；**@layer** 是层叠机制，显式声明样式来源的优先级顺序，解决的是"多来源样式谁覆盖谁"（如 reset < 组件库 < 业务覆盖）。三者可以组合：用 @layer 管理全局层级，用 CSS Modules 隔离组件作用域。

## 练习

### 练习 1：BEM 重构（基础）

把下面这段"嵌套地狱"CSS 用 BEM 重构：

```css
/* 重构前 */
.sidebar .menu .item { color: #333; }
.sidebar .menu .item .icon { margin-right: 8px; }
.sidebar .menu .item.active { color: #1677ff; }
```

**要求**：类名扁平化、特异性一致、状态用 Modifier 表达。

**提示**：Block 是 `sidebar-menu`，Element 用 `__item` / `__icon`，状态用 `--active`。重构后每个选择器特异性应为 (0,1,0)。

**预期效果**：所有选择器变为单类（如 `.sidebar-menu__item--active`），无嵌套依赖，可任意移动 DOM 位置而不破坏样式。

### 练习 2：CSS Modules 组件（基础）

用 Vite 创建一个 React 项目，实现一个 `Button` 组件：

- 样式写在 `button.module.css`
- 支持 `variant`（default / primary / danger）和 `size`（sm / md / lg）两个 props
- 用 `composes` 复用基础样式
- 打开 DevTools 观察编译后的类名

**提示**：`composes: base from './button.module.css'` 可在同文件内复用；Vite 默认开启 CSS Modules（`.module.css` 后缀）。

**预期效果**：DevTools 中类名形如 `button_primary__a3xK2`，全局无冲突；切换 variant/size 时样式正确切换。

### 练习 3：Tailwind 还原设计稿（进阶）

用 Tailwind CSS 还原一个卡片组件：

- 包含图片、标题、描述、标签列表、操作按钮
- 实现 hover 抬升效果（`hover:shadow-lg hover:-translate-y-0.5 transition`）
- 实现响应式：移动端单列、桌面端双列网格
- 实现暗色模式（`dark:` 变体）
- 在 `@theme`（Tailwind 4）或 `tailwind.config.js` 中自定义品牌色

**提示**：网格用 `grid grid-cols-1 md:grid-cols-2 gap-6`；暗色模式需先在 HTML 根元素加 `class="dark"` 或配置 `darkMode: 'class'`。

**预期效果**：移动端单列、桌面端双列；hover 时卡片上浮 + 阴影加深；切换 dark class 后配色自动切换。

### 练习 4：性能优化实战（进阶）

对一个含大量历史样式的页面做优化：

1. 用 PurgeCSS 清理未使用样式，对比前后体积
2. 提取 Critical CSS 内联到 `<head>`，用 Lighthouse 对比 FCP 变化
3. 给长内容区域加 `content-visibility: auto`，用 Performance 面板对比渲染耗时

**提示**：PurgeCSS 配置 `content: ['./src/**/*.{html,jsx,tsx}']`；Critical CSS 可用 `critical` npm 包自动生成；`content-visibility` 需配合 `contain-intrinsic-size` 防滚动条跳动。

**预期效果**：CSS 体积减少 50%+；FCP 提升 200ms+；长列表首帧渲染耗时显著下降（Performance 面板截图对比）。

### 练习 5：方案选型论述（思考）

为一个 20 人团队、含设计体系、需要 SSR 的中后台项目写一份 CSS 方案选型报告：

- 对比 CSS Modules / Tailwind / vanilla-extract 三个候选
- 从团队学习成本、设计体系落地、SSR 兼容性、产物体积、长期维护五个维度打分
- 给出最终建议与渐进迁移路径

**提示**：vanilla-extract 的 `.css.ts` 文件在构建时编译为静态 CSS，天然兼容 SSR/RSC；Tailwind 的设计约束（spacing scale、color palette）天然对齐设计体系。

**预期效果**：产出一份 1-2 页的选型报告，含五维雷达图/评分表、最终推荐方案、3 步渐进迁移计划。
