# 00 — 跨端技术概览与选型分析

> 对应大纲：认知层 | 预计时间：1 天
> 面试可答：跨端技术分为四大流派：WebView 壳方案、原生桥接方案、自绘引擎方案、桌面容器方案，各有各的适用场景和核心取舍。

---

## 1. 跨端技术解决的根问题

在进入具体技术之前，先理解跨端技术存在的根本原因——**移动端 & 桌面端的多平台碎片化**：

- iOS：Swift / Objective-C，Xcode 生态
- Android：Kotlin / Java，Gradle 生态
- Desktop（Mac / Windows / Linux）：各自独立的 GUI 框架

如果每个平台都写一套代码，成本翻倍、维护困难。跨端技术的核心目标是 **"一套代码，多平台运行"**，但代价是**性能折损、平台能力受限、调试复杂度上升**。

---

## 2. 四大流派核心原理

### 2.1 WebView 壳方案

**代表技术**：Cordova / PhoneGap / 微信小程序 / 支付宝小程序

**核心原理**：

```
┌──────────────────────────────────────────┐
│  Native 容器层（iOS/Android SDK）          │
│  ┌────────────────────────────────────┐  │
│  │  WebView（浏览器内核渲染）           │  │
│  │  ┌──────────────────────────────┐ │  │
│  │  │  HTML + CSS + JS（你的代码）  │ │  │
│  │  └──────────────────────────────┘ │  │
│  └────────────────────────────────────┘  │
│  JSBridge ←→ 原生能力（相机/定位/存储）   │
└──────────────────────────────────────────┘
```

- 页面渲染完全依赖 WebView（浏览器内核）
- 通过 JSBridge（JavaScript Bridge）调用原生能力
- 小程序的特殊之处：**双线程模型**——渲染层在 WebView，逻辑层在独立的 JS 引擎（V8 / JavaScriptCore），两者通过 Native 转发通信。这也是小程序与传统 WebView 壳方案（如 Cordova）的关键区别：Cordova 是单线程（渲染和逻辑都在 WebView 中），小程序通过双线程隔离了渲染和逻辑，性能和安全更好。

**优点**：上手快（Web 技术直接迁移），生态成熟
**缺点**：性能受 WebView 限制，复杂动画卡顿，页面跳转体验不如原生

---

### 2.2 原生桥接方案

**代表技术**：React Native

**核心原理**：

```
┌─────────────────────────────────────────────┐
│  JavaScript 引擎（Hermes / JSC）              │
│  ┌───────────────────────────────────────┐   │
│  │  React 组件树 → Virtual DOM          │   │
│  └──────────────┬────────────────────────┘   │
│                 │ JS Bridge (JSON 序列化)     │
│  ┌──────────────▼────────────────────────┐   │
│  │  Native Shadow Tree（布局计算）        │   │
│  │  ┌────────────────────────────────┐   │   │
│  │  │  Native Widget（真正的UI组件）   │   │   │
│  │  │  UIView / android.view.View    │   │   │
│  │  └────────────────────────────────┘   │   │
│  └───────────────────────────────────────┘   │
└─────────────────────────────────────────────┘
```

- JS 线程运行 React 逻辑，生成 Virtual DOM
- 通过 **JS Bridge** 将 UI 描述序列化为 JSON，传递给 Native 端
- Native 端解析 JSON，创建/更新真实的 Native Widget（iOS 的 UIView、Android 的 View）

**关键特点**：
- 不是 WebView 渲染——页面是真的原生组件
- JS Bridge 是异步序列化通信，这是性能瓶颈的核心
- React Native 的 **New Architecture**（Fabric + TurboModules + JSI）正在改变这一架构，移除 Bridge 的序列化开销

> ⚠️ 以上展示的是 RN **旧架构**。2026 年的 RN 已默认启用 New Architecture（Fabric + JSI），大幅缓解了 Bridge 序列化瓶颈。详见本章第 7 节。

**优点**：体验接近原生，Web 开发者快速上手
**缺点**：JS Bridge 在大数据量场景有性能瓶颈，平台 Bug 需要原生代码介入

---

### 2.3 自绘引擎方案

**代表技术**：Flutter

**核心原理**：

```
┌──────────────────────────────────────────────┐
│  Dart 引擎                                     │
│  ┌────────────────────────────────────────┐   │
│  │  Widget 树 → Element → RenderObject     │   │
│  └──────────────┬─────────────────────────┘   │
│                 │                              │
│  ┌──────────────▼─────────────────────────┐   │
│  │  Skia 图形引擎（自绘，不依赖平台组件）    │   │
│  │  直接将 Widget 绘制到 Canvas 上          │   │
│  └──────────────┬─────────────────────────┘   │
│                 │                              │
│  ┌──────────────▼─────────────────────────┐   │
│  │  Platform-specific Embedder             │   │
│  │  （iOS: UIKit, Android: SurfaceView）   │   │
│  └──────────────────────────────────────────┘   │
└──────────────────────────────────────────────┘
```

- 不依赖平台的 UI 组件，使用 **Skia 引擎** 直接从底层绘制像素
- 所有平台渲染出一致的 UI，没有"跟平台长得不一样"的问题
- Dart 编译为 Native Code，无需 Bridge 序列化

**优点**：性能极高、UI 一致性最好、动画流畅
**缺点**：需要学 Dart、包体积较大、平台深度集成时需写 Platform Channel

---

### 2.4 桌面容器方案

**代表技术**：Electron / Tauri

**核心原理**（以 Electron 为例）：

```
┌──────────────────────────────────────────────┐
│  主进程（Node.js）                             │
│  ┌────────────────────────────────────────┐   │
│  │  系统能力（文件系统/原生菜单/窗口管理） │   │
│  └────────────────────────────────────────┘   │
│                      IPC                      │
│  ┌────────────────────────────────────────┐   │
│  │  渲染进程（Chromium Browser）           │   │
│  │  HTML + CSS + JS → 桌面 UI             │   │
│  └────────────────────────────────────────┘   │
└──────────────────────────────────────────────┘
```

- 本质上是一个**打包了 Chromium 浏览器的桌面应用**
- 主进程在 Node.js 运行时，管理窗口和系统能力
- 渲染进程在 Chromium 中渲染 Web 页面
- 通过 IPC（进程间通信）交互

**优点**：Web 全量能力、npm 全量生态、开发效率极高
**缺点**：包体积巨大（~150MB 起步）、内存占用高

## 3. 四大流派核心对比

| 维度 | WebView 壳（小程序） | 原生桥接（RN） | 自绘引擎（Flutter） | 桌面容器（Electron） |
|------|---------------------|---------------|-------------------|---------------------|
| 目标平台 | iOS / Android / 特定 App | iOS / Android / Web | iOS / Android / Web / Desktop | Mac / Windows / Linux |
| 渲染方式 | 浏览器内核 | Native Widget | Skia 自绘 | Chromium 内核 |
| UI 一致性 | 各平台 WebView 表现不同 | 居中（组件的平台原生感） | 最佳（完全一致） | 最佳（同一浏览器） |
| 性能表现 | 一般（受 WebView 限制） | 良好（New Arch 大幅改善） | 优秀（编译到 Native） | 中（内存占用大） |
| 包体积 | 小（小程序包 < 2MB） | 中（~20MB 起步） | 较大（~30MB 起步） | 很大（~150MB 起步） |
| 开发语言 | JS/TS | JS/TS | Dart | JS/TS |
| 学习成本 | 低 | 低（有 React 基础） | 中（需学 Dart） | 低 |

## 4. RN vs Flutter：详细对比

这是面试最高频的跨端对比题。

### 4.1 渲染机制

- **RN**：JS 线程 → Bridge 序列化 → Native Shadow Tree → Native Widget（旧架构）；新架构通过 JSI 直接操作 C++ 层 Shadow Tree（详见第 7 节）
- **Flutter**：Dart → RenderObject → Skia → 直接绘制到 Canvas

Flutter 少了序列化和 Bridge 的开销，高帧率动画和大数据列表渲染上 Flutter 占优。RN 的 New Architecture（Fabric）通过 JSI 直接调用 C++ 层的 Shadow Tree，大幅减少了 Bridge 瓶颈。

### 4.2 UI 一致性

- **RN**：组件在 iOS 上渲染为 UIView，在 Android 上渲染为 View。Picker、DatePicker 等各平台长得不一样，但"平台原生感"强。
- **Flutter**：所有平台渲染结果完全一致，像游戏引擎一样精确控制每个像素。

### 4.3 生态与第三方库

- **RN**：时间长，第三方库丰富。从导航（React Navigation）到地图、支付、推送都有成熟的库。但部分库年久失修、维护质量参差不齐。
- **Flutter**：较新但发展迅速，Google 官方维护力度强。三方库数量和质量稍逊于 RN，但差距在缩小。

### 4.4 学习曲线

- **RN**：如果已经会 React Web，只学环境搭建和 RN 特有概念（1-2 天能上手写代码）
- **Flutter**：需要从头学 Dart 语言和 Widget 树开发模式（2-3 周才能比较顺手）

### 4.5 谁适合谁

| 场景 | 选 RN | 选 Flutter |
|------|-------|-----------|
| 团队技术栈 | 前端团队转移动端 | 需要从零搭建 |
| 交付速度 | MVP 验证、快速迭代 | 需要长线高质量维护 |
| UI 要求 | 跟平台长得"像"就行 | UI 一致性极致要求 |
| 性能要求 | 常规列表/表单/信息流 | 复杂动画/游戏/高频刷新 |

## 5. RN vs 小程序：核心取舍

有些时候开发者会在"做一个 RN App"和"做一个小程序"之间犹豫。

| 维度 | React Native | 小程序 |
|------|-------------|--------|
| 用户触达 | 用户在桌面/App Store 发现 | 微信/支付宝生态内分享传播 |
| 能力边界 | 完整设备能力（相机/蓝牙/NFC） | 受限（取决于平台开放 API） |
| 留存率 | 桌面图标，留存率更高 | 用完即走，留存率低 |
| 开发迭代 | 需要发版/热更新 | 审核通过即生效 |
| 跨端范围 | iOS + Android + Web | 微信/支付宝/字节等各自生态 |
| 商业化 | 自由（自有支付/广告） | 受平台规则约束 |

**选型判断**：
- 如果你的 App 需要深度设备能力、独立用户体系、高留存 → **RN**
- 如果你的业务依赖微信生态社交裂变、快速获客 → **小程序**
- 很多团队的做法：**RN 做主体 App + 小程序做生态拓展**，两者并不互斥


## 7. React Native New Architecture（2026 年现状）

这节单独列出来，因为 New Architecture 是理解现代 RN 的关键，也是面试高频考点。

### 7.1 旧架构的问题

```
JS 线程 ──JSON 序列化──→ Bridge ──JSON 反序列化──→ Native 线程
         ←──JSON 序列化──←      ←──JSON 反序列化──←
```

- 每次通信都要序列化/反序列化 JSON
- Bridge 是异步批处理的，无法同步获取 Native 数据
- 大数据量（比如图片列表）场景，Bridge 成为瓶颈

### 7.2 New Architecture 三大核心

**① Fabric（新渲染器）**
- 旧：Shadow Tree 在 JS 端 → 通过 Bridge 序列化发给 Native
- 新：Shadow Tree 在 C++ 层（Fabric），JS 通过 JSI 直接操作 C++ 对象
- 效果：减少序列化开销，渲染性能提升，支持同步渲染

**② TurboModules（新原生模块）**
- 旧：所有原生模块在 App 启动时全部初始化
- 新：按需懒加载（只初始化用到的模块）
- 效果：冷启动时间大幅缩短

**③ JSI（JavaScript Interface）**
- 旧：Bridge 是异步消息通道
- 新：JSI 是 C++ 层接口，JS 可以直接持有 C++ 对象的引用并同步调用
- 效果：JS 和 Native 之间可以同步通信，不再需要 JSON 序列化

### 7.3 当前生态现状

- New Architecture 自 RN 0.68 引入，到 0.76+ 成为默认
- Expo SDK 52+ 已全面支持 New Architecture
- 大多数主流第三方库（React Navigation、FastImage、Reanimated）已适配

## 📝 面试回答模板

> **问：跨端技术有哪些流派？各有什么特点？**
>
> 目前主流的跨端技术可以分为四大流派：
>
> 第一，**WebView 壳方案**，代表是 Cordova 和小程序。它用 WebView 加载 Web 页面，通过 JSBridge 调用原生能力。优点是上手快、Web 团队直接迁移，缺点是性能受限于 WebView。小程序的特殊之处是双线程模型——渲染和逻辑分离。
>
> 第二，**原生桥接方案**，代表就是 React Native。JS 端通过 Bridge 异步序列化 JSON，Native 端解析后创建真实的 Native Widget。优点是有原生体验，Web 开发者学习成本低，缺点是 Bridge 序列化有性能损耗。不过 RN 的 New Architecture 通过 JSI 已经大幅缓解了这个问题。
>
> 第三，**自绘引擎方案**，代表是 Flutter。它不依赖平台组件，直接用 Skia 引擎绘制每个像素，所有平台渲染结果完全一致。优点是性能极高、UI 一致性好，缺点是要学 Dart、包体积偏大。
>
> 第四，**桌面容器方案**，代表是 Electron 和 Tauri。Electron 打包 Chromium 运行 Web 应用，包体积大但开发效率高、Web 生态全量可用。Tauri 是它的轻量替代，包体积更小。

> **问：React Native 和 Flutter 怎么选？**
>
> 这取决于团队背景和业务诉求。如果团队是前端出身、熟悉 React，选 RN 学习成本最低，1-2 天就能上手写代码，适合快速出 MVP。如果团队愿意从头学、业务追求极致 UI 一致性和高性能，选 Flutter 更合适。另外从生态角度看，RN 的第三方库更丰富成熟，但 Flutter 有 Google 强力推动发展很快。一句话总结：前端团队快速迭代选 RN，长线高质量产品选 Flutter。

> **问：React Native 的 New Architecture 解决了什么？**
>
> 旧架构的核心问题是 Bridge 异步序列化的性能瓶颈。New Architecture 通过三个组件解决：第一，Fabric 将 Shadow Tree 放到 C++ 层，JS 通过 JSI 直接操作，大幅减少序列化开销；第二，TurboModules 实现原生模块懒加载，冷启动更快；第三，JSI 提供了 JS 和 C++ 之间的同步接口，让 JS 可以直接持有并调用 C++ 对象引用。简单来说就是更快、更小、更同步。
