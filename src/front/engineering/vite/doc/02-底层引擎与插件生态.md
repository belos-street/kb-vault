## 核心概念

### 1. 引擎演化史：为什么 Rolldown 统一双引擎

**旧时代（Vite 7-）的矛盾**：

| 引擎 | 语言 | 职责 | 问题 |
| ---- | ---- | ---- | ---- |
| esbuild | Go | dev 转译 + 依赖预构建 | 与生产引擎 Rollup 行为不一致（"dev 和 build 结果不同"类 bug 的根源） |
| Rollup | JS | 生产打包 | 慢（大仓库分钟级），JS 单线程 |

**Vite 8 的答案**：Rolldown（Rust 写的 Rollup 兼容实现）一条引擎接管全部——dev 转译/预构建与生产打包共用一套行为，速度接近 esbuild，插件 API 兼容 Rollup（存量插件无痛迁移）。oxc 作为 Rolldown 的 parser/transformer 承担转译，Lightning CSS 承担 CSS 压缩。

**记忆口诀：转译归 oxc，打包归 rolldown，CSS 归 lightningcss，全 Rust 化。**

> `rolldown-vite` 包是迁移期的过渡载体（在 Vite 7 上提前体验 Rolldown），Vite 8 起就是默认引擎，这个包名不再需要出现在新项目里。

### 2. 插件体系：Rollup 兼容 + Vite 专属

Vite 插件是一个带钩子的对象，钩子分两层：

```ts
import type { Plugin } from 'vite'

export function plainTxt(): Plugin {
  const virtualId = 'virtual:hello'
  const resolved = '\0virtual:hello'   // \0 前缀：约定俗成的虚拟模块命名空间

  return {
    name: 'plain-txt',
    // apply 可选 'serve' | 'build'，不设则 dev/build 都跑——
    // ⚠️ 设了 'build' 的话，下方的 configureServer 将永远不会执行

    // ── Rollup 兼容钩子（打包期核心三件套）──────────────
    resolveId(source) {
      // 拦截 import 解析：虚拟模块返回固定 id，其余返回 null 走默认逻辑
      return source === virtualId ? resolved : null
    },
    async load(id) {
      // 拿到 id，返回该模块的"源码"
      if (id === resolved) return `export default 'hello from virtual module'`
    },
    transform(code, id) {
      // 逐模块改写源码（编译器类插件的主战场：JSX、宏、注入）
      if (id.endsWith('.md')) {
        return `export default ${JSON.stringify(code)}`
      }
    },

    // ── Vite 专属钩子（dev server 能力）────────────────
    configureServer(server) {
      // dev server 就绪后可加中间件、注册 HMR 事件
      server.middlewares.use('/health', (_req, res) => res.end('ok'))
    },
    transformIndexHtml(html) {
      // 直接改写 index.html（注入脚本/标签）
      return html.replace('</head>', '<meta name="generator" content="vite"></head>')
    },
  }
}
```

```ts
// vite.config.ts 使用
import { plainTxt } from './vite-plugin-plain-txt'
plugins: [react(), plainTxt()]
```

三层钩子的心智：**resolveId/load 定义"模块从哪来"（虚拟模块），transform 定义"源码怎么变"（编译），Vite 专属钩子补 dev server 与 HTML 能力**。常用插件（react/vue/legacy/federation）全是这三层钩子的不同组合。

### 3. babel 退休清单

| babel 的旧职责 | 现在谁接管 | 需要行动吗 |
| -------------- | ---------- | --------- |
| TS/JSX 转译 | oxc（Rolldown 内置） | 零配置，无需行动 |
| React fast refresh | `@vitejs/plugin-react` v6+ 用 Oxc 做 Refresh 转换，**零 babel 依赖** | 零配置（`plugin-react-swc` 已无存在必要） |
| React Compiler（实验性） | `reactCompilerPreset` + `@rolldown/plugin-babel` 显式 opt-in | 按需 |
| Polyfill（旧浏览器） | `@vitejs/plugin-legacy`（内部 core-js） | 仅面向旧浏览器场景 |
| AST 工具 / codemod / 自定义 lint 规则 | **babel 生态仍是首选** | 需要时再学 |

结论：**构建链路里已经没有 babel 的位置**（唯一例外是 React Compiler 的 opt-in 场景）；它作为"AST 工具库"的生命周期独立于 Vite 存在。

### 4. 老 Vite 项目迁移对照表（7- → 8）

| 老配置 | Vite 8 替代 | 备注 |
| ------ | ----------- | ---- |
| `build.rollupOptions.output.manualChunks`（对象/函数形式） | `advancedChunks: { groups: [{ name, test }] }` | 旧的两种形式均已移除 |
| `optimizeDeps.esbuildOptions` | `optimizeDeps.rolldownOptions` | 字段整体更名 |
| CSS 压缩配置（esbuild css minify） | Lightning CSS 内置 | `css.transformer: 'lightningcss'` 可选启用其语法转换 |
| `rolldown-vite` 依赖 | 删除，直接用 vite 8 | 过渡包完成使命 |
| `import.meta.env` 用法 | 不变 | 无迁移成本 |

迁移实操顺序：`pnpm add -D vite@8` → 跑 build 收集报错 → 按上表逐项替换 → 对比 dev/build 产物行为。

### 5. 常用插件分层速查

| 层 | 插件 | 干什么 |
| -- | ---- | ------ |
| 框架 | `@vitejs/plugin-react` / `plugin-vue` | JSX/SFC 编译 + HMR 边界 |
| 质量前移 | `vite-plugin-checker` | dev 时在浏览器 overlay 里看 TS/lint 错误 |
| 兼容 | `@vitejs/plugin-legacy` | 旧浏览器双份产物 + polyfill |
| 微前端 | `@module-federation/vite` | MF 2.0（见 [../micro-frontend/](../../micro-frontend/readme.md)） |
| DX | `unplugin-auto-import` 等 | 自动导入、组件注册 |
| 自研 | 三层钩子组合 | 虚拟模块、代码注入、路径约定 |

## 常见踩坑点

- **插件写了 transform 但没生效** → 检查 `id` 过滤条件（dev 的 id 是绝对路径含 query，如 `?raw`）；先 `console.log(id)` 观察
- **虚拟模块在 TS 里报红** → 虚拟模块要补类型声明：`declare module 'virtual:hello' { const s: string; export default s }`
- **`\0` 前缀丢了** → 虚拟模块 resolveId 返回的 id 必须保留 `\0`，load 端才能对上
- **老项目升级后 manualChunks 报错"已移除"** → 按迁移对照表改 advancedChunks，对象形式要翻译成 groups 的 test 正则
- **dev 和 build 行为不一致** → Vite 8 下双引擎已统一，若仍出现，优先怀疑环境变量差异（`import.meta.env.PROD` 分支）而非引擎

## 面试回答模板

> **问：Rolldown 统一双引擎的动机与风险？**
> **答：** 双引擎时代 dev（esbuild）和 build（Rollup）是两套实现，同一份代码两边行为差异是顽固 bug 来源；且 Rollup 的 JS 实现在大仓库下打包慢。Rolldown 用 Rust 重写并兼容 Rollup 插件 API，一套行为贯穿 dev/build，速度接近 esbuild。最大风险是兼容性——少量依赖 Rollup 未定义行为的插件可能踩边界，官方靠大范围生态测试收敛；对使用者而言"换引擎不换 API"，业务项目基本无感，主要动作就是配置项改名（manualChunks → advancedChunks 等）。

> **问：虚拟模块插件需要哪些钩子？**
> **答：** 两个：`resolveId`——拦截对虚拟 id（如 `virtual:xxx`）的 import 解析，返回带 `\0` 命名空间的固定 id；`load`——识别该 id，返回模块源码字符串。这组合让"代码里 import 一个不存在的路径"变成运行时可用的模块，unplugin-auto-import、i18n 按需加载等插件都是这个模式。要 TS 类型支持再加一条 `declare module`。

## 练习

1. **写插件**：实现 `vite-plugin-md`——让项目里可以 `import readme from './README.md'` 拿到字符串（用 `transform` 钩子），补 TS 类型声明，dev/build 双跑验证。
2. **虚拟模块**：按本文 plainTxt 例子实现 `virtual:build-time`，导出构建时刻（`new Date().toISOString()`），体会"构建期注入"能力。
3. **迁移演练**：找一个 Vite 5/6 的旧项目（或造一个 manualChunks 对象配置），升级到 Vite 8，按对照表走完全程，记录遇到的所有 breaking change。

**预期效果**：练习 1/2 完成"钩子心智"落地；练习 3 有一份自己踩出来的迁移记录。
