## 核心概念

### 第 1 步：项目骨架

```bash
mkdir my-create && cd my-create
bun init -y
bun add commander @inquirer/prompts picocolors ora
bun add -d typescript @types/bun oxlint oxfmt
```

```jsonc
// package.json —— bin 字段是"命令名 → 可执行文件"的映射，发布后全局可用
{
  "name": "my-create",
  "version": "0.1.0",
  "type": "module",
  "bin": {
    "my-create": "./src/cli.ts"
  },
  "scripts": {
    "cli": "bun src/cli.ts"
  }
}
```

> Bun 可以直接执行 TS（shebang 写 `#!/usr/bin/env bun`）；如果要兼容只装了 Node 的用户，先 `bun build --compile` 或转译成 JS 再发。

### 第 2 步：CLI 主文件（完整代码）

```ts
// src/cli.ts
#!/usr/bin/env bun
import { Command } from 'commander'
import { input, select, confirm } from '@inquirer/prompts'
import pc from 'picocolors'
import ora from 'ora'
import { mkdir, writeFile, readFile, stat } from 'node:fs/promises'
import { join, resolve } from 'node:path'

interface Options {
  template?: string
  force?: boolean
}

// 探测路径存在性：必须用 stat（readFile 对目录抛 EISDIR 会被 catch 吞掉，
// 导致"目录已存在"检测失效 → 静默覆盖）
async function exists(p: string) {
  try {
    await stat(p)
    return true
  } catch {
    return false
  }
}

const program = new Command()

program
  .name('my-create')
  .description('团队项目脚手架')
  .version('0.1.0')
  .argument('[name]', '项目名')
  .option('-t, --template <tpl>', '直接指定模板，跳过询问')
  .option('-f, --force', '目标目录已存在时也继续')
  .action(async (name: string | undefined, opts: Options) => {
    console.log(pc.bold(pc.cyan('⚡ my-create')))

    // ── 交互层：缺什么问什么 ─────────────────────────────
    const projectName = name ?? (await input({ message: '项目名叫什么？' }))
    const targetDir = resolve(process.cwd(), projectName)

    if ((await exists(targetDir)) && !opts.force) {
      const goOn = await confirm({ message: '目录已存在，覆盖继续？' })
      if (!goOn) return
    }

    const template =
      opts.template ??
      (await select({
        message: '选个模板',
        choices: [
          { value: 'vanilla', name: 'Vanilla TS' },
          { value: 'react', name: 'React + Vite' },
          { value: 'node', name: 'Node 工具库' },
        ],
      }))

    // ── 执行层：模板渲染 → 写文件 ────────────────────────
    const spinner = ora('生成项目...').start()
    try {
      await mkdir(targetDir, { recursive: true })

      // 最小模板：package.json + index.ts（真实项目改为拷贝模板目录）
      const pkg = {
        name: projectName,
        version: '0.0.0',
        type: 'module',
      }
      await writeFile(join(targetDir, 'package.json'), JSON.stringify(pkg, null, 2))
      await writeFile(
        join(targetDir, 'index.ts'),
        `// ${template} 模板\nexport const hello = () => 'hi'\n`,
      )
      spinner.succeed(`项目已生成：${pc.cyan(projectName)}`)
      console.log(`\n  cd ${projectName} && bun install`)
    } catch (err) {
      spinner.fail('生成失败')
      console.error(pc.red(err instanceof Error ? err.message : String(err)))
      process.exit(1)
    }
  })

program.parse()
```

核心流水线五段：**输入收集 → 存在性校验 → 模板选择 → 写文件 → 下一步指引**。

### 第 3 步：本地调试（不发布也能全局用）

```bash
bun link          # 把当前包软链到全局 bin
my-create demo    # 任意目录直接用
bun unlink        # 调试完解除
```

不想软链也可以每次 `bun run /path/to/my-create/src/cli.ts demo`。

### 第 4 步：模板的真实形态

玩具版直接字符串写文件；生产脚手架的标准做法：

```
templates/
├── react/
│   ├── _package.json      # 文件名加 _ 前缀表示需要变量渲染
│   └── src/App.tsx
└── node/
    └── _package.json
```

```ts
// 本片段新增依赖（承接第 2 步的 import 补充）：cp, unlink 来自 node:fs/promises
import { cp, unlink } from 'node:fs/promises'
import { readFile, writeFile } from 'node:fs/promises' // 第 2 步已引入

// 1. 拷贝整个模板目录（变量文件用 _ 前缀防 npm 屏蔽 package.json）
await cp(join(import.meta.dir, 'templates', template), targetDir, { recursive: true })

// 2. 渲染变量：读 _package.json → 替换 {{name}} → 写成 package.json
const raw = await readFile(join(targetDir, '_package.json'), 'utf8')
await writeFile(join(targetDir, 'package.json'), raw.replaceAll('{{name}}', projectName))
await unlink(join(targetDir, '_package.json'))
```

进阶方向（按需再学，本篇不展开）：**prompts 带条件分支**（`when: answers => ...`）、**模板内 EJS/HBS 语法渲染**、**拉远端模板仓库**（degit 思路：下载 GitHub 目录 tarball 解压）。

### 第 5 步：发布

```bash
bun publish          # 发布到 npm（会自动把 bin、files 字段带上）
# 或私有 registry：bun publish --registry https://npm.internal.example.com
```

发布后用户即 `bunx my-create` / `npx my-create` 使用。

## 常见踩坑点

- **shebang 是 bun 但用户环境只有 Node** → 对外发布用 `#!/usr/bin/env node` 最稳；Bun 专属 API（`Bun.*`）就不要用
- **`bin` 指向的文件没有可执行内容** → 确认 shebang 在第一行第一列，前面不能有空行
- **`bun link` 后命令没生效** → 检查 `package.json` 的 `bin` 字段键名和 shell 里敲的命令名是否一致；重开终端
- **交互问答在 CI 卡死** → 没有参数时先判断 `process.env.CI`，CI 环境直接报错"必须传 --template"，而不是进入问答
- **`ora` 的 spinner 和 console.log 交错输出错位** → spinner 存续期间别直接 `console.log`，用 `spinner.text` 更新，或先 `spinner.stop()`

## 面试回答模板

> **问：bin 字段的工作原理？**
> **答：** `package.json` 的 `bin` 把命令名映射到包内文件。全局安装（或 `bun link`）时，包管理器在全局 bin 目录创建一个 shim 脚本指向该文件；执行命令时 shell 通过 shim 找到 shebang 指定的解释器（node/bun）来运行它。`npx` 则是临时下载包后执行同样的 shim 逻辑，不污染全局。

> **问：怎么支持远端模板？**
> **答：** degit 的思路——不发 npm 包，直接从 GitHub/GitLab 下载模板目录的 tarball（`https://github.com/user/repo/archive/main.tar.gz`）解压到缓存目录，再走本地同款"渲染变量 → 写文件"流水线。好处是模板迭代不用发 CLI 版本，坏处是要处理网络失败和版本缓存。

## 练习

1. **跑通**：`cd src/scaffold-demo && bun install && bun link`，然后在别处执行 `my-create hello`，观察生成的文件。
2. **加功能：模板选择真实生效**——把 doc 里"vanilla/react/node 三选一"真正对应到 `templates/` 下三个不同模板目录（各自至少含一个差异文件），验证选择后产物不同。
   - 提示：`cp` + `replaceAll('{{name}}', ...)` 两行就够。
3. **加功能：`--dry-run`**——加一个布尔选项，只打印"将要创建哪些文件"而不真的写盘。
   - 提示：把写文件逻辑抽成函数，dry-run 时只 `console.log` 路径列表。
4. **CI 兜底**：运行时设 `CI=true bun src/cli.ts`（不带参数），确认程序报错退出而不是挂死。
   - 提示：入口处 `if (process.env.CI && !name) throw ...`。

**预期效果**：练习 2、3 完成后，这个 demo 就是可用的团队小脚手架雏形。
