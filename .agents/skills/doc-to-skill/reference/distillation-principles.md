# 教学文档 → Skill 的蒸馏原则

做转换时，先想清楚：**教学文档是"给人学的一段旅程"，Skill 是"可直接拍板干活的一份手册"。** 转换不是压缩复制，而是换载体重写。

## 1. 能进 skill / 不能进 skill

| 能进（可执行的知识） | 不能进（过程/铺垫） |
|--------|--------|
| 核心机制与工作原理 | "本模块预计 1 天""先热身"等学习旅程 |
| 关键 API、公式、参数与决策点 | 面向初学者的逐步讲解语气 |
| 常见踩坑点与规避 | 冗余的入门背景、历史来源 |
| 与同类方案的取舍对照 | 过程性练习/作业的描述 |
| 面试关键结论句 | 章节完成度勾选清单 |

> 判别式：把教程的某一段抹掉，**用户还能不能照着 skill 把事情做对？** 能，说明这段是知识，留；只是让"学得更顺"，删。

### 1.1 不绑受众

> 产物是通用能力，可被任何人复用。教学区为特定读者写的对照语境是"铺垫"，不是知识。

- **禁止**出现教学区专属语境：专门的「与 JS/TS 心智映射」章节、「面向已有 XX 经验者」导语、「本文档你将学到」。
- 术语类比（如 `go.mod ≈ package.json`）可保留作一句点缀，帮助理解；但不要为此搭专职对照章节，那会把"通用能力"绑回"某批读者"。
- 判断：把这一节删掉，能力照常成立 → 删；删掉就读不懂 → 留。

## 2. 怎么拆"能力块"（粒度）

- 不要"一篇一个 skill"，也不要把整套硬塞成一个。
- 以 `readme.md` 的模块划分 + 作者画像（受众会什么）为准，找**自洽能力边界**。
- 判别：一个 skill 读完，用户能独立完成一件完整的事（实现一种图、跑通一个机制、排查一类问题）。满足 → 独立；满足不了的部分并入相邻滑块。
- 宁可合并成一个偏大的 skill 分 reference 章节，也不要拆成 3 个 5 行的碎片。

## 3. 蒸馏四步，每步一个产物

1. 抽**机制**：这个能力在解决什么问题，怎么解决的（一句话说清原理）。
2. 抽**方法**：从输入到输出的可执行步骤 / 关键调用链。
3. 抽**坑**：作者用警告强调的点、常见错误写法 + 正确写法配对。
4. 抽**决策**：几个方案 / 参数 / API 的取舍判据，给判断标准而非罗列。

## 4. 忠实而不照抄

- 关键结论要忠实于原文（尤其"面试可答"和作者下的定论），不能凭印象改写。
- 但呈现必须重写为 skill 的语言：第三人称/命令式、直奔要点、少过渡句。
- 技术图一律用 **Mermaid**（仓库规范），禁 ASCII 目录树。
- 适量 emoji（💡 提示 / ⚠️ 坑 / ✅ 正确例子 / ❌ 错误例子），克制。

## 4.1 用官方文档核验"忠实"

> 蒸馏最怕"凭印象改写"：作者定论与官方定论冲突时，以官方文档为准，并在能力里留链接。

- 写完后，对抽出的**关键 API/公式/定论**用官方文档（WebFetch/WebSearch）交叉比对一次，确认参数名、行为、结论没走样。
- 官方链接回填到各能力 `reference/*.md` 的"参考：官方文档"小节，供日后二次核对。
- 职责分清：`doc/` 负责"作者的讲解语境"，官方文档负责"定论正确性"；两者冲突时官方为准并标注。

## 5. 独立可搬走，是硬指标

- 生成后把 `doc/` 从眼中拿掉，逐字核验：是否还依赖教程的相对路径、篇号、教学上下文？
- 出现"参见 doc/03"、"[本模块][上篇]"等字样 → 说明没解耦，改写成 skill 内部可自洽的表述。
- **零仓库路径**：不复用 `metadata.source` 溯源字段，frontmatter 与正文都不写原教学区相对路径——搬到别的项目它就是一个普通的可搬走的 skill，不残留"我来自某仓库某目录"的依赖。
