# 教学文档质量审查器 (Doc Quality Reviewer)

审查技术教学文档（含代码示例的 markdown 教程）的质量，对照参考模板给出逐篇评分与修改建议。

---

## 触发条件

当用户提出以下请求时，应调用此 Skill：
- "review 一下这份文档质量如何"
- "检查这些教程写得好不好"
- "评估一下学习资料的完整性"
- "对照模板审查文档"
- "这批 doc 有什么改进空间"
- "review 并按照建议修改优化文档"（审查完成后进入修改闭环，见「审查 + 修改闭环」章节）

---

## 审查流程

### 0. 先读取项目级写作规范

审查前先检查项目根目录或仓库中是否有全局写作规范（如 `agents.md`、`CONTRIBUTING.md`），重点提取：
- 绘图要求（如技术绘图是否统一使用 Mermaid、禁止外链图片）
- 命名、标题、术语约定
- 其他格式约束

将这些规范与参考模板一并纳入评审基线。项目级约束常超出单份模板的范围，是最容易漏审的一类问题（典型：全文档散布 ASCII 技术图，未按项目规范转为 Mermaid）。

### 1. 先读取参考模板（Reference）

如果用户未提供模板路径，询问用户。模板通常定义了：
- 文档命名规范
- 章节结构要求
- 代码示例标准
- 练习与面试要求

若用户提供了模板（如项目根 `readme.md`），从中提取**格式规范清单**作为评审基线。

### 2. 逐篇通读所有文档

同时读取所有目标文档，避免逐篇串行阅读导致的低效。对每篇文档做以下维度的评估。

### 2.5 对照官方文档验证（分级验证协议）

文档中的技术表述不能依赖记忆或二手资料，应使用 WebSearch/WebFetch 查询官方文档验证。全量验证每个 API 不现实，按下述分级执行：

**验证分级**：

| 级别 | 范围 | 动作 |
|------|------|------|
| 必查 | 版本号、弃用/移除声明、安全配置、时间线断言、照抄即错的代码示例 | 逐条验证，附来源链接 |
| 抽查 | 参数默认值、行为描述、API 签名 | 抽查高频与关键项 |
| 豁免 | 通用概念性描述、类比说明 | 无需验证 |

**来源分级**：`官方域名文档 > GitHub releases/changelog > 官方博客 > 框架源码 > 社区最佳实践 > 个人经验`。第三方博客/聚合站仅作线索、不作依据；警惕搜索结果中的 SEO 镜像站（仿冒知名项目官方文档），重要版本信息须在官方域名或 GitHub 上交叉确认。

**时效性规则**：凡「X 版本起 / 已移除 / 当前最新」类断言，先确认当前日期，核实该版本是否已发布、该变更是否已生效。「计划发布」的版本不得表述为「已生效」（反例：将尚未发布的版本写为「XX 起移除」）。

**判定记录要求**：报告中每条 P0 级判定必须标注验证状态（已验证 + 来源 / 存疑）。凭记忆得出的结论不得直接作为错误判定——反例：凭记忆误判某合法配置项为非法，查官方文档后才撤销。

### 3. 六维评分模型

对每篇文档按以下 6 个维度打分（1-5 星），并给出总评（满分 10）。

**评分锚点**（防止普遍打 4~4.5 的分数通胀）：

| 星级 | 含义 |
|:--:|------|
| ⭐⭐⭐⭐⭐ | 可直接发布，无需实质修改 |
| ⭐⭐⭐⭐ | 整体优秀，存在小瑕疵（措辞、个别版本偏旧） |
| ⭐⭐⭐ | 可用但有明显缺口（关键内容缺失、代码存在错误） |
| ⭐⭐ | 问题较多，需大幅修改 |
| ⭐ | 严重错误或结构缺失，需重写 |

#### 维度 A：格式规范性
对照模板与项目级写作规范检查：
- 文件命名是否符合 `XX-模块名` 规范
- 头部元信息（模块映射、预计时间、面试可答）是否完整
- 代码块是否有语言标记（如 ` ```js `）
- 练习环节是否包含「要求 + 提示 + 预期效果」三段
- 面试回答模板是否使用 `> **问：**` 格式
- 绘图是否符合项目规范（如技术绘图统一 Mermaid、禁止外链图片；目录树、UI 位置示意等属合法例外）
- **参考链接**：版本断言、关键 API、新特性/迁移点处是否附官方文档或 Release Notes 链接（来源分级同 §2.5：官方域名 > GitHub changelog > 官方博客）；关键断言无出处记为「缺参考链接」
- **跨文档一致性**：术语、版本号、归类、结论在全部文档间是否一致。用 Grep 批量提取关键名词（技术名、应用名、版本号）交叉核对（反例：同一应用的归属在表格与正文中表述矛盾）

#### 维度 B：代码可运行性

按代码复杂度分级要求，避免一刀切「全部必须可运行」：

| 场景 | 要求 |
|------|------|
| 简单、自包含（单 API 用法、数十行内可独立演示） | **必须完整可运行**：依赖给出、变量声明齐全、无语法逻辑错误 |
| 中间态（补少量 mock 数据/最小环境即可跑） | 优先「最小可运行」：显式标注 mock 与最小环境，能跑就不退化成伪代码 |
| 复杂、强依赖（需真实服务、SDK Key、大型已有项目上下文） | 允许**显式标注的高质量伪代码**：写清关键变量、数据结构与数据流向 |

检查每个代码片段：
- 先判断属于哪一档，再核对该档要求（完整可运行 or 高质量标注伪代码）
- 简单场景：依赖是否明确（import/CDN 引入是否给出）、关键变量是否已声明、有无语法错误或逻辑遗漏
- 复杂场景：伪代码是否显式标注，且交代对象来源与数据结构（而非空口一句「这样就…」）
- 是否出现**未标注的「伪可运行」代码**——看起来能跑、实际缺依赖与上下文（比诚实标注的伪代码更有害，直接判 P0）

```markdown
✅ 正面示例（简单自包含 → 完整可运行）：
```js
const stage = new Konva.Stage({ container: 'root', width: 800, height: 600 });
const layer = new Konva.Layer();
stage.add(layer);
layer.add(new Konva.Circle({ x: 100, y: 100, radius: 50, fill: 'red' }));
layer.draw();
```

✅ 正面示例（复杂强依赖 → 诚实标注的高质量伪代码）：
```js
// 伪代码：消息队列消费流程，省略 Redis 连接与 SDK 初始化
async function consume() {
  const msg = await broker.dequeue('task-queue')  // 消息结构: {id, type, payload}
  const handler = handlers[msg.type]              // handlers 由各业务模块注册
  if (handler) await handler(msg.payload)         // 未知类型走兜底
  else await defaultSink(msg)
}
```

❌ 反面示例（未标注的伪可运行代码）：
```js
circle.fill('red')  // 这样就变红了（circle 未声明、缺注册与绘制，照抄即错）
```
```

#### 维度 C：面试导向性
- 面试回答模板是否紧扣知识点
- 回答内容是否「拿来就能用」（即答即中的水平）
- 是否有自问自答式的深入追问（如「面试常问：为什么没有自动渲染？」）
- 是否覆盖了面试常见的追问点（陷阱、对比、原理）

#### 维度 D：知识覆盖度
- 核心 API 是否全部涉及
- 边缘情况是否有说明（如序列化不保留事件、图片异步加载）
- 常见踩坑点是否提醒到位
- 是否有进阶延伸（性能优化、设计模式）

#### 维度 E：渐进式学习
- 各篇之间是否有自然的递进关系
- 每篇是否在前一篇基础上扩展能力
- 练习难度是否递增
- 实战整合篇是否串联了前面所有知识点

#### 维度 F：对比完整性
检查每篇是否包含「与同类方案/原生方案」的对比：
- 按篇目主题识别对比点：核心概念篇 → 架构对比；功能篇 → 实现方式对比；实战/总结篇 → 整体选型对比
- 对比要落到具体维度：性能、API 设计、适用场景、生态成熟度、迁移成本，而非只罗列名词

**对比应出现在每篇文末（面试模板之前），至少覆盖「本技术 + ≥1 个同类方案 + 原生/基线方案」的三角对比**（如 Konva vs fabric.js vs 原生 Canvas、Electron vs Tauri vs 原生开发）。

## 输出格式

### 总体评分（必须先输出，先给总评分数与一句话结论，再展开下述各节）

```
## 📊 {章节名} 文档质量 Review

**总评：X/10** —— 一句话结论。

### 一、格式规范度（对照 readme 模板）

| 规范要求 | 01 | 02 | 03 | 04 | 05 | 06 |
|----------|:--:|:--:|:--:|:--:|:--:|:--:|
| 文件命名 `XX-模块名.md` | ✅ | ✅ | ✅ | ... | ... | ... |
| 头部元信息 | ✅ | ... | ... | ... | ... | ... |
| 代码示例分级合规（简单→可运行；复杂→标注伪代码） | ✅ | ... | ... | ... | ... | ... |
| 练习环节（要求+提示+预期效果） | ... | ... | ... | ... | ... | ... |
| 面试回答模板 | ... | ... | ... | ... | ... | ... |
| 对比说明 | ... | ... | ... | ... | ... | ... |
| 参考链接/出处 | ... | ... | ... | ... | ... | ... |
```

### 二、逐篇亮点与不足（⭐评分）

每篇都使用以下格式：

```markdown
#### [01-核心概念与初始化.md](file:///absolute/path) ⭐⭐⭐⭐⭐

**亮点**：
- xxx（具体指出哪个设计好、为什么好）
- xxx

**不足**：
- xxx（明确指出缺失什么、影响是什么）
- 无（如果确实完美）
```

### 三、整体评价表

| 维度 | 评分 | 说明 |
|------|:--:|------|
| 格式规范性 | X/10 | ... |
| 代码可运行性 | X/10 | ... |
| 面试导向性 | X/10 | ... |
| 知识覆盖度 | X/10 | ... |
| 渐进式学习 | X/10 | ... |
| 对比完整性 | X/10 | ... |
| **总评** | **X/10** | **一句话总结** |

### 四、改进建议（按优先级分级）

建议必须分入三档，按 P0 → P1 → P2 顺序输出：

| 级别 | 定义 | 示例 |
|:--:|------|------|
| **P0** | 正确性问题：技术事实错误、代码照抄即错、安全风险 | API 参数错误、示例逻辑缺陷、未生效的弃用断言 |
| **P1** | 规范与结构问题：违反项目级规范、关键板块缺失 | ASCII 技术图未转 Mermaid、缺对比板块、跨文档矛盾 |
| **P2** | 小瑕疵：版本偏旧、措辞、风格不一致 | 注释中版本号过旧、依赖版本偏旧 |

每条建议格式：
```
1. **[P0] 模块 XX 修正 XXX**：当前是 YYY（验证状态：已验证+来源 / 存疑），应为 ZZZ。影响：XXX。
```

### 五、总体结论

一段话总结文档的整体质量水平，是否达到教学目标。

## 审查 + 修改闭环（第二阶段）

用户的请求常是「review 并按建议修改」。输出审查报告后进入修改阶段：

### 1. 修改顺序

P0 → P1 → P2：先修完全部正确性问题，再处理规范问题，最后是小瑕疵。

### 2. 修改策略

- 单点、局部的问题直接修改
- 大规模机械性变更（如几十张 ASCII 图转 Mermaid）用 Task 工具委派子代理并行处理，任务描述中写明范围、规则与验收标准，完成后抽查验证子代理产出
- 修改保持外科式：只改审查报告中列出的问题，不顺手做无关「优化」

### 3. 回归验证（修改后必做）

- **结构验证**：代码围栏配对（每个文件 ``` 计数为偶数）、Mermaid 块语法完整
- **残留验证**：用 Grep 批量检查同类问题是否清干净（如转换 ASCII 图后 grep 剩余制表符；区分目录树、UI 示意草图等合法例外）
- **一致性验证**：修改是否引入新矛盾（新表述与其他文档、版本表格是否一致）

### 4. 汇报

向用户输出完整修改清单：按 P0/P1/P2 分组，每项注明文件、问题、修改内容；被验证推翻的疑似项也要说明（体现验证过程）。

---

## 审查原则

1. **以模板和项目规范为准**：格式检查严格对照项目级写作规范与用户提供的参考模板，不自行发明标准
2. **以可运行为底线**：简单/自包含的代码片段必须完整可运行；中间态以「最小可运行（显式标注 mock）」优先；复杂强依赖场景允许**显式标注的高质量伪代码**，但禁止「未标注的伪可运行代码」（看似可跑、照抄即错）
3. **以面试为导向**：技术教学的最终验收标准是「面试能答、功能能做」，评估时要时刻对照这个目标
4. **以官方文档为准绳**：API 名称、参数、返回值、边界行为等技术细节，按 §2.5 分级验证协议对照**官方文档**核实。不要凭记忆判断"这个 API 大概是这样"，只有官方文档才算是权威来源
5. **先验证后结论**：每条 P0 级判定必须附验证来源或标注「存疑」，凭记忆的结论不得直接写入报告
6. **指出具体位置**：每一条不足都要指向具体的文件、行号或段落，附带修改方向
7. **正面引导**：评分可以严格，但表述要建设性——不只说「缺了什么」，还要说「加什么、加在哪里」
8. **以可溯源为质量线**：教学文档应在版本断言、API 用法、新特性处**适当附官方文档/Release Notes 链接**（写作侧要求，与 §2.5 验证协议同源），让读者能核对与深挖、避免知识孤岛；审查发现关键断言无出处时提示补链（通常 P2）

## 使用示例

**用户输入**：
> review 一下 `konva/doc` 文档质量，参考 `readme.md` 的格式规范

**Skill 执行步骤**：
1. 检查 `agents.md` 等项目级写作规范，再读取 `readme.md`，提取格式要素清单作为评审基线
2. 批量读取 6 篇 doc 文档全文
3. 对必查类技术断言（版本号、弃用声明等）做官方文档验证
4. 逐篇按六维度评分，生成格式规范度矩阵表
5. 撰写逐篇亮点/不足，给出整体评价
6. 改进建议按 P0/P1/P2 分级输出，附结论
7. 若用户要求修改，按「审查 + 修改闭环」执行并完成回归验证
