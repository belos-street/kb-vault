# 教学大纲设计师 (Syllabus Designer)

为新技术主题设计教学文档大纲：在动笔写文档之前，产出篇目规划（分层递进、每篇一句话定位、知识点/练习/面试点分配、学习路径图），并与 `doc-quality-reviewer` 共用验收标准，形成「设计 → 写作 → 审查」闭环。

---

## 触发条件

当用户提出以下请求时，应调用此 Skill：
- "设计一份 xxx 的教学大纲"
- "规划 xxx 教程的章节结构"
- "我想写一套 xxx 学习文档，先列个大纲"
- "xxx 文档应该分几篇、怎么排序"

---

## 设计流程

### 0. 读取基线规范

- 读取 `agents.md`，提取项目级写作规范（Mermaid 绘图、文件命名、LaTeX 公式、Demo 技术栈等）
- 读取 1~2 个已有章节的 `readme.md`（如 `src/front/cross-platform/` 下的章节），提取已固化的章节组织惯例（学习路径图、篇目表格、格式要素），保持新章节与既有章节风格一致

### 1. 明确目标（不清楚就问用户）

必须确认四项，缺一须向用户提问：

| 项目 | 说明 |
|------|------|
| 目标读者 | 默认按 agents.md 作者画像（资深前端/全栈，无需基础科普） |
| 前置要求 | 学本主题前需要已掌握什么 |
| 学习目标 | 学完能做出什么（功能导向） |
| 面试目标 | 学完能答什么（面试导向，本仓库的验收标准是「面试能答、功能能做」） |

### 2. 技术调研（防过时）

用 WebSearch 确认主题的现状，避免大纲建立在过时信息上：
- 当前稳定版本与主流选型（如脚手架、构建工具、状态管理）
- 重大近期变更（弃用、架构变化）
- 同类方案对比格局（用于规划对比板块）

来源分级与时效性规则同 `doc-quality-reviewer` §2.5：官方域名 > GitHub releases > 官方博客；「最新版本」类结论须对照当前日期核实。

### 3. 知识点分解与依赖分析

- 列出该主题的核心知识点（建议 20~40 个，粒度以「一个知识点 = 一个可独立讲解的块」为准）
- 标注前置依赖关系，形成依赖链：先学的必须是后学的前置
- 识别面试高频点（原理、对比、陷阱类），后续优先分配篇幅

### 4. 分层与分篇

采用六层递进模型（可按主题裁剪，但顺序不变）：

| 层 | 定位 | 回答的问题 |
|------|------|-----------|
| 认知层 | 技术全景与选型定位 | 「这是什么、为什么学、和谁比」 |
| 核心层 | 核心原理与心智模型 | 「底层怎么工作的」 |
| 基础层 | 必须先立的底线（如安全、规范） | 「写功能前必须知道什么」 |
| 应用层 | 按功能域逐个击破 | 「怎么实现具体功能」 |
| 工程层 | 调试、打包、性能、坑点 | 「怎么上生产」 |
| 速查层 | 生态选库、API 速查 | 「随用随查」 |

分篇原则：
- 每篇一个主题，命名 `XX-模块名.md`（XX 为两位序号）
- 每篇学习量控制在一次专注会话内（约 30~60 分钟）
- 篇与篇之间严格沿依赖链递进，不出现「后文才讲的概念前文先用」
- 总篇数建议 10~16 篇；知识点过多时合并为速查篇，而非无限拆篇

### 5. 每篇要素分配

每篇规划必须包含以下要素（与 doc-quality-reviewer 的格式检查对齐）：

- **一句话定位**：这篇在整个体系中解决什么问题
- **头部元信息**：模块映射、预计时间、「面试可答」一句话摘要
- **核心知识点**：本篇覆盖的知识点编号
- **代码示例要求**：完整可运行（非伪代码），依赖与声明齐全
- **练习**：要求 + 提示 + 预期效果三段式，难度跨篇递增
- **面试问答**：本篇对应的面试点（含追问：陷阱、对比、原理）
- **对比板块**：文末三角对比（本技术 + ≥1 同类方案 + 原生/基线方案）

### 6. 输出大纲文档

按以下结构输出（可直接作为目标章节 `readme.md` 的底稿）：

```markdown
# 《技术名》学习大纲

## 1. 定位
| 项目 | 内容 |
|------|------|
| 目标读者 | ... |
| 前置要求 | ... |
| 学习目标 | ... |
| 面试目标 | ... |

## 2. 学习路径图

（Mermaid graph：各层节点 + 每层知识点标注，禁止 ASCII 流程图）

## 3. 篇目规划

| 序号 | 篇名 | 层 | 一句话定位 | 核心知识点 | 前置篇目 |
|------|------|----|-----------|-----------|---------|
| 00 | ... | 认知层 | ... | ... | 无 |

## 4. 练习递进线
（跨篇练习的难度递进设计：基础操作 → 组合应用 → 实战整合）

## 5. 面试覆盖图
| 高频面试点 | 覆盖篇目 |
|-----------|---------|
| ... | ... |
```

### 7. 自检（与 doc-quality-reviewer 对齐）

大纲输出前逐项确认：

- [ ] 每篇有一句话定位，且篇目沿依赖链递进（对应 reviewer 维度 E）
- [ ] 每篇分配了练习与面试点，难度/深度递增（维度 C、E）
- [ ] 每篇有对比板块规划（维度 F）
- [ ] 技术选型与版本已经官方资料验证、未过时（§2.5 协议）
- [ ] 学习路径图为 Mermaid，符合 agents.md 绘图规范（维度 A）
- [ ] 篇目命名符合 `XX-模块名.md` 规范（维度 A）

## 设计原则

1. **面试导向**：「面试能答、功能能做」是最终验收标准，每个知识点都要能回答「这在面试里怎么考」
2. **渐进优先**：宁可多分一层铺垫，不出现知识断层；每篇都能独立回答「为什么排在这里」
3. **先调研后设计**：选型与版本结论必须来自官方资料，不凭记忆规划
4. **与既有章节一致**：组织形式沿用仓库已有章节的惯例，不另起炉灶
5. **大纲即契约**：大纲确定后，写作阶段按篇目填充，审查阶段用 doc-quality-reviewer 对照同一标准验收

## 使用示例

**用户输入**：
> 设计一份 D3.js 的教学大纲

**Skill 执行步骤**：
1. 读取 agents.md 与已有章节 readme，提取组织惯例
2. 确认目标四要素（读者/前置/学习目标/面试目标），缺失则提问
3. WebSearch 确认 D3 当前版本、v7 模块化格局、与 ECharts 等方案的对比定位
4. 分解知识点（selection、data join、scale、axis、transition、布局…）并排依赖链
5. 按六层模型分篇，每篇分配定位、知识点、练习、面试点、对比对象
6. 输出大纲文档（定位表 + Mermaid 学习路径图 + 篇目规划表 + 练习递进线 + 面试覆盖图）
7. 跑自检清单后交付，供写作阶段与 doc-quality-reviewer 审查共用
